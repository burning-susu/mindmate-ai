
## 7. 工时估算

### 7.1 主估算：执行 Flow 驱动

正式估算顺序：

```text
选择 EXECUTION_FLOW
        ↓
拆真实 Flow 工作块
        ↓
合并联调 / 自测 / 修复循环
        ↓
识别 AI 批量生成、复用、并行和重叠
        ↓
估算真实有效投入
        ↓
得到 Flow Estimate
        ↓
真实生产率校验
        ↓
高相似度历史项目校验
        ↓
项目类型区间弱校验
        ↓
异常门禁
```

> **Flow Estimate 是唯一主估算来源。**

### 7.2 工作块有效工时

```text
工作块有效工时
= AI 生成 / 修改
+ 人工 Review
+ 必要联调
+ 必要验证
+ 实际修复
```

禁止：

```text
联调完整工时
+ 测试完整工时
+ 修复完整工时
```

如果它们本来就是同一个迭代循环。

### 7.3 FLOW-01 去重规则

对 `FLOW-01`：

1. 用户端 Mock 不包含管理后台完整页面。
2. Mock → 真实 API 只估增量适配。
3. 联调 + 自测 + 常规回归 + 缺陷修复合并为 `F01-E`。
4. `F01-F` 只放尚未覆盖的专项验证，不固定预留大额工时。
5. 管理后台只估复用稳定 API / 数据 / 权限后的新增成本。
6. 最终测试只估尚未覆盖专项、全量回归、UAT 和发布准入。

### 7.4 历史真实生产率校验

即使历史项目不是“高相似度项目”，只要满足以下部分条件，就必须作为生产率旁证：

- 同一开发者或同一团队；
- 相近的 AI 主执行方式；
- 相近的软件项目规模；
- 有真实完成工时/工作日。

不得因为“项目类型不完全相同”就写成“无历史记录”。

必须输出：

```text
生产率倍率
= Flow Estimate ÷ 历史真实工时
```

门禁：

| 倍率 | 处理 |
|---|---|
| ≤1.3x | 一般合理 |
| 1.3x～1.5x | 解释新增复杂度 |
| 1.5x～1.8x | 强制逐项复核 Flow 工作块 |
| >1.8x | 默认重新估算 |
| >2.0x | 除非范围/团队/合规显著变化，否则不得直接基线 |

### 7.10 异常门禁

必须同时检查：

1. Flow 工作块是否有重复；

### 7.11 生成后跨章节一致性硬校验

正式输出前，AI **必须重新做算术求和**，不得只读取各表格底部手写的“合计”字段。

必须实际计算：

```text
SUM(Flow 工作块有效工时)
SUM(管理阶段工时)
SUM(阶段详细计划中的工时分配)
```

并验证：

```text
SUM(Flow 工作块)
=
SUM(管理阶段)
=
SUM(阶段详细计划分配)
=
Flow Estimate
```

正式总工时另行验证：

```text
正式计划总研发工时
=
Flow Estimate
+ 已确认必做且 Flow 未覆盖的特殊增量
```

第 7、10、14 章必须使用同一个正式计划总研发工时。

#### A. 关键路径一致性

关键路径不是第二套总工时，但其中引用的工作块工时必须来自**当前版本**。

生成后必须检查：

- 是否残留上一版工作块数字；
- 是否把已经合并的“联调 / 测试 / 修复”重新写成旧的大工时；
- 是否把并行工作机械求和成关键路径日历周期；
- 关键路径说明是否明确“用于依赖/日历，不用于第二次求总工时”。

发现旧数字时必须重新生成关键路径，不得保留。

#### B. 历史生产率一致性

如果文档任一章节已经存在历史真实生产率：

- 后续章节不得写“无真实历史工时”“旁证缺失”；
- “高相似度历史基准不存在”与“存在生产率旁证”必须区分；
- 生产率倍率必须使用同一历史实际工时和同一 Flow Estimate 计算。

#### C. 版本一致性

生成后必须检查：

```text
文档标题版本
=
版本记录中的当前版本
=
变更记录引用的当前模板/规则版本（如适用）
```

不得出现文件标题已升级但版本记录仍停留在旧版本。

#### D. 条件风险一致性

必须验证：

```text
条件风险储备
∉ 正式计划总研发工时
```

只有已经确认必做、且 Flow Estimate 未覆盖的增量才允许进入正式工时。

#### E. 输出门禁

以下任一情况存在时，不得输出“已通过一致性校验”：

- 实际求和不一致；
- 阶段映射有工作块工时丢失；
- 同一工作块被跨阶段重复分配；
- 关键路径保留旧版本工时；
- 历史生产率前后矛盾；
- 版本号前后矛盾；
- 条件风险误计入正式工时。

允许四舍五入误差：

```text
≤ 1h
```

超过则必须自动修正后再输出。

# 使用说明

这两份模板定位为**公司对外/对内正式项目文档**，重点是让产品、项目负责人、技术负责人、开发和测试都能快速看懂。

不建议把以下 AI 工程治理概念直接放入公司主文档：
- Project Profile
- Assessment
- Capability
- Workflow
- DEC
- Batch
- Evidence
- TRACE
- Progress Register

这些内容继续由内部 AI 开发治理体系维护。

推荐的文档关系：

```text
公司层
├── 通用技术架构选型说明书
├── 通用AI开发执行流程
└── 通用项目开发计划

项目层
├── PRD / 需求规格说明书
├── 技术架构说明书
├── API文档
├── 数据库设计
├── 项目开发计划
├── 测试文档
└── 发布/部署文档

AI治理层（内部）
├── 通用文档提示词 v3.2
├── Project Profile
├── Assessment
├── Capability
├── Workflow
├── DEC
├── Batch
├── Evidence
├── TRACE
└── Progress Register
```

核心原则：

> **公司文档负责“讲清楚”，AI治理文档负责“管得住”。**
>
> **开发执行流程负责“怎么开发”，项目开发计划负责“按这个 Flow 要花多久、怎么排”。**

对于采用 AI 辅助或 AI 主执行的项目，还应遵守：

> **开发计划必须反映真实 AI 开发生产率。历史实绩优先于传统人工经验，项目级总工时优先于细任务机械累加。开发手册和治理体系的作用应是降低返工、提高质量和稳定性，而不是把相同项目的计划工时放大数倍。**

# AI 工时估算示例

## 示例一：类似小程序项目

历史：

```text
小程序 + 后台 + 后端
AI 主执行
实际 20 天 × 8h = 160h
```

当前项目：

```text
同类型
但新增更复杂的离线、资金和真机验证
```

合理做法：

```text
160h
→ 只对新增差异修正
→ 加少量治理/验证
≈ 190～230h
```

## 示例二：门户网站

历史：

```text
复杂小程序项目 = 160h
```

当前：

```text
企业门户 + CMS
无离线
无资金
无复杂真机
```

错误：

```text
直接以 160h 为门户基准
```

正确：

```text
识别为“内容门户 + CMS”
→ 使用门户参考区间 60～120h
→ 再按真实需求修正
```

## 示例三：大型多系统项目

如果项目包含：

- 多个业务系统；
- 多团队；
- 大规模数据迁移；
- 强合规；
- 多环境、多区域；
- 大量第三方系统；

则不受普通 120～320h AI 项目区间约束，应专项估算。

> **最终目标：不是把所有项目压到同一个工时，而是让每个项目使用“正确项目类型 + 正确历史基准 + 正确差异修正”。**
