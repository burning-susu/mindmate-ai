# 通用 AI 开发执行流程（公司版）V3.2

> 适用范围：采用 AI 辅助或 AI 主执行的软件项目，包括 Web、管理后台、小程序、App、H5、前后端分离项目及其他软件项目。  
> 文档定位：定义“项目在实施阶段具体怎么开发”，不替代 G0～G11 生命周期 Workflow，不替代项目开发计划。  
> 核心原则：**先选择适合项目的执行 Flow，再按 Flow 工作块实施和估时；Flow 是实施阶段内部路径，不是新的治理阶段。**

---

## 0. 文档边界

本手册回答：

> **项目进入开发实施后，工作按照什么顺序、并行关系和验证方式推进？**

不回答：

- 项目当前处于 G0～G11 哪一阶段；
- PRD 是否批准；
- 技术栈如何选型；
- 项目总工时最终是多少；
- 哪个业务决策应由谁批准。

这些分别由 Workflow、PRD、技术架构、项目开发计划和治理机制负责。

### 0.1 与现有概念的关系

```text
PROJECT_PROFILE / ASSESSMENT
        ↓
WORKFLOW BLUEPRINT（G0～G11）
        ↓
G10 DELIVERY / G11 IMPLEMENTATION
        ↓
选择 EXECUTION FLOW
        ↓
按 Flow 工作块开发、联调、测试和修正
        ↓
项目开发计划按 Flow 工作块估时和排期
```

> `WORKFLOW` ≠ `EXECUTION FLOW`。  
> Workflow 管生命周期和治理门禁；Execution Flow 管实施阶段内部的实际开发方式。

---

## 1. Flow 选择原则

生成项目开发计划或进入实施前，必须先选择一个主执行 Flow。

选择依据至少包括：

| 维度 | 判断内容 |
|---|---|
| 项目类型 | 门户 / 管理后台 / Web 业务 / 小程序 / App / 多端系统 / 后端服务 |
| API 现状 | 无 API / API 待设计 / API 已稳定 / 第三方 API |
| UI 成熟度 | 无 UI / 原型 / 高保真 / 已有系统 |
| 前后端关系 | 同人/少人一体开发 / 独立前后端团队 / 仅前端 / 仅后端 |
| 设备与平台能力 | 无 / 浏览器 / 微信 / 原生设备能力 |
| 高风险能力 | 离线、支付、资金、身份、敏感数据、复杂第三方 |
| 交付方式 | 新项目 / 增量迭代 / 迁移 / 重构 |
| AI 参与程度 | 辅助 / AI 主执行 + 人工 Review |

### 1.1 Flow 状态

- `PROPOSED`：已推荐但未确认；
- `CONFIRMED`：已确认，可用于计划和开发；
- `STALE`：项目事实变化，需要重选或复核；
- `SUPERSEDED`：被新 Flow 替代，保留历史。

### 1.2 Flow 变更

如果项目中途发生以下变化，应重新评估 Flow：

- 从单端扩展为多端；
- API 从“待开发”变成“已有成熟 API”；
- 新增复杂离线/支付/设备能力；
- 团队从单人变多人并行；
- 开发模式从 AI 主执行改为传统团队分工；
- 前端、后端或后台的依赖关系发生明显变化。

Flow 变化不等于推翻项目 Workflow。只更新实施路径及受影响计划。

## 2. FLOW-01：AI 前端 Mock 先行型

### 2.1 适用场景

优先适用于：

- 新建小程序 / Web 前端 + 后端项目；
- 单人或少量开发者；
- AI 主执行 + 人工决策/Review；
- 页面和交互可先于真实 API 开发；
- 后端 API 尚未完成；
- 管理后台可以复用稳定后的 API 和数据模型。

### 2.2 默认执行顺序

```text
需求 / UI / 核心业务规则
        ↓
关键技术 Spike
        ↓
轻量 API / Data Contract
        ↓
前端页面 + Mock
        ├──────────────┐
        │              │ 并行
        ↓              ↓
前端状态/交互       后端环境/基础软件
                       ↓
                  后端数据模型/API
                       ↓
        └──────────────┘
                ↓
            前后端联调
                ↓
Mock / Contract / API / 类型持续对齐
                ↓
边调试 + 边测试 + 边改代码
                ↓
用户端/小程序主链路基本稳定
                ↓
管理后台集中开发
                ↓
后台与后端联调
                ↓
专项回归 / UAT / 发布
```

### 2.3 工作块

| 工作块 | 主要内容 | 是否可并行 | 工时计量原则 |
|---|---|---|---|
| F01-A 前置收口 | PRD、UI、核心规则、Spike、轻量 Contract | 部分 | 只计算必要决策/验证 |
| F01-B 前端 Mock | 页面、交互、状态、Mock、异常态 | 可与后端环境并行 | AI 批量生成和复用应折减 |
| F01-C 后端环境 | DB、Redis、对象存储、网关、容器、配置 | 可与前端并行 | 只计算真实安装/调试 |
| F01-D 后端核心 | 数据模型、API、业务规则、状态机 | 部分 | 高风险业务不应过度折减 |
| F01-E 联调验证循环 | Mock→真实 API、字段/状态/错误对齐、开发自测、必要回归和缺陷修复 | 与后端/前端修正交替 | **联调+测试+修复作为同一循环估算，不拆成多个大工时块** |
| F01-F 专项验证 | 真机矩阵、弱网、性能、安全、资金等“尚未在 E 中覆盖”的专项 | 仅按需要触发 | **只计算剩余专项增量；常规验证不得重复计时** |
| F01-G 后台管理 | 复用 API/数据/权限后的运营后台 | 主链路稳定后 | 按边际成本，不按新系统从零算 |
| F01-H 收口发布 | 专项回归、UAT、部署、发布、交接 | 后期 | 仅剩余专项与发布工作 |

### 2.4 Mock 规则

Mock 不是随意假数据，至少要对齐：

- 接口用途；
- 请求/响应字段；
- 状态枚举；
- 错误结构；
- 分页/时间/幂等等公共规则。

建议：

```text
轻量 Contract
→ Mock
→ 页面
→ 后端实现
→ 联调时校正 Contract
```

禁止：

```text
Mock 随意设计
→ 后端独立设计另一套接口
→ 联调阶段大规模重写前端
```

### 2.5 “主链路基本稳定”判定

满足以下多数条件即可开始集中做后台，不要求用户端 100% 完成：

- 核心实体基本稳定；
- 主要状态机基本稳定；
- 核心 API 不再频繁 Breaking Change；
- 登录/权限模型基本稳定；
- 核心业务正常路径可重复运行；
- 高风险技术能力已完成必要 Spike。

## 3. FLOW-02：API / 后端先行型

适用于：

- 业务规则和数据模型复杂；
- 多个前端依赖统一 API；
- Contract 稳定性比页面先行更重要；
- 前端团队可稍后并行接入。

```text
业务规则/状态机
→ 数据模型
→ API Contract
→ 后端核心实现
→ Mock Server / API 可用
→ 前端并行接入
→ 联调与持续测试
→ 后台/辅助端
→ 回归/发布
```

工时重点在状态机、数据、API 和核心业务，不应把多个前端重复计算同一后端能力。

---

## 4. FLOW-03：已有 API 前端接入型

适用于：

- 后端或第三方 API 已成熟；
- 主要任务是 Web / 小程序 / App 前端；
- API 变更权较低。

```text
API 盘点
→ 类型/Mock 生成
→ 页面和状态
→ 真实 API 接入
→ 异常/权限/边界
→ 回归
→ 发布
```

估时时不应包含“从零后端开发”。

---

## 5. FLOW-04：门户 / 内容站型

适用于：

- 企业官网、门户、内容站、CMS；
- 强展示、弱业务状态；
- 无复杂资金、离线和设备能力。

```text
信息架构/内容模型
→ 页面骨架
→ 组件/视觉
→ CMS/内容接口
→ SEO/性能/响应式
→ 内容验收
→ 发布
```

如果仅展示站点，不应套用小程序 + 后端 + 管理后台的复杂 Flow。

---

## 6. FLOW-05：纯后端服务型

适用于：

- API 服务、数据处理、任务调度、平台服务；
- 无前端或前端不在本项目范围。

```text
规则/数据/状态
→ Contract
→ 环境
→ 核心服务
→ 集成测试
→ 性能/安全
→ 部署发布
```

---

## 7. FLOW-06：多端并行型

适用于：

- 多个成熟团队；
- 多个前端/客户端同步开发；
- API Contract 较早冻结；
- 明确的独立负责人和集成节奏。

```text
Contract / Data Baseline
        ↓
后端核心 ────────────────┐
Web 前端 ────────────────┤
小程序/App ──────────────┤ 并行
后台管理 ────────────────┘
        ↓
分批集成
        ↓
跨端回归
        ↓
UAT / 发布
```

不适合单人开发时机械套用，否则会制造虚假并行和重复工时。

## 9. Flow 驱动工时估算规则

项目开发计划必须首先按 Flow 工作块估算。

### 9.1 主估算

```text
Flow 工作块
→ 识别真实工作内容
→ 合并同一迭代循环
→ 去除并行 / 复用 / 重叠
→ 估算真实有效投入
→ 得到 Flow Estimate
```

### 9.2 Flow 工作块不得“换名后继续传统估时”

Flow 工作块不是传统阶段的改名版。

对于 AI 主执行项目：

- 不得把“联调”“持续测试”“缺陷修复”分别估成三个完整大块；
- 不得把“Mock 页面”和“真实 API 页面”估成两套完整前端；
- 不得把“用户端已验证 API”在管理后台中再次按后端从零开发；
- 不得把同一轮 AI 同时生成的代码、类型、Mock、测试和文档按五份纯人工工时累计；
- 不得为了让总工时落入项目类型区间而反向放大各 Flow 工作块。

### 9.3 FLOW-01 默认估时合并规则

对 `FLOW-01`：

```text
F01-A 前置收口 / Spike
F01-B 用户端页面 + Mock
F01-C 后端环境
F01-D 后端核心
F01-E 联调 + 持续测试 + 修复循环
F01-F 未覆盖专项验证（条件触发）
F01-G 管理后台边际开发
F01-H 最终回归 / UAT / 发布
```

其中：

1. `F01-E` 必须把常规联调、自测、接口验证、缺陷修复合并估算。
2. `F01-F` 不是固定必加的大工时块；只有明确存在额外专项时才计入。
3. `F01-G` 只估复用稳定 API / 数据模型 / 权限后的新增页面与运营逻辑。
4. `F01-H` 不得再次包含已经在 `F01-E/F01-F` 完成的测试。

### 9.4 历史真实生产率必须参与异常校验

历史实绩分两类：

- **高相似度历史项目**：可作为强校验基准；
- **低/中相似度但同一开发者、同一 AI 主执行模式的真实生产率**：必须作为生产率旁证。

不得因为“不是完全同类”就把真实生产率从校验中删除。

至少输出：

```text
当前 Flow Estimate ÷ 历史真实工时 = 生产率倍率
```

建议门禁：

| 相对历史真实生产率 | 处理 |
|---|---|
| ≤1.3x | 一般合理 |
| 1.3x～1.5x | 说明新增复杂度 |
| 1.5x～1.8x | 强制逐项解释 Flow 工作块 |
| >1.8x | 默认需要重估 |
| >2.0x | 除非范围/团队/合规显著变化，否则不得直接采用 |

> 即使历史项目不是高相似度项目，只要开发者、AI 主执行方式和项目规模有参考意义，就不能忽略这项异常校验。

### 9.5 项目类型区间只做弱校验

项目类型参考区间用于发现明显离谱结果，优先级低于：

1. 真实 Flow 工作块；
2. 用户/团队真实生产率；
3. 高相似度历史项目。

不能因为：

```text
Flow Estimate 落在“180～320h”
```

就自动判定合理。

如果真实生产率显示异常，应优先检查 Flow 工作块是否重复、过度保守或仍在套传统人工估时。

### 9.6 风险与条件储备

风险分两类：

#### 已发生 / 高确定性额外工作

满足以下条件才计入正式计划工时：

- 已知必做；
- Flow 工作块尚未覆盖；
- 有明确触发事实或交付要求；
- 可说明为什么不是常规开发工作。

#### 未发生 / 不确定风险

只登记为：

```text
条件储备 / 风险储备
```

默认**不计入正式计划总研发工时**。

例如：

- Provider 账号异常；
- 额外真机兼容问题；
- 尚未确认的性能整改；
- 尚未发生的安全返工。

只有风险实际触发后再通过变更更新计划。

### 9.7 禁止重复

以下不得重复累计：

- Mock 页面开发 + 真实 API 接入作为两套完整前端；
- 联调 + 持续测试 + 缺陷修复作为多个完整阶段；
- Flow 已包含的 Provider、真机、资金、安全、发布再次作为固定“特殊增量”；
- 管理后台复用稳定 API 后仍按一套新系统从零估算；
- 项目类型区间已经隐含的常规风险再次加时。

### 9.8 总工时公式

默认：

```text
正式计划总研发工时
= Flow Estimate
+ 已确认且 Flow 未覆盖的必做增量
```

不包含：

```text
未触发风险储备
外部平台等待
客户等待
审核等待
```

这些单独记录。

## 10. 测试在 Flow 中的位置

默认采用：

```text
实现
↕
联调 / 自测 / 修正
↕
必要专项验证
```

而不是：

```text
全部开发完成
→ 独立大测试阶段
→ 大量返工
```

最终测试阶段主要负责：

- 未覆盖的专项测试；
- 全量回归；
- 真机/平台矩阵；
- 性能/安全；
- UAT；
- 发布准入。

## 12. 公司级原则

> **项目计划不是先拍一个总工时，再把数字分给阶段。**
>
> **正确顺序是：选 Flow → 按真实工作块估有效投入 → 去重叠/复用 → 得到总量 → 用历史和项目类型做校验 → 排期。**

> **开发手册的作用是提高稳定性和降低返工，不应把 AI 主执行项目重新估成传统纯人工项目。**
