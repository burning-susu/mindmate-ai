# 小程序全栈开发与上线 SOP
> 文档类型：Capability
> Capability ID：CAP-PLATFORM-MINIPROGRAM-FULLSTACK
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G1、G3、G6、G8、G9、G10、G11
> 激活条件：PROJECT_PROFILE 识别为小程序/跨端小程序项目，且需要真实平台、真机或上线能力验证

## 0. Capability 元数据
- **目标**：提供小程序客户端、后端、管理端、平台能力、环境、联调、发布和专项验收的一体化 SOP。
- **输入**：平台类型、App/应用标识、登录/支付/存储/消息 Provider、真机范围、环境与上线目标。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。

## 0.1 定位
本文档用于 uni-app/原生小程序 + 后端 API + Web 管理后台的全栈项目。

它补充的是小程序项目特有的工程链路：平台标识、真机权限、离线能力、平台审核、支付/消息、服务器部署和正式上线；以微信为例时可进一步映射到 AppID、订阅消息等具体能力。它不替代对应 REQ 的 Spec、测试用例和验收清单。

默认原则：先定义交付口径，再设计技术方案；先建立接口和环境边界，再并行开发；Demo、体验版和正式生产环境分别验收。

## 1. 交付口径与里程碑

开始开发前必须明确以下三个里程碑，不能用“项目完成”一个词覆盖全部状态：

1. **Demo 可预览**：页面、核心流程和 Mock Provider 可以在开发者工具或测试 AppID 下展示。
2. **体验版可联调**：测试应用标识/真实测试环境、服务器、接口、对象存储和真机链路可验证。
3. **正式生产上线**：正式生产应用标识（具体名称依平台而定）、合法域名、隐私协议、平台审核、真实支付/提现、备份、监控、回滚和上线验收均已完成。

每个里程碑都要记录：代码版本、数据库版本、配置模式、测试范围、已知缺口和是否允许对外使用。

## 2. 开工前置

### 2.1 需求与 Spec

- 原始 PRD/需规文档不能直接代替 Spec。
- Spec 必须声明功能边界、数据结构、业务规则、异常处理和可验收标准。
- 另行声明目标平台、AppID 状态、登录/支付/存储 Provider、真机范围、自动化测试、性能测试和安全测试范围。
- 明确 Demo 阶段哪些能力只做 Mock，哪些能力必须在体验版或生产环境验证。

### 2.2 架构与契约

- 先确定前端、后端、后台、数据库、对象存储、缓存和消息服务的边界。
- 先建立数据字典和接口契约，再批量生成前后端代码。
- 统一字段、枚举、错误码、分页、时间时区、上传协议和鉴权方式。
- 架构或存储方案发生变化时，补 ADR 和迁移说明，不只修改架构图。

### 2.3 凭据与环境

- 密钥、密码、AppSecret、支付私钥、API v3 Key、服务器账号和 SSH 私钥不得进入 Git、压缩包、Prompt 记录或普通部署文档。
- `.env.example` 只保留变量名和占位符；真实值通过环境变量或安全的 Secret 管理注入。
- 本地、测试、体验版和生产环境使用独立配置，Provider 模式必须可见且可检查。
- 开工前先建立“敏感配置清单”和轮换责任人；发现已泄露凭据时，默认按已泄露处理并轮换。

## 3. 主线阶段

### 阶段 1：需求规格化

输入：原始需求、平台限制、已有资产。

产物：Spec、范围边界、数据结构、业务规则、异常处理、验收标准和变更记录。

退出条件：每个核心功能都有明确的“实现/不实现”和可判定验收方式。

### 阶段 2：架构、数据与接口契约

输入：定稿 Spec。

产物：架构说明、ADR、数据库 DDL、迁移策略、接口契约、错误码和环境变量清单。

退出条件：前端、后端和后台对字段、状态和 Provider 切换方式达成一致。

### 阶段 3：工程骨架与垂直切片

先初始化小程序、后端和后台工程，再优先打通一条最小垂直链路，例如“登录 → 查询任务 → 领取 → 拍照/缓存 → 提交”。

退出条件：链路可以在声明的 Demo 或测试环境中重复运行，并有最小测试数据和回滚点。

### 阶段 4：业务模块并行开发

按接口契约并行开发用户端、后端和管理端；每个模块完成后同步更新 Spec、契约、测试场景和进度日志。

不得使用一个示例模块代表全部同类模块；所有同类功能都要明确完成状态。

### 阶段 5：平台能力接入

独立管理以下能力：真实登录、隐私授权、类目/资质、合法域名、订阅消息、支付/提现、二维码/小程序码和审核发布。

每项能力记录：前置材料、申请状态、测试环境、正式环境、阻塞点和最晚启动时间。

### 阶段 6：联调与测试

至少覆盖：

- 单元/业务逻辑测试；
- 接口参数、认证、越权、状态冲突和幂等测试；
- 真机、权限、弱网、离线、GPS、文件上传和重试测试；
- Demo Provider 与真实 Provider 的切换测试；
- 支付、隐私和个人信息相关安全检查；
- 需要时再执行性能测试和接口压测。

没有运行记录、测试结果或截图证据的内容，只能标记为“待验证”，不能写成“已完成”。

### 阶段 7：部署与发布

发布前必须完成：数据库备份、迁移预演、构建产物校验、密钥注入、HTTPS/域名检查、健康检查、日志检查和回滚演练。

小程序代码、后端、后台、数据库迁移和服务器配置分别记录版本，不能只写“重新部署”。

### 阶段 8：上线验收与交接

交付物至少包括：最终代码版本、Spec/计划/测试/验收、环境变量清单、迁移记录、部署步骤、回滚步骤、备份策略、监控入口、已知问题和后续待办。

## 4. 并行工作线

以下事项可以与研发主线并行，但必须单独记录，不要强行塞进编码阶段：

- 平台类目、主体资质、隐私政策和平台审核；
- 支付商户号、商家转账、证书、回调和订阅消息模板；
- 服务器、域名、HTTPS、备案、对象存储和备份；
- 测试用户、管理员账号、真实设备和采集场景准备。

并行工作线至少维护“依赖、负责人、预计等待时间、阻塞影响、最晚启动时间”五项信息。

## 5. 变更与版本规则

- 需求变更先改 Spec，再同步计划、接口、测试和验收，最后改代码。
- 计划工期变更时，说明是范围增加、估算调整、并行工作未计入，还是质量工作被延期。
- 版本快照目录名只能作为辅助证据；最终基准优先使用 Git 提交、Tag 和服务器实际运行版本。
- 多个代码副本存在时，建立版本证据图，记录来源、差异、可运行状态和最终采用理由。

## 6. 小程序专项验收

- 首次授权、拒绝授权、重新授权和权限关闭均有结果；
- 在线、断网、弱网、冷启动、微信重启和清理缓存场景均有明确预期；
- GPS、相机、相册、定位精度、规则缓存和失败重试均有证据；
- 上传成功、上传失败、重复提交、任务过期和缓存冲突均有处理；
- 测试应用标识与正式应用标识 切换不改变业务主键和核心数据结构；
- 真实支付、隐私和平台消息能力未完成时，体验版不得宣称正式生产可用。

## 7. 适用范围声明

本 SOP 是跨项目通用流程。具体项目仍须在 REQ 的 Spec 中声明：哪些阶段适用、哪些能力不适用、采用哪种 Provider、需要哪些真实平台验证，以及最终交付口径。
