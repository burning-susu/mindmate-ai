# 响应式与浏览器兼容清单
> 文档类型：Capability
> Capability ID：CAP-UI-RESPONSIVE-COMPATIBILITY
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G5.5、G8、G9.1、G10、G11

## 0. Capability 元数据
- **目标**：提供响应式断点、网格降级、触屏交互转换、视觉状态、浏览器兼容和验收的通用检查清单。
- **输入**：目标设备/浏览器范围、设计基线、交互方式、页面类型与发布口径。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。

## 0.1 定位
本文档回答"怎么做到不同设备适配好、审美过关、浏览器兼容"这三件事的具体可执行标准。

**浏览器范围默认只覆盖 Chromium 系（Chrome/Edge/百度/360/QQ 等同内核浏览器），不含 Firefox**，理由与例外情形见第 3.0 节。

**不是所有项目都要执行本清单**：是否执行、执行到什么程度，由对应 REQ 的 `spec.md` 第0节"适用范围声明"决定。纯后端/接口项目、内部固定环境系统可以声明"不适用"或"降级执行"，不用被这套要求捆绑。

## 1. 设备适配（响应式）

### 1.1 断点标准（默认建议，项目可在 Spec 里覆盖）
- 移动端：`< 768px`
- 平板：`768px ~ 1024px`
- 桌面：`> 1024px`

**断点集合必须收敛，且在开工前就定下来（源码实测补充的硬性要求）**：

- 全项目断点取值**不超过 4 种**，且必须集中定义、全站复用。上面三档对应 2 个断点（768/1024）已能覆盖多数门户，最多再加一个大屏档。
- **反面实测经验**：真实项目中如果通过大量临时 media query 逐处修补，容易形成大量互不一致的断点，最终导致行为不可预测。因此断点必须作为项目基线统一声明。
- 自查方法：全局搜 `@media`，把断点值去重列出来。超过 4 种就说明是补丁式响应式，应当归并。
- 归并原则：优先保留与设备类别对应的断点（768/1024），把相邻的零散值（如 860/880/900）合并到同一档，宁可某个组件在某个宽度下不是最优，也要保证整站行为可预测。

### 1.2 硬性要求
- [ ] 页面 `<head>` 包含 `<meta name="viewport" content="width=device-width, initial-scale=1.0">`
- [ ] 布局使用相对单位（`%`、`rem`、`flex`、`grid`），禁止用固定 `px` 写死容器宽度
- [ ] 图片/媒体元素设置 `max-width: 100%`，避免溢出容器
- [ ] 在浏览器开发者工具里至少切到一个手机尺寸和一个平板尺寸实测过，不只测桌面默认窗口
- [ ] 小程序项目不适用本节（rpx 单位规则见 `设计稿转代码流程.md` 第6节），走小程序专属机型适配规则

### 1.3 排版适配方法论（多列布局、字号缩放、hover→触屏交互转换）

> 背景：1.1/1.2 节只回答"断点定在哪、要不要测过"，没回答"断点两侧具体怎么排版、hover 类交互在触屏上怎么办"。这两个问题此前是空白，2026-09-07 补充。

#### 1.3.1 断点数值的用法
- 项目级默认仍是三档（移动 `<768px`、平板 `768-1024px`、桌面 `>1024px`），用于 Spec 里声明适用范围、判断"要不要做移动适配"。
- 单个组件内部允许比三档更细，但同一组件的多级断点必须保持连续递减、不要和三档标准混着用不一致的临界值（比如同一意图的"收窄一档"，一个组件写 768、另一个写 720，等价语义应统一数值）。
- 内容密集型页面（多列卡片墙、大量图文模块）如果三档不够用，可参考更细的六级序列：`1600/1400/1200/1024/768/480`，其中 `1200px` 常作为"桌面横向导航→触屏汉堡菜单"的关键转折点，`480px` 用于超窄机型（iPhone SE 等）二次收缩。是否启用六级序列按组件复杂度判断，不强制。

#### 1.3.2 多列网格降级规则
- 桌面（`>1024px`）：设计稿定的原始列数（3~5 列均可）。
- 平板（`768-1024px`）：降一档，即 4 列→3 列、3 列→2 列。
- 手机（`<768px`）：卡片型内容（图+标题+简介）收为 2 列，纯列表型/图文说明型内容直接收为 1 列。
- 超窄机型（`≤480px`）：即使平板档给了 2 列，也要判断内容宽度是否够用，不够则进一步收为 1 列，不能只信任"移动端统一 2 列"这一条粗规则。
- 表格类元素（`<table>` 或表格样式的 div 网格）：列数超过 2 列时，必须用容器包裹并设置 `overflow-x: auto`，不能假设文字会自动收缩换行——固定列数的表格在窄屏下几乎必然被压变形或挤出容器。
- **平板档不是必经步骤**：如果 Spec 声明该项目排版适配范围只做 PC + 手机（平板不适用），直接跳过 `768-1024px` 这一档规则，桌面列数在 `<1024px`（或项目自定的单一断点）直接收为手机档列数（2 列/1 列），不需要先经过"降一档"的中间态。是否设中间档取决于是否声明要适配平板，不是排版方法论本身的强制要求。

#### 1.3.3 字号/间距缩放规则
- 优先用 `html` 根字号分级 + 组件内部 `rem` 单位做整体等比缩放（例如 `>1600px=16px，1024-1600px=14px，<1024px=13px`），不要给每个标题单独写一份 `clamp()` 再逐个人工核对——分级缩放改一处、全站生效，`clamp()` 写多了容易各组件缩放节奏不一致。
- 大标题（`h1`/hero 主标题）如果中文字数较多（约 20 字以上），`clamp()` 数值上"缩小了"不代表视觉上没问题：必须在最窄断点下实际看一眼换行行数。超过 3 行说明字号策略不够，需要缩短文案或改变排版（如换行点手动控制），不能只看 `clamp()` 参数就判定"已适配"。

#### 1.3.4 hover → 触屏交互转换规则（核心缺口，此前完全空白）
触屏设备没有 hover 态，任何仅靠 `:hover` 触发的功能性交互（展开菜单、显示子级列表、显示悬浮说明），到了触屏设备上等同于**功能失效**，不是"体验打折"。判定与处理原则：

- **判定范围**：CSS 里任何 `:hover` 选择器，只要它控制的是"点击/触发才能看到的功能性内容"（子菜单展开、tooltip、悬浮操作按钮），都要过一遍这条规则；纯装饰性效果（按钮变色、阴影加深）不受影响。
- **处理方式二选一**：
  1. **改为点击/触摸触发**：菜单展开、子级导航等"操作类"交互，用 JS 判断触摸/点击切换类名，或用 `:focus-within`／checkbox hack 等纯 CSS 方案，替代 `:hover`。
  2. **改为常态显示**：说明文字、图片遮罩等"装饰性/说明类"交互，直接在窄屏下常显，不依赖任何触发动作。
- **实现约束**：hover 效果本身要写在 `@media (hover: hover) and (pointer: fine)`（或等效的 `min-width` 媒体查询，如 `min-width: 1024px`）内，不要写在无条件的基础样式规则里。否则触屏设备点击后可能触发"hover 态残留、点了却没有对应的取消触发方式"的卡死问题。
- **验收清单新增项**：凡是代码里出现 `:hover`，都要能回答"这条在 ≤1024px 下是否被上述媒体查询排除，或者有没有等效的点击态实现"，回答不出来视为未完成。

#### 1.3.5 验证方式
- 1.2 节"切一个手机尺寸看一眼"是最低门槛，做排版适配时不够。建议在 `768px` 和 `480px`（如项目用到超窄机型断点）两档核心宽度下各验证一次，重点检查四项：导航是否可操作、多列网格是否正确降级、依赖 hover 的功能是否有可用的替代触发方式、长文案/表格是否溢出容器。

## 2. 审美基线

### 2.1 可代码化的部分
- [ ] 颜色只使用 `主题配色清单.md` 里对应场景选定的那一套变量（`primary/secondary/accent/text/bg/border` 等命名），禁止在组件里手写规范外的十六进制色值
- [ ] 间距、圆角、字号如果项目没有自己的设计规范，默认遵循 4px 基准倍数（4/8/12/16/24/32...），不用随意取值（如 13px、17px）
- [ ] 同一项目内，同类元素（按钮高度、卡片圆角、标题字号）保持一致，不同页面之间不各写一套

### 2.2 无法代码化的部分（必须人工确认）
- [ ] **审美最终由人工目视复核确认，不能只靠代码规则判断"好看"**。AI 生成的初版布局/配色只是起点，验收前必须人工打开页面实际看一遍，判断留白是否合理、视觉层次是否清晰
- [ ] 涉及正式对外交付的项目（企业官网、门户），建议对照 `设计稿转代码流程.md` 里路线二/三的做法，有设计稿或规范做基准，不要纯靠 AI 直出后不做人工校对

### 2.3 交互状态基线（hover / active / focus，开工前必须定，不是做完再补）

**来源**：实际项目项目复盘。实际项目复盘表明，交互状态基线缺失会产生难以定位的视觉/交互缺陷，因此本节把状态设计前置。

**硬性规则**：

1. **hover 区域必须绑定在最外层容器上**，不能绑在内部子元素（图片、标题、内层 padding 盒）上。子元素绑定会导致鼠标在子元素边界移动时状态反复通断。
2. **禁止用会改变元素自身占位尺寸的属性做 hover 效果**。以下写法会造成"悬停 → 元素变大/位移 → 鼠标脱离原区域 → 状态取消 → 元素还原 → 鼠标又进入"的无限循环闪烁：
   - ❌ hover 时改 `width` / `height` / `padding` / `margin` / `font-size` / `gap`
   - ❌ hover 时新增 `border`（会把内容挤动，除非同时用 `outline` 或预留等宽透明边框）
   - ✅ 改用 `transform: scale()` / `translateY()`、`box-shadow`、`background-color`、`opacity`、`outline`——这些不参与布局计算，不会改变命中区域
   - ⚠️ **例外：作用在伪元素上的尺寸变化是安全的**。`.x:hover::before{height:5px}`、`.x:hover::after{width:100%}` 这类下划线/装饰条动效不参与宿主元素的命中区计算，不会造成通断循环，可以放心用。判据是"改的是不是宿主自己的盒模型"，不是"改的是不是尺寸属性"——源码实测中 87 处 hover 有 3 处改了尺寸，2 处在伪元素上（安全），只有 1 处 `gap` 改在元素自身（反模式）
3. **状态集必须成套定义**，不允许只写 hover 就交付。每个可交互元素都要明确：默认态 / hover / active（按下）/ focus-visible（键盘聚焦）/ disabled（若存在）。
4. **必须有过渡时长**：状态切换加 `transition`（推荐 `0.2s ease`），既避免视觉突变，也能吸收边界处的微小抖动。
5. **不可点击的元素不能长得像可点击**。序号、标签、装饰性徽标不要做成按钮外观（描边+圆角+填充色），否则用户会误以为可点。这条同样来自该项目的真实返工。
6. **键盘可达**：`:focus-visible` 必须有可见样式，不允许 `outline: none` 后不给替代样式（无障碍硬性要求）。
7. **触屏端 hover 失效的处理**见本文档第1.3节，不在本节重复。

**落地写法**：

```css
.card {
  transition: transform .2s ease, box-shadow .2s ease;
  border: 1px solid transparent; /* 预留边框位，hover 换色不挤动布局 */
}
.card:hover {
  transform: translateY(-4px);   /* 不改布局尺寸 */
  box-shadow: 0 8px 24px rgb(0 0 0 / 12%);
  border-color: var(--color-primary);
}
.card:active { transform: translateY(-1px); }
.card:focus-visible { outline: 2px solid var(--color-primary); outline-offset: 2px; }
```

**自查清单**：

- [ ] 每个可交互元素的 hover 监听是否挂在最外层容器
- [ ] hover 效果是否只用了不影响布局的属性（transform/shadow/color/opacity/outline）
- [ ] 是否在卡片边界、卡片之间的水槽处来回移动鼠标做过实测，确认无闪烁
- [ ] 状态集是否成套（default/hover/active/focus-visible/disabled）
- [ ] 是否存在"看起来像按钮但点了没反应"的元素
- [ ] 所有可交互元素键盘 Tab 聚焦时是否有可见样式
- [ ] hover 改尺寸时，确认改的是**伪元素**还是**宿主自己的盒模型**（前者安全，后者禁止）

> **该案例的成因已永久不可得**：源码到手后实测发现，"能力总览"模块在整站推翻重做时已被移除，闪烁代码随之消失（详见 `00-治理/待源码验证清单.md` SRC-001）。本节规则是通用预防措施，不依赖该项目的具体成因，独立成立；其中"伪元素例外"一条是源码实测后补充的，原规则只写"禁止改布局属性"过于宽泛，会误禁掉安全的下划线动效。

## 3. 浏览器兼容性

### 3.0 默认范围：只测 Chromium 系，不测 Firefox

**默认不做 Firefox 测试与兼容处理，除非 REQ Spec 里明确声明需要。**

判断依据：

- 国内桌面浏览器九成以上是 Chromium 内核。Chrome、Edge、百度、360、QQ、搜狗浏览器**内核相同**，测通 Chrome 即覆盖这一整片
- Firefox（Gecko 内核）国内份额约 1%，且 Firefox 与 Safari(WebKit) 是唯二需要单独验证的独立内核
- 完整过一遍 Firefox 的成本不是"装个浏览器十分钟"：按 26 页规模的站点计，人工逐页核对导航展开/tab 切换/灯箱/滚动动画/响应式两档需 2-3 小时，**且每次改版都要重复**，是持续成本而非一次性投入
- 展示型网站上 Firefox 渲染差异的后果通常是渐变没生效、动画不触发一类的观感问题，不会造成数据丢失或流程中断

低概率 × 低影响 × 持续成本，判定不值得做。

**什么情况下要重新纳入**：

- REQ Spec 的"目标浏览器"字段明确写了要 Firefox
- 交付对象使用信创/国产化终端（麒麟、统信 UOS 等），其默认浏览器多基于 Firefox。**注意这种情况该测的不是 Windows 版 Firefox，而是目标系统上的实际浏览器**，需客户方配合或搭虚拟机，不能在 Windows 上模拟
- 面向公众的国际化产品（海外 Firefox 份额高于国内）

### 3.1 代码层面（默认执行，与是否测 Firefox 无关）
- [ ] 项目配置 `browserslist`（如 `.browserslistrc` 或 `package.json` 里的 `browserslist` 字段），明确目标浏览器版本范围
- [ ] 使用 CSS 时避免依赖单一浏览器的实验性属性（如某些 `-webkit-` 专属写法），必要时用 `autoprefixer` 自动处理前缀，不手动只写一套前缀
- [ ] 使用 JS 新特性前，确认目标浏览器版本已支持（可参考 caniuse），不确定时降级写法或加 polyfill

这三条是**静态代码检查**，不需要打开浏览器、改一次永久生效、不随改版重复产生成本，所以即便不测 Firefox 也保留执行。滚动条样式是最典型的例子：`::-webkit-scrollbar` 在 Firefox 完全无效，Firefox 用 `scrollbar-width`/`scrollbar-color`，两套都写的成本极低。

### 3.2 实测要求
- [ ] **本地起服务后在 Chrome（或任一 Chromium 系浏览器）打开验证一次**
- [ ] 检查：页面布局是否一致、交互功能是否正常、控制台是否有报错
- [ ] 移动端视口（≤768px）至少验证一档，重点是导航菜单在触屏下能否展开——这类"功能性失效"优先级高于样式差异
- [ ] 如发现渲染差异，记录在该 REQ 的 `progress-log.md` 里，说明是否已修正或是可接受的差异
- [ ] **仅当 Spec 声明需要 Firefox 时**，才追加 Firefox 实测，并在 `progress-log.md` 里说明声明依据

## 4. 代码优化检查项（UI 开发场景专属，与 AGENTS.md 通用编码规范互补）
- [ ] 组件拆分合理，不存在一个文件堆多个页面职责
- [ ] 没有明显的重复样式代码块，可复用的间距/颜色/圆角已提取成变量或复用已有 token，不是每个组件各写一份
- [ ] 没有遗留调试用的临时代码（console.log、注释掉的旧代码块）
- [ ] 没有无用的空样式类、未使用的变量

本清单默认以"任务级引用"方式使用（每次 5 要素 Prompt 里手动引用）。如果项目使用某个 AI 编辑器，可以把经批准的核心规则适配为该编辑器的运行时规则文件；编辑器规则只是适配层，不成为新的事实源。

**启用步骤**：
1. 在该项目根目录建 `.cursor/rules/compatibility-adapt-rule.md`（不是本手册仓库里建，是具体业务项目里建）
2. `globs` 字段填该项目实际使用的文件后缀（如用 Vue 就填 `**/*.vue`，用 React 就填 `**/*.tsx`，本手册不预设具体框架）
3. Web 项目和小程序项目分开建两份规则文件，不要用同一份文件的 `globs` 同时匹配两端的文件后缀——两者适配逻辑不同（见第1节"小程序不适用本节"），混在一份规则里会导致规则互相打架

**Web 项目规则模板**（`globs` 需按项目实际技术栈填写）：
```yaml
---
description: 设备适配、审美、浏览器兼容、代码优化强制约束（Web端）
globs:
  - "{{项目组件文件后缀，如 **/*.vue 或 **/*.tsx}}"
  - "**/*.ts"
  - "**/*.js"
  - "**/*.css"
  - "**/*.scss"
---

### 编辑器运行时规则适配模板（Web/桌面端）

## 适配规则
1. 断点：移动端<768px，平板768-1024px，桌面>1024px；禁止固定 px 硬编码尺寸，弹性布局优先
2. 图片/媒体元素设置 max-width:100%，避免溢出

## 视觉审美规则
1. 颜色只用项目已选定的配色变量，不手写规范外色值；间距/圆角/字号统一，不随意取值
2. 涉及正式对外交付的项目需有设计稿或规范做基准，不能纯靠 AI 直出不做人工校对

## 浏览器兼容规则
1. 默认只保障 Chromium 系浏览器（Chrome/Edge/百度/360/QQ 等同内核，测一个即覆盖）表现一致，不做 Firefox 测试，除非 Spec 明确声明（依据见本文档第 3.0 节）；避免依赖单一浏览器的实验性属性
2. 需要兼容多浏览器时用 autoprefixer 统一处理前缀，不要只手写一个浏览器的私有前缀（那样反而会漏掉另一个浏览器，不是"移除前缀"而是"统一管理前缀"）
3. 出现兼容风险主动提示，说明降级方案

## 代码优化规则
1. 生成代码自动清理冗余代码、重复样式；组件合理拆分复用；保证可维护性
```

**小程序项目规则模板**（`globs` 需按项目实际使用的小程序/跨端框架填写，rpx 替代 px/flex 断点逻辑）：
```yaml
---
description: 设备适配、审美、代码优化强制约束（小程序端，不含浏览器兼容项）
globs:
  - "{{项目小程序组件文件后缀}}"
  - "**/*.js"
  - "**/*.ts"
---

### 编辑器运行时规则适配模板（小程序端）

## 适配规则
1. 统一使用 rpx 自适应单位，禁止 px 固定宽高，保障多机型适配一致
2. 禁止直接复用 Web 端布局逻辑（flex/grid 网页自适应规则不直接搬）

## 视觉审美规则
同 Web 项目规则模板第2节。

## 代码优化规则
同 Web 项目规则模板第4节。
```

> 具体项目决定使用何种 AI 编辑器后，应由该项目生成对应运行时适配规则，并引用本 Capability 的正式版本，不要在编辑器规则里重新维护一套不同内容。
