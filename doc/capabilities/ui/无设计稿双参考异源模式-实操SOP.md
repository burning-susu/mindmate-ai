# 无设计稿双参考异源模式-实操SOP
> 文档类型：Capability
> Capability ID：CAP-UI-REFERENCE-DUAL-SOURCE
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G5.5、G8、G9.1、G10、G11
> 激活条件：无正式设计稿，需要分别借鉴结构与视觉，且两个参考源的职责边界明确

## 0. Capability 元数据
- **目标**：在结构参考 A + 视觉参考 B 的模式下完成内容盘点、来源标注、视觉抽象、开发与验收，并防止多个参考源混杂导致视觉语言失控。
- **输入**：结构参考源、视觉参考源、原始内容素材、页面类型模板与项目合规边界。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
`设计稿转代码流程` Capability 第5.1节定义了"路线一：无设计稿AI直出流"的两种细分模式之一——双参考异源模式（内容结构参考A站、视觉参考B站），但只给了流程骨架，没有给出每一步具体怎么落地执行的操作细节。

本文档是这条路线的**实操SOP**，来源于多个实际 UI 项目复盘，将可复用的结构参考、内容审校、视觉抽象、素材处理和合规方法沉淀为操作清单。

**使用方式**：走双参考异源模式时，按下面七步顺序执行；每一步给出的"关键做法"是从真实项目验证过的经验，"踩坑提醒"是真实发生过的问题，照做能直接绕开。本文档不是唯一做法，团队/个人有更优流程时应当更新本文档，而不是弃用不管。

## 1. 第一步：结构模板生成

**输入**：内容结构参考网站的源码（保存到本地方便反复核对）

**关键做法**：
- 结构模板不是机械照抄参考网站的全部栏目，要排除不适用的部分（如公司规模小、暂无招聘需求，则排除"人才招聘"类栏目）
- 每类页面（产品页/方案页/其他页面类型）要先定好**固定字段模板**，明确"这类页面必须包含哪些板块"，不要等内容填充到一半才发现某类页面漏了字段——本次项目里"核心优势""应用案例"两个字段就是这样被漏掉，返工时才补齐
- 导航栏目的分类合并/拆分，要参照真实参考网站的实际结构验证，不要凭直觉判断（本次项目"产品中心"和"解决方案"该不该合并成一个一级栏目，反复调整了两轮才定型）

**踩坑提醒**：结构模板初版容易出现"参考网站的导航逻辑没吃透就直接套用"的问题，建议先完整通读一遍参考网站的所有页面，再动手画结构图，不要边看边画。

## 2. 第二步：内容盘点与来源标注

**输入**：原始内容素材（PPT、Word文档、访谈记录等）

**关键做法**（来自真实项目的踩坑总结，逐条验证过有效）：
1. **完整深度扫描素材目录**，包括所有子目录，不要只看第一层。命名暗示"处理产物"的目录（如带 `output`/`final` 字样），往往是已经加工过的最新最完整版本，反而容易被忽略
2. **同名/相似命名的素材文件要全部核对**，不能只挑一个就用——不同版本的同类素材（如"框架版""丰富版"两份产品手册）内容深度和覆盖范围可能差异很大
3. 素材是图片格式的PPT（文字检索工具搜不到内容）时，优先查找有没有配套的文本提取文件，没有就只能逐页读图，且要对读图判断的内容降低置信度，明确标注"基于截图判断，建议核实源文件"
4. **每一段填充内容末尾标注来源文件（含具体页码/位置）**。如果对原始素材做了合并、简化、改写，必须额外标注"处理方式"——没有来源标注的内容，下游环节没办法判断"是原文照抄"还是"二次加工"，默认会被当作照抄对待
5. 合并/简化要谨慎：能保留原始颗粒度就不要合并（如把8个独立行业分类合并成6类，会丢失每一项的独立信息量），不要凭空新增素材里没有的分类
6. 核对"内容是否已覆盖"时，要同时检查**呈现结构和信息密度**，不能只看关键词是否出现——原素材是分点/卡片结构，网站压缩成一句话塞进一个字段里，也应该算作"部分缺失"

**踩坑提醒**：跨对象关系类描述（如"产品A与产品B的联动机制"）容易被漏记单向——整理素材习惯逐个对象过一遍，遇到这类关系描述必须**双向记录**在两个对象的内容里，整理完成后要专门检查一遍关系维度的双向完整性。

## 3. 第三步：内容定版（多轮迭代）

**关键做法**：
- 多份素材信息冲突时（如公司地址、愿景使命等基础信息在不同文档里有不同版本），先判断权威性等级（官方定稿 vs 内部草稿），不要直接采信最新拿到的一份。判断依据：素材本身的语气线索（草稿语气通常带"待补充""建议资料"这类措辞）
- 维护一份"当前生效的基础信息记录"，每次新素材出现冲突信息时先比对这份记录，而不是每次重新讨论一遍
- 内容打磨过程会持续贯穿到接近定版，不是独立的一次性步骤

**归属/分类判断的核心原则**：给内容打标签、分类归属（如某段内容属于"核心优势"还是"核心功能"）时，判断依据应该是**对被分类对象本身定义的理解**，不是机械匹配素材里原始携带的分类标签。

真实案例：某产品页的几条功能点，最初按素材文档里现成的分类标签直接归类，结果被指出归属判断错了——功能点该归到A产品还是B产品，不能看素材把它写在哪个标签下，要看这条功能本身描述的能力边界，是不是真的属于该产品的定义范畴。改正后的判断方式是：先把该产品的核心定义想清楚，再逐条判断每个候选内容是否真的落在这个定义范围内，而不是"素材写了什么标签就归到哪"。

**踩坑提醒**：
1. 本步骤最容易出现"逐段核对来源时才发现大量内容在原始资料里找不到出处"的返工——第二步的来源标注做得越彻底，本步骤返工越少。
2. 归属判断错误往往不是一次性的，一旦某个分类标准建立错了，后续所有同类内容都会被错误归类，返工成本会随内容量线性增加——分类判断标准应该在处理第一批内容时就明确说清楚"依据什么标准判断"，而不是先归类、等被指出错了才回头解释标准是什么。

## 4. 第四步：视觉复刻

**核心方法论（本SOP最重要的一条经验）**：
> 复刻目标网站的视觉样式，**不是"边看边照抄某处具体细节"，而是先系统学习目标网站用了哪些页面组件和交互状态，抽象出一套可复用的通用模板，再对模板做内容和图标替换**。

真实项目里最初直接"照着复刻"，结果只有一个模块真正复刻成功，其余大部分模块视觉效果和目标网站相差很远，反复修改了很多轮才达到预期效果。事后复盘的结论是：没有先做"系统学习该网站的样式清单"这一步，导致每次改动都是局部对齐、没有统一的模板基准。

**执行步骤**：
1. 通读目标网站所有页面，列出它实际使用了哪些页面组件（导航悬浮卡片、卡片列表、轮播、悬浮态样式等）
2. 针对每个要复刻的组件，单独总结出"结构+悬浮态/交互态变化"的通用模板（不是复制这一处的代码，是提炼出"这个组件的样式规律是什么"）
3. 拿这份通用模板去套用到自己项目的对应组件上，只替换内容、图标、文字，样式结构保持一致
4. 排版/视觉约束要提前写清楚：是否沿用现有CSS体系文件路径、新增样式类的命名规则、已有交互功能（如点击放大、动画）改动前要先确认绑定的类名/脚本，避免改动时误伤

**踩坑提醒**：如果发现某个页面/组件复刻了很多轮还没达到预期效果，先停下来检查是不是跳过了"先学习该组件的样式规律"这一步，而不是继续在细节上反复微调。

**执行第1步前先查复用**：开始深度提取某个视觉参考站之前，先看项目视觉参考库索引（如有）索引表，如果该站已有现成的提取文档，直接复用，不要重新打开源码提炼一遍。提取完成后的产出文档，除了存进当前项目自己的文档目录，也应复制一份进项目视觉参考库并登记索引，供后续项目复用（做法见该目录README第1节）。

## 5. 第五步：开发实现与素材处理

**关键做法**：
- 图片替换采用**单图确认制**：生成一张、和用户确认一张，再生成下一张，不批量甩一堆图片让用户事后挑
- **原图必须保留**（单独建一个备份目录存放压缩/替换前的原始图片），压缩/替换后的图片单独存放，不覆盖原图
- 架构图/复杂图表类素材，要求"不能出现裁剪、文字必须清晰可读"，如果发现现有图片不满足这两条，直接重新生成，不要凑合使用模糊或裁切不全的版本

**踩坑提醒**：架构图之类的图片一旦在页面里显示裁剪或文字模糊，即使内容是对的，也应该被判定为"未通过"，不要因为内容大方向没错就忽略呈现细节。

## 6. 第六步：合规与真实性红线（贯穿全程，不是独立阶段）

**硬性要求**：
- 不得为了内容丰满而编造不存在的数据、案例、合作方、资质
- 敏感内容（内部测算数据、未经第三方认证的效益提升数字、涉及内部机密、未公开敏感信息或其他受限制披露的信息等）只做识别和标注"已排查"，不能直接照抄原话使用，必须与用户确认披露范围和表述方式
- 应用场景/案例的横向扩展（基于产品能力边界推演出的潜在场景）必须有能力边界依据支撑，AI只提供候选方向和思路，由用户筛选确认，不能自己直接定稿写进正式内容
- 缺失素材的板块（如客户logo、资质证书、团队照片）先搭建容器结构占位，不编造内容填充，同时列入待补清单

## 7. 第七步：收尾验收

定版前逐项确认（可直接作为该 REQ 的 `test-cases.md` 或 `acceptance.md` 补充检查项）：
- [ ] 每类页面的硬性板块字段是否齐全（对照第1步定的固定字段模板）
- [ ] 内容深度维度是否覆盖到位，且经过第二步的来源核对，没有编造内容
- [ ] 页面结构顺序体现的是"基于内容理解重新设计"，不是"在旧结构上堆叠新内容"
- [ ] 涉及敏感/合规内容的板块已标注风险并与用户确认披露范围
- [ ] 视觉复刻的组件样式是否经过"通用模板提炼"，还是仍停留在局部拼凑阶段
- [ ] 排版改动是否破坏了原有的交互功能（点击、动画等绑定的类名/脚本）
- [ ] 仍缺失的内容（如占位的客户logo、资质证书）已整理成清单交付用户，不是含糊过关
- [ ] 如果项目无法使用 Git（如企业账号限制、纯本地开发），是否已按里程碑节点做过整包快照备份（备份规则见 项目 Git 治理规则 补充章节）

## 8. 与手册其他文档的关系
- 本文档是`设计稿转代码流程` Capability路线一"双参考异源模式"的操作细化，选路线时先看那份文档的判断依据，走这条路线后再对照本文档执行
- **姊妹文档**：`无设计稿单参考同源模式-实操SOP.md`（路线一另一种细分模式）。两份 SOP 的第2、3、5、6、7 步完全共用**本文档**，那份只写单参考模式特有的第1、4步；因此本文档这五节的修改会同时影响两种模式，改动时需一并考虑
- **开工前置**：走本模式同样要完成`设计稿转代码流程` Capability第5.1.1节的四项硬性前置（参考站/复刻程度/配色/版心网格），并过第5.1.2节"先出结构再动手"关口——该关口已在多个实际项目中得到验证，两种模式均适用。版心网格见项目版心与网格基线，交互状态基线见项目响应式与兼容基线第2.3节
- 第2步的来源标注要求，呼应测试方法论 Capability里"缺陷判断要有依据、不能凭主观臆断"的原则
- 第6步合规红线，呼应安全测试 Capability里"不编造内容"的通用要求（虽然场景不同，但原则一致）
- 无法使用Git时的备份方案，见项目 Git 治理规则补充章节
