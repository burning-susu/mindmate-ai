# 设计稿转代码流程
> 文档类型：Capability
> Capability ID：CAP-UI-DESIGN-TO-CODE
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G5.5、G8、G9.1、G10、G11
> 激活条件：项目存在 Figma/蓝湖/其他结构化设计稿、参考站视觉基准，或需要建立从视觉资产到代码的可复用落地路线

## 0. Capability 元数据
- **目标**：选择设计资产到代码的实现路线，明确 MCP 能力边界，并建立结构确认、视觉基准、交互补齐和人工验收关口。
- **输入**：设计稿/参考站、UI Contract、Design Token、页面结构、项目技术栈与交付精度要求。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
## 0.1 定位
本文档是**可复用的选型参考资料**，回答"有/没有设计稿时，该走哪条路线把设计稿变成代码"。

本身不是某个具体项目的强制规则：
- 具体某个 REQ 选定了走哪条路线，写进该 REQ 的 REQ/Spec 技术栈章节
- 项目级第一次拍定走哪条路线（尤其涉及是否引入某个 UI 组件库、是否禁用某类组件），按 项目架构文档 的原则新增一份 项目 ADR 目录中的 ADR-XXX-xxx.md 记录决策依据
- 本文档不直接进入 `AGENTS.md`，避免把某个项目的具体技术栈选择写成全局通用规则

## 1. 核心结论
Figma-MCP / 蓝湖-MCP 思路可行，但不是一键生成可直接上线代码的万能方案，有明确的能力边界（见第3节）。

MCP（Model-Context-Protocol）本质是一条数据通道：让 Cursor / Windsurf / Claude Code 远程读取 Figma / 蓝湖里结构化的图层、尺寸、色值、切图资源，AI 拿到完整设计上下文再生成页面代码，替代手动打开设计工具复制 CSS、下载切图的重复劳动。

## 2. Figma-MCP 与蓝湖-MCP 的区别

### 2.1 Figma-MCP
官方原生开放 API，稳定性高，生成效果最成熟。
- 需要：生成一个 Figma personal access token（密钥）配置进 MCP 服务
- 能力：读取画板、Auto-Layout 布局、组件变体、Design Token 颜色字体，导出图片资源，转 Flex 布局代码

### 2.2 蓝湖-MCP
第三方开源项目，**非蓝湖官方出品**（需注意）。
- 需要：本地启动 MCP 服务，还要登录态 Cookie，有一定鉴权维护成本
- 能力：读取蓝湖标注数据、批量下载切图、解析页面，生成前端页面代码（具体输出何种框架/CSS方案代码，取决于所用工具的配置）
- 风险：官方接口更新时随时可能失效，官方不提供保障

> PSD、AI 源文件本身**不能直接丢给 MCP**，必须先上传蓝湖 / Figma，转换成在线可读取的设计稿链接。

## 3. MCP 能做到 / 做不到的事

### 3.1 能自动完成（省去手动切图）
- 自动读取宽高、边距、圆角、阴影、色值、字号行高，不用手动复制标注
- 自动下载所有图标、图片切图资源，导出 PNG/SVG，不用逐个右键导出
- AI 拿到完整数据，直接产出页面基础骨架代码（具体输出何种框架/组件库/CSS方案的代码，取决于项目自己的技术栈约定，需要在提示词或 Rules 里明确指定）
- 提取全局设计 Token，统一颜色、间距变量

### 3.2 做不到（最容易踩坑的点）
1. **不能自动识别业务交互逻辑**：MCP 只读静态视觉图层，点击弹窗、Tab 切换、表单校验、请求接口、状态切换都不会自动生成，必须手写
2. **还原度只有 70%~90%，不能直接上线**：复杂嵌套布局、重叠元素、列表循环、响应式断点，AI 常写出 `position: absolute` 这类硬编码布局，需要人工改成 flex/grid 并像素校对
3. **不会自动适配已有组件库**：AI 默认生成原生 HTML 标签，不会自动复用项目封装好的业务组件，需要在提示词、Rules 里强制约束
4. **蓝湖 MCP 维护成本高**：第三方开源工具，接口随官方更新可能失效

## 4. 完整工作流（旧手动流程 → MCP 自动化流程）

旧手动流程：PSD → 上传蓝湖 → 人工复制标注+下载切图 → 手动写页面代码

MCP 自动化新流程：
1. 设计师上传 UI 稿到 Figma / 蓝湖，完成标注
2. 在 Cursor/Windsurf 本地配置好 Figma-MCP / 蓝湖-MCP
3. 发送指令+粘贴设计稿链接给 AI，示例：
   ```
   读取这份设计稿，生成页面代码，使用flex布局；列表用v-for循环渲染；
   自动导出全部切图资源；严格复用项目组件库，禁止绝对定位。
   ```
4. AI 自动拉取图层数据，生成初始代码、下载切图
5. 人工校对、微调像素、补齐交互逻辑、对接后端接口、自测走查还原度

## 5. 三条开发路线选型

视觉实现可按交付精度和设计资产完整度选择三条路线。三条路线是可选策略，不是项目固定等级；具体路线由 Assessment 与 REQ 决定。总览见 项目自身的流程图或 capability 资产（如有）（路线一细分单参考同源/双参考异源两种模式，路线二、三各自独立）。

| 路线 | 设计稿要求 | 核心场景 | 预期还原精度 |
|---|---|---|---|
| 路线一：无设计稿 AI 直出流 | 无 | 练习、Demo、轻量化临时项目 | 常规视觉，非像素级 |
| 路线二：低保真 Figma 草图 + MCP + Rules | 低保真线框图 | 个人正规项目、长期迭代、可上线门户 | 结构精准，视觉规范统一 |
| 路线三：高保真 Figma 成品稿 + MCP + Rules | 专业高保真成品稿 | 企业商用、UI 交付、正式上线 | 以设计稿为基准进行高精度还原；最终精度以验收目标为准，不作绝对 100% 保证 |

### 5.1 路线一：无设计稿 AI 直出流
适合个人练习、Demo、简单页面、短期项目；不适合正式上线、长期迭代、多页面统一视觉的项目。

不启用任何 Figma-MCP、蓝湖-MCP，依靠竞品参考+AI 生成+人工微调完成开发。

#### 5.1.1 开工前四项硬性前置（缺任一项不得进入编码）

本路线没有设计稿，**验收基准只能靠前置约定建立**。以下四项必须全部有明确答案并写进该 REQ 的 `spec.md`，否则整个开发过程没有可判定的对错标准，返工没有终点：

| 前置项 | 落在哪 | 缺失的真实后果 |
|---|---|---|
| ① 参考站已选定（1个或2个，对应下方两种细分模式） | 该 REQ 的 `spec.md` | 只给"要XX风格"这类形容词，无法验收 |
| ② 复刻程度已约定（取向参考/结构复刻/视觉复刻三档） | `无设计稿单参考同源模式-实操SOP.md` 第1.1节 | 反复出现"你并没有按照它的网站来" |
| ③ 配色已拍定 | 项目 Design Token / 主题配置 | 开工后改配色，所有组件返工 |
| ④ 版心与网格已拍定 | 项目版心与网格基线 第4节声明模板 | 卡片忽大忽小、板块之间不对齐 |

交互状态基线（hover/active/focus）同属开工前须定的内容，见 项目响应式与兼容基线 第2.3节。

#### 5.1.2 硬性关口：先出结构，再动手

**AI 不允许在拿到参考站后直接产出成品页面。** 必须先交付并确认两样中间产物：

1. **AI 自述读到了什么**——分别读到哪些页面、各页的内容结构与标题、样式布局是否都能读取到
2. **页面结构模板**（Markdown，含板块序列与层级，暂不含正文）

确认无误后才进入内容填充与编码。该关口已在多个实际项目中被证明能降低返工，因此定为本 Capability 路线一的**硬性步骤**，两种细分模式均适用。

#### 5.1.3 标准流程

1. 收集参考素材：选定**唯一主参考站**（或结构/视觉各一个，共2个），梳理导航、模块、配色、排版规范
2. 完成 5.1.1 四项前置声明，写进 `spec.md`
3. **过 5.1.2 关口**：AI 先自述读到的内容，再产出页面结构模板，确认后才动手
4. 内容填充：按结构模板逐板块填充，标注来源，缺内容的板块列清单交用户，不编造、不删板块
5. AI 生成页面：以确认过的结构模板 + 定版内容 + 四项前置为输入生成
6. 人工视觉微调：统一间距、圆角、配色、排版（对照 ③④ 两项声明，不是凭感觉调）
7. 补齐交互联调：菜单高亮、轮播、列表、分页、hover 状态等（对照交互状态基线）

> 经验说明：路线一如果跳过“先出结构”而直接生成成品，容易出现大范围返工；因此本 Capability 将该步骤前置为硬性关口。

#### 5.1.4 两种细分模式

- **单参考同源模式**：结构、布局、视觉、配色全部对标同一个标杆站点，开发速度最快。实操见 `无设计稿单参考同源模式-实操SOP.md`
- **双参考异源模式**：结构参考A站（复用成熟栏目逻辑），视觉参考B站（筛选优质配色样式），解决单参考站样式老旧、结构不适配的问题。实操见 `无设计稿双参考异源模式-实操SOP.md`

**反模式（不推荐）：散点多参考**——同时并列3个以上参考站、按模块各学一个。各站的版心、字号阶梯、配色体系、圆角阴影语言互不相同，逐模块拼装必然导致整站视觉语言不统一，且失去唯一基准后验收退化为逐条主观意见。实际项目中曾出现同时并列多个参考站并最终需要大范围重做的情况。确需借鉴其他站的某个具体交互时，作为**单点增强项**登记在 `spec.md`，并声明"仅借鉴行为逻辑，视觉服从主参考站体系"。详见 `无设计稿单参考同源模式-实操SOP.md` 第5节。

优缺点：零设计成本、开发极速、样式自由度高；但无强制设计规范、依赖人工统一视觉、无法像素级还原。

### 5.2 路线二：低保真 Figma 草图 + MCP 自动化
适合正式上线门户、多页面体系、长期迭代、需要视觉统一和自动化规范开发的项目。

核心逻辑：不需要精美高保真UI，只画低保真线框图约束结构、尺寸、图层，视觉样式统一由配色规范+样式框架落地，兼顾规范性与效率。

标准流程：
1. 结构规划：参考竞品梳理全站栏目、模块、布局与风格基调
2. 绘制低保真草图：仅框选模块结构、尺寸、层级，不做精细视觉
3. MCP 自动化解析：自动读取宽高、间距、布局结构，自动导出图片资源
4. Rules 约束生成代码：禁止绝对定位、预留交互函数
5. 统一视觉风格：基于配色规范统一色调、圆角、排版
6. 交互与上线：对接接口、补齐业务交互、自测验收

优缺点：兼顾速度与工程规范、视觉统一、可长期迭代；需要绘制极简草图，存在极低设计成本。

### 5.3 路线三：高保真 Figma 成品稿 + MCP 企业级落地
仅适用于设计师交付完整高保真、组件规范齐全、Token 完整、状态齐全的成品设计稿，适合企业商用、多人协作、像素级交付项目。

核心优势：最适合高精度设计稿落地：可最大限度保持布局、Token、组件和状态一致；实际验收精度仍取决于设计稿质量、实现技术与终端适配。

标准流程：
1. 设计稿验收：确认组件、色值 Token、字体间距、交互状态、图层分组完整规范
2. MCP 全量解析：读取全局色值、圆角、阴影、字重、组件变体，自动高清切图
3. 严格 Rules 约束：禁止私自改样式、强制复用设计 Token、静态视觉 1:1 对标
4. AI 生成高保真代码：结构、样式、资源完全对标设计原稿
5. 人工像素校对：修正 AI 细微偏差
6. 业务落地上线：补齐交互、接口对接、兼容自测、验收上线

优缺点：工业级像素还原、规范统一，适配商用多人协作；依赖专业完整高保真设计稿，无法自主凭空产出。

### 5.4 默认测试力度参考（按路线，仅供参考，不强制）
选定路线一/二/三之后，对应 REQ 的 `spec.md` 第0节还要分别声明响应式清单、CSS技术方案、接口设计规范、自动化测试、性能测试、安全测试是否需要执行。每次都从零判断比较费时间，下表给出三条路线的**默认参考值**，实际填写时仍以该 REQ 的真实场景为准，不是照抄表格：

| 声明字段 | 路线一（练习/Demo） | 路线二（个人正规上线） | 路线三（企业交付） |
|---|---|---|---|
| 响应式与浏览器兼容清单 | 否 / 部分执行 | 是 | 是 |
| 自动化测试 | 仅人工测试 | 核心逻辑单元测试 + 关键路径E2E | 单元测试+接口自动化+E2E 全覆盖 |
| 性能测试 | 不适用 | 视是否对外交付决定 | 前端性能+接口压测 |
| 安全测试 | 不适用 | 视是否涉及登录/数据决定 | 前端+接口全覆盖 |

**判断依据**：路线一场景本身生命周期短、访问量小，参照 `自动化测试选型与规范.md` 第1.2节、`性能测试选型与规范.md` 第1.2节、`安全测试选型与规范.md` 第1.2节的"不必强求"清单，基本都能声明为最低档；路线三场景本身要求工业级交付质量，测试力度也应对应到最高档；路线二是最容易拿不准的中间态，建议先看该 REQ 具体涉不涉及登录/支付/个人信息（涉及则安全测试不能省），再看是不是长期迭代维护的核心模块（是则自动化测试值得投入），不要因为"路线二"这个标签本身就机械套用同一档。

## 6. 小程序场景的适配
上述三条路线的选型逻辑可以迁移到小程序，仅以下部分需要针对性改造：

| 项目 | Web 端 | 小程序端 |
|---|---|---|
| 技术栈 | 由项目自己的技术选型决定（本文档不绑定具体框架/CSS方案） | 需替换为小程序跨端框架（如项目选定的跨端方案） |
| 布局单位 | px / flex / grid | rpx 自适应单位 |
| 参考素材 | Web 网页竞品 | 同类型小程序竞品截图 |
| 组件规范 | Web DOM 标签 | 小程序原生 / 跨端框架组件 |
| 适配逻辑 | PC 优先 | 移动端手机优先 |

硬性禁忌：
- 禁止直接复用 Web 网页代码，所有布局、样式、DOM 标签必须重构适配小程序规范
- 禁止混用 Web 尺寸单位，全局统一使用 rpx
- 禁止 Web 专属交互（hover、滚动、弹窗逻辑），统一使用小程序原生 API
- 小程序优先使用原生/Uni 内置组件，禁止照搬 Web 端 UI 组件库样式

## 7. 仅有 PSD/AI 源文件时怎么办
结论：可行。流程为 **PSD/AI → 导入 Figma 标准化整理 → Figma 导出规范设计稿 → Figma-MCP 自动解析 → Rules 约束开发**，前端可自主完成切图、解析、开发全闭环，无需设计师二次交付 Figma 原稿。

不建议直接基于 PSD/AI 开发：原生文件图层混乱、无标准化 Design Token、样式参数零散，无法被 MCP 识别解析，代码规范性和像素精度无法保障。

标准落地流程：
1. **PSD/AI 源文件预处理**：清理无效图层、冗余素材，统一画板尺寸，修复样式丢失、图层错位问题
2. **Figma 标准化重构**：导入 Figma，统一图层命名、组件分组、层级规范，补齐圆角、阴影、字重、色值，生成可被 MCP 识别的标准稿件
3. **自主切图与样式提取**：轻量化开发可用切图标注工具批量导出；规范化开发直接在 Figma 内切片，交由 MCP 全自动解析
4. **匹配三大路线自动化开发**：按第5节的选型逻辑挑选路线一/二/三
5. **Rules 约束 + 落地**：统一代码写法、布局方式、样式规则，补齐交互、对接接口、完成自测上线

适用场景：存量老旧项目、仅有 PSD/AI 源文件的改版项目、无设计师对接的自主开发项目，Web 门户和小程序双端均适用。

## 8. 常见问答

**Q：MCP 能否读取组件库官网文档？**
普通 MCP 不支持，搭配 Context7 MCP 可实时读取最新官方 API。

**Q：前台门户能否用某个现成 UI 组件库？**
这是具体项目的技术栈约束，不是通用规则，取决于该项目是否要求手写自由样式、组件库视觉风格是否符合项目定位。若某项目决定禁用某类组件库，应写进该项目自己的 AGENTS.md 或对应 REQ 的 Spec 技术栈章节，不写在本文档或全局 `AGENTS.md` 里。
