# 无设计稿单参考同源模式-实操SOP
> 文档类型：Capability
> Capability ID：CAP-UI-REFERENCE-SINGLE-SOURCE
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G5.5、G8、G9.1、G10、G11
> 激活条件：无正式设计稿、存在一个可同时承担结构与视觉基准的主参考站，并选择路线一

## 0. Capability 元数据
- **目标**：在单一主参考站模式下完成基准确定、结构确认、内容填充、视觉复刻、交互补齐和收尾验收，避免 AI 直接从模糊审美描述开始编码。
- **输入**：主参考站、内容素材、视觉目标、复刻程度、Design Token 与 REQ 范围。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。

`设计稿转代码流程` Capability 第5.1节把"路线一：无设计稿AI直出流"分成两种细分模式，双参考异源模式已有 `无设计稿双参考异源模式-实操SOP.md`，本文档补齐另一半：**单参考同源模式**——结构、布局、视觉、配色全部对标**同一个**标杆站点。

**经验来源**：多个实际项目的 UI 开发复盘表明，在无设计稿情况下，先建立唯一视觉基准、再进行结构与内容确认，可以显著降低返工。本文保留这些可复用做法，不将具体项目名称、站点名称或内部 Prompt 编号视为通用规则。

**与双参考异源 SOP 的关系**：第2、3、5、6、7 步（内容盘点、内容定版、开发实现、合规红线、收尾验收）两种模式**完全共用**，本文档不重复抄写，直接指向那份文档。本文档只写单参考同源模式**特有**的第1、4步，以及一条独有的前置关口。

**什么时候选这条模式**：只有一个可对标站点、且该站点的结构与视觉都适用；追求速度；内容源已经齐备（PPT/PDF 等）。若参考站结构可用但视觉老旧，改走双参考异源模式。

## 1. 前置关口：先定基准，再动手（硬性，缺一不可）

本模式最大的风险是"**参考站没选就开工**"。实际项目复盘中，缺少参考基准时通常容易出现多轮返工。

动手写第一行代码之前，下面四项必须全部有明确答案并写进该 REQ 的 `spec.md`：

| 前置项 | 判据 | 缺失后果（真实发生） |
|---|---|---|
| ① 参考站已选定且唯一 | 能说出站点 URL，且确认其结构与视觉都适用 | 仅给“科技感”“简约”“高端”等形容词无法验收，返工无终点 |
| ② 复刻程度已约定 | 见第1.1节三档 | 双方对"参考"的理解不一致，反复出现"你并没有按照它的网站来" |
| ③ 配色已拍定 | 按 项目 Design Token / 主题配置 选定一套，或从参考站提取 | "主题色彩过于暗淡"——开工后再改配色，所有组件都要返工 |
| ④ 版心与网格已拍定 | 按 项目版心与网格基线 第4节填声明 | "同样一行3个卡片，一会大一会小，大标题也没有对齐" |

③④ 两项是通用前置基线，与本模式无关也必须做；本模式特有的是 ①②。

### 1.1 "复刻到什么程度"必须约定成三档之一

实际项目复盘中，缺少参考基准时通常容易出现多轮返工。根因不是 AI 不听话，而是**"参考"这个词本身没有精度**。开工前必须约定属于下面哪一档：

| 档位 | 含义 | 验收标准 |
|---|---|---|
| A 取向参考 | 只借鉴气质方向（配色明暗、疏密节奏） | 无法逐项验收，只能人工目视认可。**不适合正式交付项目** |
| B 结构复刻 | 板块顺序、栏目层级、每屏承载什么内容与参考站一致，视觉自行设计 | 逐板块对照参考站清单打勾 |
| C 视觉复刻 | 板块序列 + 字号/颜色/间距/交互态与参考站一致，**只替换文字、图标、图片** | 逐组件对照参考站实测数值 |

**默认推荐 C**，因为它是唯一能被逐项验收的档位。实际项目复盘中，缺少参考基准时通常容易出现多轮返工。

选定 C 档时，必须同时明确**替换清单**：哪些是照搬（布局/字号/色值/交互态），哪些是替换（文案/图标/图片/案例数据）。不写清单，就会反复出现"这个也该按它的来"。

### 1.2 硬性关口：先出结构，再动手（双项目验证）

**AI 不允许在拿到参考站后直接产出成品页面。必须先交两样中间产物，经确认后才进入编码。**

| 顺序 | 中间产物 | 对应指令（实际项目复盘中，缺少参考基准时通常容易出现多轮返工。两个独立项目在同一步骤上收敛，构成对该关口的强验证，因此在 `设计稿转代码流程` Capability 第5.1节被定为**路线一硬性步骤**，两种细分模式都适用。

"AI 自述读到了什么"这一步单参考模式尤其不能省：参考站的结构与视觉都由它一家承担，AI 若读漏了页面或读不到样式，后续所有产出都建立在残缺认知上，而这件事在成品出来之前是看不出来的。

## 2. 第二步：内容盘点与来源标注

**与双参考异源模式完全一致**，直接执行 `无设计稿双参考异源模式-实操SOP.md` 第2节，不在此重复。

本模式的补充点：结构模板来自参考站，而内容来自自己的素材，两者的板块必然对不齐。填充时按"结构模板逐板块问'我的素材里有什么能填进来'"的方向做，**缺内容的板块单独列成清单交给用户，不要自己编造，也不要悄悄删掉该板块**。实际项目复盘中，缺少参考基准时通常容易出现多轮返工。

## 3. 第三步：内容定版（多轮迭代）

**与双参考异源模式完全一致**，见 `无设计稿双参考异源模式-实操SOP.md` 第3节。

本模式的补充点：**模板填充必须全量覆盖，不能只填示范项**。实际项目复盘中，缺少参考基准时通常容易出现多轮返工。**"同结构套用"不是交付物，是待办事项。**

## 4. 第四步：视觉复刻

方法论与 `无设计稿双参考异源模式-实操SOP.md` 第4节**完全一致**（先系统学习参考站的组件与交互态，抽象出通用模板，再替换内容——不要边看边照抄局部细节），执行前同样先查 `视觉参考库/README.md` 索引表避免重复提取。

本模式**特有**的三点：

1. **同源的优势要用足**：结构与视觉出自同一个站，因此"板块序列"与"该板块长什么样"是配套的，应当**成对提取**（如"首屏=大屏轮播+透明顶导"），而不是先定结构再单独找视觉。分开做会丢掉配套关系，等于把同源模式退化成异源模式。
2. **首屏与顶部导航要单独立项确认**。实际项目复盘中，缺少参考基准时通常容易出现多轮返工。这两处是用户第一眼看到的地方，也是参考站特征最集中的地方，建议第一轮就单独拿出来对齐，不要混在整站里一起做。
3. **禁止散点多参考**。见第5节。

## 5. 反模式警示：散点多参考（不要这样做）

实际项目复盘中，缺少参考基准时通常容易出现多轮返工。

**这不是第三种正规模式，是反模式，不推荐。** 原因：

- 每个站的版心、字号阶梯、配色体系、圆角与阴影语言都不同，逐模块拼装的结果是整站视觉语言不统一，而不统一本身又会触发新一轮返工
- 没有唯一基准，"做得对不对"无法判定，验收退化成逐条主观意见
- 该阶段结束后项目并未收敛，反而紧接着发生了整站推翻重做

**正确做法**：选定唯一主参考站。确有某个具体交互（如大屏切换、卡牌轮播）想借鉴其他站，把它作为**单点增强项**显式登记在 `spec.md`，并说明"仅借鉴该交互的行为逻辑，视觉仍服从主参考站的字号/配色/间距体系"，不要让它带进自己的视觉语言。

## 6. 第五至七步：开发实现、合规红线、收尾验收

三步与双参考异源模式**完全一致**，直接执行 `无设计稿双参考异源模式-实操SOP.md` 第5、6、7节。

本模式在收尾验收时**额外**追加以下检查项：

- [ ] 复刻档位（A/B/C）是否在 `spec.md` 声明，且验收按该档位的标准执行
- [ ] C 档时，替换清单里"照搬项"是否真的照搬（字号/色值/间距/交互态逐项比对参考站）
- [ ] 首屏与顶部导航是否单独对齐过参考站，而不是混在整站里粗过一遍
- [ ] 结构模板的所有板块是否**全量**填充完成，没有留"其余同结构套用"的示范式产出
- [ ] 缺内容的板块是否已列成清单交付用户，且没有被编造内容或悄悄删除
- [ ] 是否存在从其他站带进来的、与主参考站视觉语言冲突的模块
- [ ] 版心/网格声明与交互状态基线是否已按 项目版心与网格基线 第6节、项目响应式与兼容基线 第2.3节自查通过
