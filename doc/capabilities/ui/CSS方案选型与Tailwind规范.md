# CSS方案选型与Tailwind规范
> 文档类型：Capability
> Capability ID：CAP-UI-CSS-TAILWIND
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G5.5、G8、G9、G9.1、G10、G11
> 激活条件：项目需要 Utility-first CSS，且 Assessment 判断其收益高于引入/迁移成本，或项目已明确选用 Tailwind

## 0. Capability 元数据
- **目标**：帮助项目判断是否采用 Tailwind，并在采用后提供 Token、class、任意值、组件库共存与验收规范。
- **输入**：UI 约束、现有 CSS 体系、组件库、设计 Token、响应式要求与维护方式。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
## 0.1 定位
本文档回答两个问题：
1. 要不要用 Tailwind？给出优劣势和适用场景，帮助按需求描述判断
2. 选了 Tailwind 之后怎么写代码？给出具体规范

**本身不是强制规则**：是否使用 Tailwind，由项目 Assessment 与 REQ/Spec 的 CSS 技术方案声明决定。仅当项目选择 Tailwind 或 Tailwind 混合模式时，才启用第4～7节。

若项目第一次拍定要不要引入 Tailwind（尤其是要不要和现有组件库共存），按项目治理规则记录技术选型 ADR（如该选型达到架构决策等级），不要只在 Spec 里写一句话就跳过。

## 1. Tailwind 优势
- 消除命名焦虑：不用绞尽脑汁给每个元素起 `panel-header-left-btn` 这类自定义类名，减少大量无意义的 CSS 命名工作
- 开发速度快：样式直接写在 class 里，不用来回切换 html/css 文件，减少上下文切换成本，产品临时要求微调间距/颜色/圆角时效率很高
- 天然契合 Design Token 体系：颜色/间距/断点都能在配置文件里统一定义，和 项目已批准的 Design Token / 主题配置 里的变量可以直接对应，约束团队不能随意写 `margin:17px`、`color:#ff2233` 这类不规范样式
- 按需生成，未用到的 class 会被自动清除，生产环境打包体积可控
- 响应式前缀（`sm:/md:/lg:`）内置，可以直接对齐项目定义的断点体系，不用手写媒体查询
- 团队协作时样式命名统一，不会出现十个人写十种 class 命名风格的问题
- 适合碎片化 UI、零散组件：侧边栏、弹窗、工具栏、图例、卡片这类小控件开发速度提升明显

## 2. Tailwind 劣势
- class 字符串一长就难读，复杂组件容易变成"一行代码看不清结构"
- 不熟悉 utility-first 思路的人容易滥用，写成内联样式的等价物，失去复用性；新人也有一定学习成本，需要记忆大量工具类名称
- 复杂动画、特殊渐变、精细的伪元素效果，还是要退回写自定义 CSS，不是万能的；一个样式包含大量属性且被十几个页面重复使用时，全部写工具类会造成大量重复代码
- 不配合组件化拆分时，容易出现同一段 class 字符串到处复制粘贴，反而违反 DRY 原则
- 和 Element-Plus / Ant Design 这类自带完整视觉体系的组件库混用，容易样式冲突或产生"两套视觉控制权互相打架"的问题
- 难以交给非开发人员维护：运营、美工看不懂一长串工具类，后期想手动改页面样式几乎不可能
- **只能控制 DOM 层，无法控制非 DOM 渲染层**：Canvas、WebGL、地图/三维引擎（如 Cesium、Three.js）里的实体、材质、颜色等渲染样式完全不受 Tailwind 管理，这部分必须用对应渲染引擎自己的 API 设置。若项目包含此类特殊渲染层，边界划分应写进该项目自己的补充规则（不在本通用文档里展开具体某个引擎的处理方式）
- 老项目接入改造成本高：原有项目已用 SCSS、CSS-Module、BEM 等规范时，引入 Tailwind 会出现两套样式体系，容易样式冲突

## 3. 适用场景判断（决策维度，不建立独立评分器）

### 3.1 倾向采用 Tailwind 的信号
1. 项目是现代前端工程（有现成的构建工具链），非传统静态页面、非老旧无构建流程的项目
2. UI 定制化程度高，页面组件碎片化，大量弹窗、卡片、侧边栏、控制面板类元素
3. 需求迭代频繁，UI 样式经常微调（间距、颜色、布局反复修改）
4. 需要建立统一内部设计规范，约束颜色、间距、尺寸
5. 项目组件复用度中等偏低，一次性页面、大屏可视化页面居多
6. 团队成员愿意统一学习 Tailwind，无强烈抵触 utility-first 开发模式

### 3.2 谨慎采用或不采用 Tailwind 的信号
1. 页面极其简单：仅少量文字图片，DOM 元素少、样式几乎不会改动
2. 大量超长、复杂样式，且在多处全局复用（复杂动画、复杂关键帧、大型布局）
3. 老项目已有成熟的 SCSS / BEM / CSS-Module 样式体系
4. 后期需要非开发人员（运营、美工）手动修改页面样式
5. 团队内部多数成员拒绝 utility-first 模式，不愿意学习工具类语法
6. 小程序项目：Tailwind 本身是 Web CSS 方案，不直接支持 rpx 单位，需要额外适配层，要先确认对应工具是否成熟、是否有维护成本

### 3.3 折中方案：混合模式（最常用，Tailwind + 少量自定义 CSS）
适合：核心页面级 UI（弹窗、侧边栏、卡片、控制面板）用 Tailwind，复杂动画、特殊渐变、非 DOM 渲染层容器（若有）单独写 CSS 或用对应引擎自己的 API。

这是实践中最常见的选择，不是"二选一"，需要在 Spec 里写清楚具体分工边界（哪些模块用 Tailwind、哪些单独写 CSS），而不是笼统写"混合使用"。

## 4. 选定 Tailwind 后的规范使用（选中后强制执行）

### 4.1 class 书写顺序
不要求手动记忆排序规则，安装 `prettier-plugin-tailwindcss` 后由工具自动排序，保证团队协作时风格统一。若需要人工核对，推荐顺序：
1. 布局定位：`relative absolute fixed top-0 left-0`
2. 盒模型：`w-full h-auto p-4 m-2 gap-2`
3. Flex / Grid：`flex items-center justify-between`
4. 背景颜色：`bg-white`
5. 边框、阴影：`border border-gray-200 shadow-md rounded-lg`
6. 文字样式：`text-sm text-gray-600 font-medium`
7. 交互状态：`hover:bg-gray-100 active:bg-gray-200`
8. 媒体查询、响应式前缀：`md:w-1/2 sm:hidden`

### 4.2 颜色只能引用项目 Token，禁止手写色值
- 颜色值统一来自 项目已批准的 Design Token / 主题配置 里项目已选定的那一套变量，接入方式：把清单第8节的 CSS 自定义属性值填入 `tailwind.config` 的 `theme.colors` 字段
- 禁止在组件里写 `bg-[#165DFF]` 这种任意值色值，即使颜色和 token 里的值一样，也要用 token 名称引用（如 `bg-primary`），保证后续统一改色时只需改一处配置

### 4.3 禁止滥用任意值语法
- 禁止 `w-[137px]`、`text-[15px]` 这类任意值写法，优先用 Tailwind 配置里已有的间距/尺寸阶梯（如 `w-32`、`text-base`）
- 确实需要设计稿里的精确数值且找不到对应阶梯时，先检查是否该在 `tailwind.config` 的 `theme.extend.spacing` 里补一个新阶梯值，而不是就地写任意值——任意值写多了会导致设计token失去统一入口

### 4.4 断点必须自定义覆盖，不能用默认值
Tailwind 断点必须以项目已批准的响应式断点为准。不要因为 Tailwind 默认值存在就直接采用；若项目自己的断点不同，应在 `tailwind.config` 中显式配置并在 Spec 中记录：
```js
// tailwind.config.js
module.exports = {
  theme: {
    screens: {
      'md': '768px',   // 平板起点，对齐响应式清单
      'lg': '1024px',  // 桌面起点，对齐响应式清单
    },
  },
}
```

### 4.5 重复 class 组合要提取
同一段 class 组合在 3 处以上重复出现时，视为需要重构的信号，禁止继续复制粘贴长串 class。两种提取方式：

**方式A：`@apply` 提取到全局 CSS**（适合纯 DOM 样式、无需独立组件的场景）
```css
/* src/index.css */
@layer components {
  .panel-card {
    @apply flex items-center p-4 bg-white rounded-lg shadow-md border border-gray-100;
  }
}
```
页面直接使用：
```html
<div class="panel-card">内容</div>
```

**方式B：封装成组件**（优先推荐，适合长期维护的业务组件）
业务组件优先封装成组件而不是单纯 `@apply`；若组件已存在但仍在别处复制长串 class，应改为复用该组件。

### 4.6 与现有组件库共存时的规则
若项目同时使用某个 UI 组件库（如后台管理系统里后台用组件库、前台门户用 Tailwind），需要在该项目的 ADR 里明确边界：哪些区域用组件库、哪些区域用 Tailwind 手写，不要让两者在同一个组件内部混用导致样式优先级冲突。

## 5. 代码审查红线（禁止行为）
以下行为在评审时应直接拒绝，不是"建议修改"：
1. 禁止无限制堆砌超长 class、不做任何提取（对照第4.5节的"3处以上重复"标准）
2. 禁止大量使用任意值语法（`bg-[#xxxxxx]`）绕过 `tailwind.config` 的主题配置（对照第4.3节）
3. 禁止 Tailwind 和大量内联样式（如 `style="width:200px"`）混合滥用——要么用 Tailwind 的工具类，要么走自定义 CSS，不要两套并存在同一个元素上
4. 禁止用 `!important` 强行覆盖 Tailwind 默认样式——出现这种情况通常说明样式优先级设计有问题，应回头检查是否与组件库样式冲突（对照第4.6节），而不是用 `!important` 掩盖

## 6. 验收关联
若某 REQ 声明"CSS技术方案：Tailwind"或"混合模式"，验收时额外检查：
- [ ] 未出现任意值语法（`w-[137px]` 类写法），除非已在 `tailwind.config` 里补了对应阶梯
- [ ] 颜色均通过 token 引用，未见硬编码色值
- [ ] `theme.screens` 已按响应式清单的断点覆盖默认值
- [ ] 重复 3 次以上的 class 组合已提取为组件或 `@apply` 语义化类
- [ ] 未出现第5节列出的4条审查红线行为
- [ ] 若声明"混合模式"：已按 Spec 里写明的分工边界核对，Tailwind 和自定义 CSS 的职责范围没有混淆

## 7. 落地执行流程（选型-编码闭环）
1. **选型评估阶段**：根据第3节决策维度，输出选型结论（用第3.4节模板），写进 REQ 的 `spec.md`
2. **初始化阶段**：配置 `tailwind.config.js`，接入项目已选定的配色变量（对照第4.2节）、断点（对照第4.4节）
3. **编码阶段**：按第4节规范开发
4. **代码评审阶段**：对照第5节红线检查，发现问题打回修改，不是"建议"
5. **迭代维护阶段**：重复出现的样式及时按第4.5节提取，不要等到验收前才集中处理
