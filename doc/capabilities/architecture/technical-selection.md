# Capability：Technical Selection / 技术架构选型分析

> 建议位置：`doc/capabilities/architecture/technical-selection.md`  
> Capability ID：`CAP-ARCH-TECH-SELECTION`  
> 定位：提供“如何做技术选型”的专业方法；不规定任何项目必须采用 Vue、Spring Boot、MySQL、COS 或其它固定技术。  
> 配套模板：`doc/templates/TECH-DECISION-TEMPLATE.md`

## 1. 能力目标

当项目需要确定技术栈、架构组件、外部服务、工程工具或部署方式时，本 Capability 负责把模糊的“给我一套技术栈”转换为可审计的技术决策过程：

```text
项目事实/约束
→ 决策领域识别
→ 候选方案发现
→ 单项分析
→ 层次与兼容性分析
→ 组合方案构建
→ 方案比较
→ 当前推荐
→ 用户确认/ADR（如需要）
→ 技术栈总览
```

它解决的核心问题不是“AI 知道多少技术名”，而是防止：
- 只给一个默认栈，没有真实候选；
- 把 OpenAPI、springdoc、Swagger UI 这类不同层次的东西错误做成单选；
- 漏掉 `A+B` 或主方案+辅助方案；
- 先写总技术栈，再倒推理由；
- 因需求尚未 100% 收敛而完全无法提前产出架构 Draft；
- 把 Draft 推荐误写成项目已批准决定。

## 2. 触发条件

建议在以下场景激活：
- G6 总体技术架构；
- 新项目技术栈选择；
- 旧项目重构/迁移；
- 引入新的数据库、缓存、对象存储、消息系统、认证方案、API 技术或部署平台；
- 技术成本、性能、安全、维护或供应商约束发生变化；
- 架构文档需要提前产出，但仍存在部分业务/技术 TBD。

不需要因为修改一个普通工具版本、格式化规则或完全可逆的局部实现细节就强制启用完整分析。

## 3. 前置输入

最低需要读取：
1. 当前项目需求/PRD/来源状态；
2. PROJECT_PROFILE / ASSESSMENT（如有）；
3. 当前代码、配置、运行环境（已有项目）；
4. 已确认的 DEC / ADR / 外部平台约束；
5. 团队、交期、预算、合规、部署环境等现实约束；
6. 与当前决策有关的其它 TECH_DECISION。

输入可以不完整，但必须分类：
- `CONFIRMED`
- `PROVISIONAL / ASSUMPTION`
- `INFERRED`
- `TBD`

不得用 AI 一般经验把 TBD 静默补成项目事实。

## 4. 受控提前产出

### 4.1 允许提前 Draft 的条件

只要满足以下条件，就可以生成技术架构/技术选型 Draft，不必等待所有需求决策完全结束：
- 项目目标和主要使用场景已经足以判断大方向；
- 已知范围足以识别主要技术领域；
- 尚未确认内容可以明确列出，并能判断它影响哪些技术决策；
- 不存在“无论选哪种业务规则都会导致完全不同系统形态”且未被识别的重大冲突；
- 当前输出目的只是分析、沟通或评审，不冒充 Approved/Baselined。

### 4.2 提前 Draft 必须包含

- 当前输入成熟度；
- Assumption / TBD；
- TECH_DECISION 清单；
- Proposed 与 Confirmed 的显式区分；
- Blocking / Deferable；
- 最晚确认点；
- 上游变化后的 Revalidation 规则。

### 4.3 禁止事项

提前 Draft 不允许：
- 提高 PROJECT_STAGE；
- 把推荐方案改成已批准决定；
- 因“公司要文档”而虚构业务数据、并发、成本或平台约束；
- 绕过代码开发、数据库修改、发布等正式门禁；
- 用 Draft 反向覆盖 Approved PRD/ADR。

## 5. 决策领域识别

先识别“需要做什么决定”，再识别技术名。常见领域包括但不限于：
- 客户端/跨端框架；
- Web 前端框架和工程化；
- 后端语言/框架与应用形态；
- 数据库；
- ORM/数据访问；
- Schema migration；
- 文件/对象存储；
- API 风格；
- API 契约标准；
- 契约生成/展示/调试工具；
- 认证、Token 和会话；
- 权限模型；
- 缓存、分布式锁；
- 消息/异步任务；
- 搜索；
- 定时任务；
- 网关；
- 部署和容器；
- 可观测性；
- 测试技术。

不要机械把每项都列为决策。只有对当前项目有实际选择空间或明显影响时才建立 TECH_DECISION。

## 6. TECH_DECISION 粒度

一个好的技术决策单元必须：
- 能用一个明确问题描述；
- 候选处于可比较或可组合的合理层次；
- 其结论发生变化时，影响范围可识别；
- 不把多个无关问题塞成“选一套技术栈”一次性决定。

错误粒度：
> “技术栈选 Vue + Spring + MySQL + Redis + COS 吗？”

推荐拆分：
> “小程序端使用原生、UniApp 还是 Taro？”  
> “业务主数据采用哪类关系数据库？”  
> “图片文件使用公有云对象存储、自建 S3 兼容存储还是其它方式？”  
> “API 采用什么风格，契约如何生成和展示？”

## 7. 候选发现

### 7.1 候选数量不固定

规则：
- 有几个 materially viable candidates 就列几个；
- 不为了模板制造 3 个选项；
- 不因 AI 熟悉某个技术就只列 1 个；
- 如果只有一个可行方案，说明其它常见方案的排除理由。

### 7.2 候选来源

优先来自：
1. 项目已有技术/平台约束；
2. 公司已有基础设施；
3. 用户明确候选；
4. 当前生态中与项目约束匹配的成熟方案；
5. 迁移兼容要求。

候选版本、许可证、平台支持等会随时间变化；需要具体当前事实时应查正式文档或可靠来源，而不是凭记忆断言。

## 8. 层次识别与组合方案

### 8.1 先判断“是否真的是竞争关系”

例如 API 领域可能同时存在：
- API 风格：REST；
- 契约标准：OpenAPI；
- Java 契约生成：springdoc-openapi；
- 在线展示：Swagger UI / Knife4j；
- 团队协作/调试：Apifox 等。

这些不一定互斥。错误做法是让用户在“OpenAPI / Swagger UI / springdoc / Apifox”里四选一。

### 8.2 组合方案构建

对互补组件建立组合：

```text
COMBO-1 = 核心技术 + 适配/实现 + 可视化/协作工具
```

每个组合必须说明：
- 每个组件负责什么；
- 为什么不能只用其中一个；
- 是否有能力重复；
- 版本/协议/部署是否兼容；
- 引入额外组件的收益是否大于复杂度。

### 8.3 组合方案也参与比较

最终推荐可以是：
- 单一方案 A；
- 组合 A+B；
- A 为主、B 只在特定场景启用；
- 分层方案（例如不同端采用不同框架）；
- 当前阶段 A，达到触发条件后迁移到 B。

## 9. 评价维度

不是所有决策都用同一套权重。至少从以下维度选相关项：
- 业务适配；
- 平台限制；
- 数据归属；
- 安全/隐私/合规；
- 性能和容量；
- 一致性和失败恢复；
- 可用性；
- 成本；
- 开发复杂度；
- 运维复杂度；
- 团队熟悉度；
- 交付周期；
- 测试；
- 可观测性；
- 迁移/回滚；
- 供应商锁定；
- 生态成熟度和生命周期；
- 与其它 TECH_DECISION 的兼容性。

禁止用无依据的统一打分制造伪精度。能量化的用真实指标；不能量化的写条件和取舍。

## 10. 推荐规则

推荐必须同时包含：
1. 推荐内容；
2. 推荐成立的前提；
3. 核心理由；
4. 不采用其它仍可行方案的原因；
5. 组合中各组件职责；
6. 主要代价和风险；
7. 重新评估触发条件。

Draft 推荐一律是 `PROPOSED`。如果用户尚未确认，不得因为“推荐很明显”就写成 `CONFIRMED`。

## 11. 阻断等级与最晚确认点

- `BLOCKING`：不确认会让下游无法可靠设计/实施，必须在对应阶段出口前解决。
- `DEFERABLE`：可以暂缓，但要写明最晚确认点；到点仍未确认就升级为阻断。
- `INFORMATIONAL`：记录背景，不控制阶段。

是否 Blocking 由依赖关系决定，不是“所有技术选择都默认高影响”。

## 12. 与 IDP / ADR 的关系

### 12.1 TECH_DECISION 与 IDP

- 高影响：按 `INFORMED_DECISION_PROTOCOL` 每轮 1 项完成解释、初选、影响复述、二次确认和应用。
- 低影响：可按治理允许一次处理最多 2 项，但仍需独立 ID。
- 仅生成 Draft 推荐，不需要把每项都提前确认；确认门禁发生在“要把 Proposed 升级成项目正式决定”时。

### 12.2 TECH_DECISION 与 ADR

- TECH_DECISION：候选和组合分析过程。
- ADR：已确认的长期架构决定。
- 不是所有低影响 TECH_DECISION 都必须创建 ADR。
- 一旦创建 ADR，技术栈总览应引用 ADR/TECH_DEC，而不是维护第二套独立事实。

## 13. 技术栈总览生成规则

技术栈总览是**输出汇总，不是输入默认值**。

生成前检查：
- 每个重要条目是否有 TECH_DECISION；
- 当前是 Proposed 还是 Confirmed；
- 是否遗漏互补组合中的组件职责；
- 是否有两个 TECH_DEC 结论互相冲突；
- 是否把工具层、协议层、框架层混成一个单选；
- 是否把 TBD 静默写成确定技术名。

## 14. 上游变化与 Revalidation

需求、规模、交期、成本、平台、团队或其它 TECH_DEC 变化时：

```text
CHANGE
→ 找出受影响 TECH_DEC
→ KEEP / REVALIDATE / INVALIDATE / ADD / REMOVE
→ 只重算受影响候选和组合
→ 更新推荐状态
→ 必要时更新 ADR/架构/计划
```

不因为一个局部变化无差别重写所有架构文档。

## 15. 输出质量检查

完成技术选型前逐项检查：
- [ ] 决策问题是否比“技术名选择”更完整？
- [ ] 候选是否真实、数量是否由实际可行性决定？
- [ ] 是否识别了技术层次？
- [ ] 是否检查互补和组合方案？
- [ ] 推荐是否可以追溯到项目约束？
- [ ] 是否解释不选其它方案的原因？
- [ ] 是否检查跨 TECH_DEC 兼容性？
- [ ] Draft 推荐是否仍标记 Proposed？
- [ ] Blocking/Deferable 和最晚确认点是否明确？
- [ ] 技术栈总览是否由决策汇总而来？
- [ ] 是否避免默认固定技术栈？
- [ ] 上游变化后是否有 Revalidation 路径？
