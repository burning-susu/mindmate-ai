# 性能测试选型与规范
> 文档类型：Capability
> Capability ID：CAP-TEST-PERFORMANCE
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G3、G8、G9、G10、G11
> 激活条件：对外服务、高并发、大数据量、性能敏感场景，或历史上存在性能缺陷且需要建立回归基线

## 0. Capability 元数据
- **目标**：判断是否需要性能测试，并提供前端性能、接口压测、基线、退化分析和上线关联的执行规范。
- **输入**：业务场景、目标用户量、数据规模、已有性能问题、部署环境与交付口径。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
## 0.1 定位
本文档回答两个问题：
1. 要不要给这个 REQ / 项目做性能测试？给出判断依据
2. 要做的话，测什么指标、用什么工具？给出可执行规范

**本身不是强制规则**：是否需要性能测试，由项目 Assessment 与对应 REQ/Spec 的“是否需要性能测试”声明决定。内部小工具、一次性练习性质的需求可以声明"不适用"；对外正式交付的门户/高并发场景/大数据量渲染场景应当声明需要覆盖。

与已有测试体系的关系：自动化测试 Capability 解决的是"功能对不对"（单元测试+E2E），当前 REQ 的 `test-cases.md` 的人工用例表格同样是功能测试范畴。本文档解决的是"快不快、扛不扛得住"，是独立于功能正确性之外的第三个测试维度。三者关系见第4节。

## 1. 要不要做性能测试：判断依据

### 1.1 值得投入性能测试成本
- 对外正式交付的项目（企业官网、门户网站），首屏加载慢会直接流失用户，性能是产品体验的一部分，不是可选项
- 会承载明显并发压力的接口/服务（如活动秒杀、抢购、大量用户同时访问的营销页）
- 涉及大数据量渲染的场景（长列表、大表格、复杂图表），数据量增长后容易出现卡顿甚至页面无响应
- 曾经出现过性能问题的模块（对照 项目缺陷/问题台账），修复后应该建立对应的性能基线，防止同一个问题在后续迭代中再次出现（回归测试的核心价值，与功能测试同理）

### 1.2 不必强求性能测试
- 内部管理工具、访问量小、用户群体固定的系统，性能压力本身就不大
- 一次性 Demo、练习性质的需求，生命周期短
- 项目还在快速试错阶段，页面结构频繁大改，此时建立的性能基线很快就会过期，投入产出比低

### 1.3 声明模板（可直接复制填入 REQ 的 spec.md）
```text
【性能测试声明】
本 REQ 测试范围：{{前端性能（首屏/交互响应） / 接口压测（并发承载） / 前端性能+接口压测 / 不适用}}
判断依据：{{如：对外门户首页，首屏加载速度直接影响用户留存 / 内部工具，访问量小，无需专门测性能}}
```

## 2. 性能测试的两个维度，不要混为一谈

性能问题分两类，测试方法和工具完全不同，判断"要不要测"时应该分开判断，不要笼统地问"要不要做性能测试"：

### 2.1 前端性能：单个用户访问时"快不快"
关注页面加载和交互的用户体感，核心指标（来自 Web Vitals，是目前可作为常用 Web 性能指标体系的参考）：
- **LCP（Largest Contentful Paint，最大内容绘制）**：页面主要内容渲染完成的时间，衡量"感觉页面加载完了"的速度
- **FCP（First Contentful Paint，首次内容绘制）**：页面开始显示内容的时间
- **CLS（Cumulative Layout Shift，累积布局偏移）**：页面加载过程中元素跳动的程度，影响体验但常被忽略
- **INP（Interaction to Next Paint，交互到下次绘制）**：用户点击/输入后页面响应的速度

**参考基线**（参考目标值，不是跨项目强制阈值；最终目标必须由项目场景和交付口径确定）：LCP 应在 2.5 秒以内，INP 应在 200 毫秒以内，CLS 应小于 0.1。超过这个范围通常意味着用户能明显感觉到"慢"。

### 2.2 接口/服务端压力测试：多个用户同时访问时"扛不扛得住"
关注系统在并发压力下的承载能力，核心指标：
- **响应时间（Response Time）**：单次请求从发出到收到响应的耗时，通常关注 P95/P99（95%/99%的请求都能在这个时间内完成，比"平均响应时间"更能反映真实体验，因为平均值会被少数快请求拉低）
- **吞吐量（Throughput / QPS）**：单位时间内系统能处理的请求数
- **错误率**：压力增大后请求失败（超时、5xx）的比例

**判断依据**：这类测试针对的是后端接口，前端工程师如果对接的接口没有明确并发场景（如秒杀、抢购），通常不需要主导这类测试；如果项目本身包含明确的高并发场景，需要联合后端一起测，前端负责验证"接口压力大时，页面是否有对应的降级提示，而不是直接白屏或无响应"。

## 3. 工具选型：按测试维度分别选择，不要求全都用

### 3.1 前端性能工具
| 工具 | 特点 | 适合场景 |
|---|---|---|
| Lighthouse | Chrome 内置，一键跑出评分和具体指标，上手成本最低 | 日常开发自查、CI 里跑基础性能回归检测 |
| WebPageTest | 支持多地区、多网络环境（如模拟弱网）测试，报告更详细 | 需要验证不同网络条件下真实用户体验的场景 |
| Chrome DevTools Performance 面板 | 可以录制并分析具体是哪段代码/哪个资源拖慢了页面 | 已经发现有性能问题，需要定位具体原因时使用 |

**判断依据**：日常开发自查、快速出个分数用 Lighthouse；要深入分析卡在哪一步，用 DevTools Performance 面板；要验证不同网络/地区下的真实体验，用 WebPageTest。三者不是二选一，可以配合使用。

### 3.2 接口压测工具
| 工具 | 特点 | 适合场景 |
|---|---|---|
| k6 | 用 JS 写测试脚本，上手门槛低，云端/本地均可跑，现代化程度高 | 前端工程师主导或参与压测时优先选，因为脚本语言与前端技术栈一致 |
| JMeter | 老牌工具，图形化配置，生态成熟，历史项目存量大 | 团队已有 JMeter 使用经验，或需要兼容已有的压测脚本资产时选它 |

**判断依据**：如果前端需要参与压测脚本编写，k6 用 JS 编写脚本的学习成本最低；如果压测主要由后端/测试团队主导，跟随他们已有的工具链即可，不必强行统一。

## 4. 与已有测试体系的关系（避免三套测试互相脱节）

| 测试类型 | 回答的问题 | 对应文档 |
|---|---|---|
| 功能测试 | 这个功能做对了吗（正常路径、边界值、异常处理是否符合业务规则） | 当前 REQ 的 `test-cases.md`（人工用例） + 自动化测试 Capability（单元测试/E2E自动化覆盖） |
| 性能测试 | 这个功能够快吗、扛得住压力吗 | 本文档 |
| 响应式与浏览器兼容 | 这个功能在不同设备/浏览器下表现一致吗 | `响应式与浏览器兼容清单.md` |

三者是同一个 REQ 下三个独立的验收维度，**互不替代**：功能测试全部通过不代表性能达标（可能逻辑对但很慢）；性能达标也不代表功能正确（可能跑得快但结果错）。声明是否需要执行时，应该在 Spec 第0节分别声明，各自独立判断，不要因为已经声明了"需要自动化测试"就假设性能测试也顺带做了。

## 5. 性能基线管理：让性能测试形成可持续的机制，不是测一次就完了
第1.1节提到"曾经出现过性能问题的模块应该建立性能基线"，本节说明基线具体怎么建立、怎么用。

### 5.1 什么是性能基线
基线是"第一次正式测出来、被认可为可接受的性能指标值"，作为后续所有对比的参照点。比如某个页面第一次测出 LCP 是 1.8 秒，且这个数字符合预期，这个 1.8 秒就成为该页面的基线。

### 5.2 基线的建立时机
- 该 REQ 首次上线前，正式跑一次性能测试（对照第2、3节的指标和工具），把结果记录在 当前 REQ 的进度 Evidence / 性能记录 里，标注为"基线"
- 若之前从未建立过基线（老项目补测），第一次达标的测试结果即可作为基线起点，不需要追溯"历史上本该是多少"

### 5.3 基线的持续比对：每次相关改动都要回归比对
后续任何涉及该模块的改动（不只是这个 REQ 本身，也包括它依赖的公共组件/接口被其他 REQ 修改），上线前都应该重新跑一次性能测试，和已记录的基线做比对：
- **未退化或有提升**：更新 当前 REQ 的进度 Evidence / 性能记录，把新的测试结果标记为新基线（基线应该随项目演进持续刷新，不是固定不变的历史值）
- **退化在可接受范围内**（如建议阈值：相对基线劣化不超过20%）：记录退化幅度和原因，判断是否可接受，可接受则照常上线，同时更新基线为当前值（承认这是新的正常水平）
- **退化超过可接受范围**：必须在上线前说明原因、评估是否需要优化后再上线，不能"性能测试出了问题但假装没看到直接上线"

### 5.4 与上线前检查的挂钩
若该 REQ 或其影响的模块声明了需要性能测试，"性能基线比对通过或已说明退化原因"应作为上线前检查清单的一项，与功能测试、安全测试的检查项并列，缺一不可，不能因为功能测试通过就认为可以上线。

## 6. 验收关联
若某 REQ 声明"性能测试：前端性能"或"接口压测"或"前端性能+接口压测"，验收时额外检查：
- [ ] 已用声明的工具跑出实际指标数据，不是凭感觉判断"够快了"
- [ ] 前端性能指标对照第2.1节基线，明显超出的地方已说明原因或已优化
- [ ] 接口压测已覆盖 Spec 里描述的实际并发场景（如声明是秒杀场景，压测并发数应贴近预估真实流量，不是随意跑一个数字）
- [ ] 性能测试的结论（通过/需优化/待跟进）已记录在该 REQ 的 当前 REQ 的进度 Evidence / 性能记录 里，作为后续迭代的性能基线参考
- [ ] 若该模块此前已有性能基线记录，本次已按第5.3节做退化比对，未见"明知退化超标却直接上线"的情况

若声明"不适用"：本节不适用，直接跳过。
