# 自动化测试选型与规范
> 文档类型：Capability
> Capability ID：CAP-TEST-AUTOMATION
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G3、G8、G9、G10、G11
> 激活条件：REQ/项目明确需要自动化测试，或风险、复用度、维护周期、关键业务程度使自动化回归具有明显收益

## 0. Capability 元数据
- **目标**：决定是否引入自动化测试、测试分层、工具选择、测试数据、CI 门禁以及 AI 辅助测试闭环。
- **输入**：需求 Spec、关键业务路径、已有测试工具链、环境能力、发布门禁要求。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
## 0.1 定位
本文档回答两个问题：
1. 要不要给这个 REQ 写自动化测试脚本？给出判断依据
2. 要写的话，用什么工具、测到什么颗粒度？给出可执行规范

**本身不是强制规则**：是否需要自动化测试、需要到什么程度，由对应 REQ 的 `spec.md` 第0节"是否需要自动化测试"字段声明决定。一次性练习性质的轻量需求（如 `具体练习/一次性需求` 示例包）可以声明"仅人工测试"，不强制写自动化脚本；涉及核心业务逻辑、长期维护的模块应当声明需要自动化覆盖。

与 当前 REQ 的 `test-cases.md` 的关系：那份文档里的人工测试用例表格（TC-001 等）永远是"要验证什么场景"的唯一事实源，本文档解决的是"这些场景里哪些该用脚本自动跑，而不是每次都靠人工点一遍"。两者不是替代关系，是分工关系。

## 1. 要不要写自动化测试：判断依据

### 1.1 值得投入自动化测试成本
- 核心业务逻辑（计算、状态转换、数据校验），一旦出错影响面大
- 会被长期维护、多次迭代的模块——手动回归测试的成本会随着迭代次数线性增加，自动化测试是把这个成本摊平
- 被多处复用的工具函数/组件——一旦改动，影响范围不容易靠人工全部想清楚，跑一遍测试比人工排查更可靠
- 之前出过 Bug 的模块（对照 `bugs-backlog.md`），修复后应该补一条对应的自动化用例，防止同一个问题再犯（回归测试的核心价值）

### 1.2 人工测试已经足够，不必强求自动化
- 一次性 Demo、练习性质的需求，生命周期短，写自动化脚本的维护成本超过收益
- 纯视觉/交互体验类判断（"好不好看""动画顺不顺"），这类判断本质上需要人工目视确认，自动化测试测不出"好看"，只能测"元素存在/属性正确"
- 项目还在快速试错阶段，UI/交互频繁大改，此时写的自动化测试会被频繁推翻重写，投入产出比低
- 简单静态页面、功能极少、不涉及交互逻辑分支的场景，不值得为此搭建自动化测试环境
- 单个函数级别的逻辑验证不要用 E2E 工具（如 Playwright/Cypress）去测——启动真实浏览器的成本远高于单元测试框架，这类场景应该用第2.1节的单元测试工具，"够不够格用E2E"和"该不该自动化"是两个独立的判断，不要混着问

### 1.3 声明模板（可直接复制填入 REQ 的 spec.md）
```text
【自动化测试声明】
本 REQ 测试范围：{{单元测试+接口自动化+E2E / 部分组合 / 仅人工测试}}
判断依据：{{如：涉及金额计算逻辑，需要单元测试覆盖边界值 / 一次性练习组件，人工过一遍TC表格已足够}}
```

### 1.4 辅助脚本语言的选择原则
业界不少测试培训资料的自动化脚本示例是用 Python 写的（如 pytest、Locust）。自动化测试脚本优先采用项目主语言与现有测试生态（见第2节），本文不绑定某一种语言或工具，不建议为了配合某个教程或某个工具的示例代码专门再学一门语言。原则：
- 辅助脚本（数据处理、批量校验、临时排查工具）优先用项目主语言（JS/TS）写，保持技术栈统一，降低维护成本
- 例外：某个工具只有 Python 实现、且明显比用 JS 重新实现更省事（如某些成熟的压测工具生态更偏 Python），此时可以引入 Python 作为该工具专属的脚本语言，但不应因此把项目其他测试脚本也迁移过去
- 判断依据同第2节"技术栈相关，不写死推荐谁"——工具服务于项目，不是项目服务于工具

## 2. 工具选型：技术栈相关，不写死推荐谁

本节只给判断依据，具体选哪个工具取决于项目已有技术栈——不要为了用某个工具而引入新的构建体系，优先选和项目现有工具链兼容度最高的那个。

### 2.0 先问：需不需要框架

**上框架之前先确认轻量脚本能不能解决。** 纯静态展示站（无构建体系、无 npm、改动频率低）搭常态化自动化测试环境，投入产出比通常不合理——这类项目最高频的故障是断链，用一个几十行的脚本就能全覆盖。

如项目已有轻量静态资源/链路自查工具，应优先复用项目现有工具；本 Capability 不规定具体工具路径（零依赖，扫全站 HTML 内部引用 + 锚点目标校验，秒级出结果，无需起服务器/浏览器）。实战中它发现过 21 个页面 favicon 路径缺 `../`、78 处锚点跳转静默失效。

**什么时候才升级到框架**：需要验证交互行为（点击、hover、表单）、需要跨浏览器一致性、需要验证 JS 执行后的渲染结果——这些静态扫描做不到，见第 2.2 节。

> **关于语言选择的例外说明**：这里使用的辅助脚本示例可能是 Python，与第 1 节"辅助脚本优先用项目主语言（JS/TS）"的原则不一致。判断依据：目标项目是纯静态站，**没有** JS/TS 工具链（无 package.json、无构建步骤），此时"项目主语言"这个前提不成立，选零依赖的 Python 反而比为一个脚本引入 npm 更省事。若项目本身已有 Node 工具链（如同时在用 `02-工具/SEO优化工具.md` 那套 Node 脚本），把它改写成 Node 更符合技术栈统一原则——逻辑很简单，重写成本低于长期维护两种语言的成本。

### 2.1 单元测试框架
| 工具 | 特点 | 适合场景 |
|---|---|---|
| Vitest | 与 Vite 生态原生集成，配置成本低，运行速度快（复用 Vite 的模块转换） | 若项目本身使用 Vite，优先评估，配置几乎零成本 |
| Jest | 生态最成熟，插件/断言库/Mock方案最全，历史项目存量最大 | 项目用 Webpack 或历史遗留构建体系时选它，或团队已有 Jest 经验积累 |

**判断依据**：项目构建工具是 Vite → 优先 Vitest；是其他构建体系或没有强烈倾向 → Jest 更保险（生态成熟度更高，遇到问题更容易找到解决方案）。两者 API 高度相似，迁移成本不高，不必过度纠结这个选择。

### 2.2 端到端（E2E）测试框架
| 工具 | 特点 | 适合场景 |
|---|---|---|
| Playwright | 微软维护，原生支持 Chromium/Firefox/WebKit 三大引擎。注意默认口径只测 Chromium（见"响应式与浏览器兼容清单"第 3.0 节），多引擎能力是"声明需要时才用得上"的余量，不是选它的默认理由 | 需要覆盖多浏览器兼容性验证的项目；或仅测 Chromium 但看重其调试工具与稳定性 |
| Cypress | 调试体验好（时间旅行调试、实时重载），社区教程多 | 只需要覆盖已声明的目标浏览器、更看重开发调试体验的项目 |

**判断依据**：浏览器范围以项目 Spec / Capability 声明为准，此时两者皆可，按团队熟悉度选。只有当该 REQ 的 Spec 明确声明要追加 Firefox（如交付对象用信创终端、面向海外）时，Playwright 的多引擎支持才成为决定性优势——可以用它把第3.2节的人工多浏览器验证自动化。**不要因为"Playwright 支持三引擎"就默认去跑三引擎**，那等于自己给项目加了清单里判定不值得做的成本。

### 2.3 与人工验证的关系（重要，不是"自动化能完全替代人工"）
自动化测试和 项目启用的响应式/浏览器兼容 Capability 第2.2节"无法代码化的部分"不冲突：
- Playwright/Cypress 能自动化验证"元素是否渲染、交互是否触发、跳转是否正确"这类**逻辑正确性**
- 不能替代"这个布局好不好看、留白是否合理"这类**审美判断**，这部分仍然要求人工目视复核
- 建议：用自动化测试跑通功能路径 + 保留一次人工审美复核，两者都做，不是有了自动化测试就可以跳过人工确认

### 2.4 失败时保留排查证据
E2E 测试失败后不要仅凭日志猜测原因，应配置失败时自动保留截图/录屏（多数主流 E2E 工具都内置此能力），让排查者不需要在本地重新复现就能看到失败当时的页面状态。这是"测试失败后怎么定位问题"的通用要求，不是某个工具的专属功能。

### 2.5 小程序真机与外部 Provider 测试
涉及小程序时，浏览器自动化不能代替真机验证。至少把以下维度写进 `test-cases.md`：

- 首次授权、拒绝授权、重新授权、系统权限关闭和换设备；
- 在线、弱网、断网、冷启动、重启微信、清理缓存和恢复网络；
- 相机、定位、相册、GPS 精度、离线规则缓存、上传队列和失败重试；
- 测试 AppID/正式 AppID、Mock/真实 Provider、合法域名和订阅消息配置。

第三方能力按环境分层：

1. 单元测试默认 Mock 第三方 SDK 和支付服务，只验证本地逻辑。
2. 接口自动化在独立测试环境验证鉴权、状态流转、幂等和错误处理，不直接操作生产支付或生产数据。
3. 真实支付、提现、订阅消息和平台审核只在明确授权的测试/生产环境执行，并保留金额、账号、配置和结果的脱敏证据。

没有真机、平台配置或运行日志证据的场景，结果只能记为“待验证”，不能写成“已通过”。

## 3. 单元测试规范

### 3.1 测试文件命名与存放
- 与被测文件同名，加 `.test.ts`/`.spec.ts` 后缀（具体后缀跟随项目所用框架的默认约定，Vitest/Jest 均支持这两种）
- 存放位置：优先与被测文件同目录（如 `utils/formatDate.ts` 对应 `utils/formatDate.test.ts`），或项目已有统一的 `__tests__/` 目录约定，两种方式选一种在项目内统一，不要混用

### 3.2 测什么，不测什么
- **优先覆盖**：纯函数、工具函数、业务逻辑计算（这类输入输出确定，测试成本低、收益高）
- **不必强求覆盖**：UI 组件的样式细节、纯展示型无逻辑分支的组件（测试这类东西的维护成本可能超过它能捕获的价值）
- 每写一个测试用例前先问：这段代码之前出过bug、或者未来最可能因为改动而出bug的地方在哪？测试资源优先投在这里，不是无差别地追求覆盖率数字

### 3.3 覆盖率不是目标，是参考信号
不设强制覆盖率红线（如"必须100%覆盖"），覆盖率数字可以用来发现明显的测试盲区，但不能作为唯一的验收标准——100%覆盖率不代表测试质量好，可能只是测试了大量无意义的路径。

### 3.4 测试独立性原则
每条测试用例应该能单独运行、单独通过，不依赖其他用例执行后留下的状态（如共享的全局变量、上一条用例写入的数据）。用例之间存在隐性依赖时，会导致"单独跑这条用例失败，但跑全部用例又通过"这类难排查的问题，也会导致调整用例顺序或并行执行时结果不稳定。该原则同样适用于第5节的 E2E 测试和第4节的接口自动化测试。

### 3.5 AAA 结构：单个测试用例内部的书写规范
一条测试用例内部建议按三段式组织，段落之间用空行分隔，让人一眼看出每段在做什么：
- **Arrange（准备）**：构造测试需要的输入数据、初始状态、Mock 依赖
- **Act（执行）**：调用被测试的函数/方法，只做这一件事
- **Assert（断言）**：验证结果是否符合预期

好处：断言部分越纯粹（不掺杂数据准备逻辑），用例越容易读懂"这条用例到底在验证什么"，也更容易在测试失败时快速定位是准备阶段的问题还是断言本身写错了。

### 3.6 Mock 的具体分类
第2.3节/第5.3节提到"外部依赖应该被 Mock"，但 Mock 不是只有一种形式，按用途区分：
- **Stub（打桩）**：替换掉一个依赖，让它返回固定的值，不关心它有没有被调用、调用了几次（如让"获取当前时间"固定返回某个时间点，方便测试和时间相关的逻辑）
- **Mock（狭义，含调用验证）**：不仅替换返回值，还要验证这个依赖有没有被正确调用（调用了几次、传了什么参数），常用于验证"该调用某个副作用函数时，是否真的调用了"（如验证提交表单后确实调用了一次"发送请求"的函数，且参数正确）
- **Spy（窥探）**：不替换原有实现，只是在旁边记录调用情况，原函数正常执行，用于"我想知道这个函数被调用的细节，但不想改变它的行为"的场景

**判断依据**：只关心返回值用 Stub；需要验证"有没有被正确调用"用 Mock；不想干扰原有逻辑只想观察用 Spy。三者是同一件事（替身对象）的不同侧重，具体测试框架里可能用同一套 API 实现（如 Vitest/Jest 的 `vi.fn()`/`jest.fn()`），概念上区分清楚有助于写出目的明确的测试。

## 3.7 集成测试的概念边界：别和接口自动化混为一谈
"集成测试"这个词在不同语境下指两种不同的东西，容易混淆：
- **前端模块集成测试**：验证纯前端内部多个模块/组件协作是否正确，不涉及真实网络请求（如"添加商品到购物车组件后，购物车图标的数量是否正确更新"这类跨组件的数据流转）。这类测试仍然用单元测试框架（Vitest/Jest）写，只是测试范围从"单个函数/组件"扩大到"多个模块的协作"，本质上是第3.2节"测什么"的延伸，不需要单独的工具
- **接口自动化测试**：验证前端和后端之间的接口调用是否正确，属于第4节的范畴，需要真实发起网络请求

**判断依据**：如果测试对象是纯前端逻辑（不管涉及一个模块还是多个模块协作），都归入本节（单元测试规范）处理；一旦测试涉及真实发起 HTTP 请求验证接口行为，就归入第4节。测试多模块协作时，模块的外部依赖（如接口请求）通常仍需要 Mock（对照第3.6节），只是被测对象的范围从单一函数扩大到多个模块的组合。

## 4. 接口自动化测试规范（单元测试与E2E之间的中间层）
接口自动化测试指不启动浏览器，直接对 HTTP 接口发请求、校验响应，速度比 E2E 快（不用渲染页面），又比单元测试更贴近真实场景（真的发了网络请求，走了真实的路由和中间件）。这一层容易被忽略——很多项目只有"单元测试"和"E2E测试"两层，缺了这个中间层，导致接口层面的问题只能靠 E2E 间接发现，定位成本更高。

### 4.1 什么时候优先写接口自动化，而不是直接写 E2E
- 验证某个接口本身的行为（参数校验、状态码、响应结构）时，优先写接口自动化测试，不必启动浏览器走完整页面流程
- 只有当需要验证"页面上的交互触发了正确的接口调用，且页面正确处理了响应"时，才需要 E2E
- 对照 项目 API Contract / 对应 API Capability 的接口测试清单"接口测试用例设计清单"逐类设计用例（参数校验类、认证授权类、业务逻辑类、响应结构类）

### 4.2 环境切换：baseURL 不能写死
接口自动化测试通常需要在多个环境跑（本地开发、测试环境、CI环境），请求的目标地址（`baseURL`）应该做成可配置项（如通过环境变量注入），不要写死在测试代码里。同一套测试脚本切换 `baseURL` 就能在不同环境复用，不需要为每个环境复制一份测试代码。

### 4.3 数据依赖：谁负责准备测试数据
接口自动化测试往往依赖特定的数据状态才能验证（如"测试删除订单"需要先有一条订单存在）。数据准备方式：
- 测试运行前，通过接口自身创建所需的前置数据（如先调用"创建订单"接口拿到订单ID，再测试删除该订单），这样测试自成一体，不依赖外部手动造数据
- 避免依赖"数据库里恰好已经存在的某条固定数据"，这类硬编码的数据依赖一旦该条数据被清理或修改，所有相关测试都会连带失败，且很难第一时间看出真实原因
- 具体的数据构造/清理策略见第7节"测试数据管理"

### 4.4 断言策略：不能只看状态码
- 最基础的断言是 HTTP 状态码是否符合预期，但只断言状态码远远不够——状态码对了不代表响应体内容对
- 完整的断言应该组合：状态码 + 响应体关键字段的值 + 响应体的结构（字段是否齐全、类型是否正确）
- 涉及副作用的接口（如创建、更新、删除），断言不能只看接口本身返回了什么，还要验证副作用是否真的发生（如创建后能否用查询接口查到这条新数据），必要时结合第7节的数据校验方式直接查库确认

### 4.5 链路测试：验证跨接口的业务流程
有些业务场景需要连续调用多个接口才能完成（如"下单"要经过创建订单、扣减库存、发送通知这几个接口/内部调用）。链路测试的目的是验证这条链路整体是否按预期完成，而不是孤立地测试单个接口：
- 按业务顺序依次调用相关接口，每一步都断言当前步骤的结果符合预期，同时为下一步提供所需数据（如用上一步返回的订单ID作为下一步的入参）
- 特别关注链路中间某一步失败时，前面已经执行的步骤是否被正确回滚/补偿（如扣了库存但通知发送失败，库存应该恢复还是允许不一致，这是业务规则决定的，测试要验证实际行为符合 Spec 里描述的规则）

### 4.6 测试组织方式
- 按接口所属的资源/模块分组组织测试文件（如 `users.api.test.ts`、`orders.api.test.ts`），与 `RESTful API设计规范.md` 里的资源划分保持一致，方便定位
- 每个接口至少覆盖第4.1节提到的四类用例中和该接口相关的部分，不要求每个接口都覆盖全部四类（如一个纯查询接口没有"认证授权类"里的写操作冲突场景）

## 5. E2E 测试规范

### 5.1 覆盖关键路径，不是全覆盖
E2E 测试运行成本高（要真实起服务、模拟浏览器交互），只覆盖**核心用户动线**：
- 用户最常走的主流程（如登录→下单→支付这条链路）
- 一旦损坏会直接影响业务的路径（如支付失败、登录失效）

不需要给每一个边缘交互都写E2E测试，边缘场景/异常输入优先靠单元测试覆盖业务逻辑层、接口自动化覆盖接口层，E2E测试聚焦在"整条链路能不能跑通"。

### 5.2 与响应式清单的联动
若该 REQ 同时声明了"是否需要执行响应式与浏览器兼容清单"为"是"，E2E 测试脚本默认只需在配置里跑 Chromium 一个引擎，对应清单第3.2节的实测要求；**仅当 Spec 的"目标浏览器"字段明确声明要追加 Firefox 时**，才在 Playwright 的 `projects` 里加上 Firefox 引擎。跑完自动化后仍建议至少人工打开一次做最终确认。

### 5.3 Mock 策略的基本原则
- 单元测试里，外部依赖（接口请求、第三方SDK）应该被 Mock，保证测试跑的是"这段逻辑本身对不对"，不受外部服务是否可用影响
- E2E 测试更贴近真实场景，优先用真实接口（或搭建好的测试环境接口），非必要不 Mock；如果依赖的第三方服务不稳定或有调用成本（如真实支付网关），才针对这一处做 Mock

### 5.4 元素定位优先级（决定脚本稳不稳定的关键）
E2E 测试脚本的稳定性主要取决于"用什么方式找到页面元素"，优先级从高到低：
1. **按角色/无障碍属性定位**（如按钮的角色是"button"、名称是"提交"）：最贴近真实用户找元素的方式，UI改样式不受影响
2. **按可见文字定位**：直观，但文案改了脚本就要跟着改，适合文案相对稳定的场景
3. **按表单标签定位**：适合表单类页面
4. **按专属测试属性定位**（如给元素加一个只用于测试标识的属性）：最不受样式、文案、DOM结构变动影响，稳定性最高，但需要开发在编码阶段配合埋点

**尽量少用 CSS 选择器/DOM 结构路径定位**（如按 class 名或第几个子元素定位）：这种方式和页面的具体实现细节强绑定，UI 稍微调整样式或调整 DOM 层级，脚本就会失效，维护成本最高。这条原则不限于某个具体工具，Playwright、Cypress 等主流 E2E 工具都遵循同样的优先级逻辑。

### 5.5 POM（页面对象模式）：避免元素定位代码到处重复
当同一个页面的元素选择器（第5.4节的定位逻辑）被多条测试用例分别写一遍时，一旦页面改版，需要同步改多处，这正是 `CODE-STANDARDS.md` 第4.1节"3处以上重复要提取"的信号。

**做法**：把某个页面的元素定位和基础操作封装成一个"页面对象"（如 `LoginPage` 类/模块），测试用例只调用页面对象暴露的方法（如 `loginPage.login(username, password)`），不直接在用例里写元素选择器。好处：
- 页面结构变化时，只需要改页面对象内部实现，所有引用它的测试用例不用改
- 测试用例本身读起来更像业务流程描述，而不是一堆底层操作细节

**判断依据**：只有一两条简单用例、页面结构不复杂时，不必为了"规范"强行拆页面对象；当同一个页面被3条以上用例复用、或者页面元素结构本身比较复杂时，页面对象模式的收益才会显现，判断标准和第4.1节的"3处以上重复"一致。

### 5.6 等待机制：为什么不该手写延时
早期的自动化测试工具需要手动写延时（如"等待2秒再操作"）来应对页面异步加载，这种写法的问题是：延时设太短会因为页面还没加载完就误判失败，设太长会让整套测试跑得很慢，而且遇到网络波动时延时长度永远是"猜的"，不可靠。

现代主流 E2E 工具（Playwright 等）内置**自动等待**机制：执行点击/输入等操作前，会自动等待目标元素出现并达到"可操作"状态（可见、未被遮挡、非禁用）再执行，等到超时才报错。这意味着**正常情况下不需要手写任何延时代码**，如果发现某处测试不稳定要靠加延时才能过，通常说明：
- 页面真实的加载状态和自动等待机制判断的"可操作"状态不一致（如元素已经在DOM里但数据还没渲染完成，看起来"可点"但点了没反应）
- 应该找到一个能准确反映"真正加载完成"的等待条件（如等待某个数据字段出现在页面上），而不是回退到猜测性的固定延时

## 6. 测试报告与归档
- 本地跑测试出问题靠第2.4节的截图/录屏排查即可；接入 CI（见第8节）后，每次运行都应该生成可访问的测试报告，且能追溯历史运行记录（哪次提交对应哪次测试结果），不是跑完看一眼终端输出就丢弃
- 报告至少包含：本次运行的通过/失败/跳过数量、失败用例的具体断言信息、失败用例对应的截图/录屏链接（E2E场景）
- 报告归档的意义：当某个功能间歇性失败（这次跑过、下次跑不过），如果没有历史记录，很难判断是环境问题还是代码本身不稳定；有历史记录可以看出"从哪次提交开始变得不稳定"，大幅缩小排查范围

## 7. 测试数据管理
自动化测试（尤其是接口自动化、E2E）的稳定性很大程度上取决于测试数据管不管得住，这一节解决"测试要用的数据从哪来、用完怎么处理"的问题。

### 7.1 测试环境与生产数据隔离
测试（尤其是会写入/删除数据的测试）必须在独立于生产环境的数据库/环境里跑，不能对生产数据做任何测试性的增删改。这是底线要求，不是"最佳实践"层面的建议。

### 7.2 数据初始化策略：每次测试前建立已知状态
测试结果要可预测，前提是测试开始前的数据状态是已知、可控的。两种常见策略：
- **每次测试前重置到已知状态**（如清空测试专用的表，插入固定的种子数据），保证不管之前跑过多少次测试、顺序如何，这次测试开始时的状态都一样
- **测试自己创建自己需要的数据**（对照第4.3节"数据依赖"），测试用例内部先调用接口创建好本次需要的前置数据，不依赖外部预先准备好的固定数据

**判断依据**：如果多条测试用例都需要类似的基础数据（如都需要一个已存在的用户），用种子数据初始化更省重复代码；如果某条用例需要的数据比较独特，让它自己创建更清晰、更符合第3.4节"测试独立性原则"。

### 7.3 测试后的数据清理
写入型测试（创建、修改）执行后产生的数据，应该在测试结束后清理（删除掉，或者依赖第7.2节"每次前重置"的策略自然覆盖），避免测试数据不断累积，长期跑下去污染整个测试环境，也避免下次测试因为"数据已经存在"（如唯一性约束冲突）而失败。

### 7.4 用直接查库校验作为断言的补充手段
不要完全信任接口返回的数据就代表操作真的生效了——接口可能返回了"成功"，但实际没有正确落库（如事务处理有问题）。对于重要的写操作，除了断言接口返回结果，建议直接查询数据库确认最终数据状态确实符合预期，这是第4.4节"断言策略"里提到的验证副作用是否真实发生的具体做法。

### 7.5 回归测试要覆盖边缘数据状态，不只是"干净"的正常数据
建立测试数据时，除了覆盖"一切正常"的数据状态，还应该覆盖真实业务里会遇到的边缘状态（如订单处于"已取消"状态时不能再支付、库存为0时不能下单）。这些边缘状态数据的构造本身也应该纳入第7.2节的初始化策略里，不要每次都临时手动造。

## 8. 验收关联
若某 REQ 声明"自动化测试"包含单元测试/接口自动化/E2E 中的任意组合，验收时额外检查：
- [ ] 自动化脚本覆盖了 `test-cases.md` 里标注为"已有脚本覆盖"的所有用例
- [ ] 覆盖了 Spec 第5节"异常处理"里列出的每一种异常场景，不是只测了正常路径
- [ ] 若包含接口自动化，已按 项目 API Contract / 对应 API Capability 的接口测试清单清单检查过参数校验/认证授权/业务逻辑/响应结构四类场景
- [ ] 若包含 E2E 且该 REQ 也声明了响应式清单要求，E2E 脚本已配置多浏览器运行
- [ ] 测试文件命名和存放位置符合第3.1节约定
- [ ] 未为了追求覆盖率数字而写大量无意义的测试用例（如给纯展示组件的每个prop都写一条断言）
- [ ] 涉及数据写入的测试，已按第7节做好数据隔离与清理，未污染测试环境

若声明"仅人工测试"：本节不适用，直接跳过，以 `test-cases.md` 里的人工用例表格作为验收依据。

## 9. CI 流水线与门禁分级
自动化测试脚本写好后，价值不止于"本地手动跑一遍"，更大的价值在于接入 CI（如 GitHub Actions / GitLab CI），在每次提交/合并前自动运行，防止改动在未被察觉的情况下破坏已有功能。

### 9.1 接入时机
若该 REQ 声明了需要自动化测试，建议在测试脚本稳定跑通几轮之后接入 CI，不必等到项目所有测试都写完才接入——先让已有的测试进入自动化流程，后续新增的测试自然会被覆盖。

### 9.2 门禁分级：不同阶段跑不同深度的测试
CI 门禁不是"一刀切在每个环节都跑全部测试"，按耗时和重要性分级，按项目风险和 CI 能力，至少建立快速门禁与发布前深度门禁中的一种或多种：
- **提交/推送时（快门禁）**：跑单元测试（速度快，几秒到几十秒），未通过直接阻断，不允许继续
- **合并到主分支/准备发布前（慢门禁）**：在快门禁基础上，追加跑接口自动化测试和 E2E 测试（耗时更长），未通过阻断合并/发布，不是"提示一下但仍允许继续"

**核心原则**：门禁没通过就是硬性阻断，不是可以忽略的警告——如果门禁形同虚设（红了也照样合并），CI 本身就失去了意义。

### 9.3 与提交规范的联动
接入 CI 后，提交代码前的自查清单（见 `DOCS-GIT.md` 的"提交前自查清单"）里应该补一条"本地已跑过相关测试脚本且全部通过"，把自动化测试和提交规范打通；`DOCS-GIT.md` 里"打 tag 前"的回滚原则也应补充"CI 必须全绿才能打 tag"，不允许在已知测试失败的状态下标记一个"稳定版本"。

是否接入 CI、接入到什么程度，本身也是按需判断，不强制要求，判断依据同第1节。

## 10. AI辅助测试闭环：用调度脚本让"写代码-跑测试-修复"自动循环
在重复出现“AI改代码→跑测试→按失败结果继续修复”的场景"让AI写代码→自己跑测试→把报错粘贴回去让AI改"这个循环时，这一步可以用一个调度脚本自动化，省去人工来回粘贴日志的动作。本节只给架构判断依据和可复制的脚本模板，**不在本手册仓库里放置真正会执行的脚本**——原因见第10.4节。

### 10.1 两种架构，先分清楚要不要上重的方案
- **方案A：中控调度脚本**（推荐起点）：一个本地脚本按顺序调用"AI生成代码→跑测试→判断结果→失败则把报错回传给AI要求修复→重跑"，中间没有独立的服务，AI之间不直接对话，全部消息经调度脚本转发。开发量小，一个脚本文件就能跑。
- **方案B：双向对等Agent**（A2A架构）：把"写代码"和"跑测试"分别包装成两个独立的常驻服务，让它们能互相主动呼叫、互相回调，不需要中控转发。开发量大（要搭两套服务、维护双向通信协议），只有在需要多个Agent长期协作、频繁交互的场景才值得投入。

**判断依据**：个人开发者的典型场景是"写一个模块→测→改→测，直到通过"，这是线性流程，不需要两个Agent互相主动呼叫，方案A完全够用，更适合作为轻量起点；若项目已有多 Agent 平台，可按实际需要采用其他方案。方案B的复杂度在这个场景下不成比例，不建议现阶段投入。

### 10.2 方案A的关键风险点（原始参考脚本容易忽略的地方）
直接抄一份网上流传的调度脚本示例大概率会踩到这几个坑，落地前先确认已解决：
- **不能靠字符串匹配判断测试成败**：像 `if "All tests passed" in test_result` 这种判断方式，测试框架换个版本或输出格式改了就会误判。应该让测试命令输出结构化结果（如 JSON 格式的测试报告），调度脚本解析这个结构化数据来判断，不是猜文本里有没有某句话
- **必须设重试上限，且达到上限后要人工介入，不能无限循环**：AI对报错的理解可能本身有偏差（修复A的时候搞坏了B），没有上限的循环会一直空转，消耗大量API调用
- **执行AI生成的代码本身有风险**：即便在测试环境，运行未经人工审查的代码也要注意隔离（不要在能访问生产资源的环境里跑这套闭环），且需要日志留存，方便回头看AI每一轮到底改了什么
- **具体CLI命令的参数要先验证，不能假设能直接跑**：不同版本的CLI工具接口可能不同，落地前先手动跑一遍确认命令本身能执行，再接入调度脚本

### 10.3 方案A的脚本模板（解决了第10.2节字符串匹配问题的版本）
以下是**改进后的伪代码模板**，用于说明结构，不是可以直接复制运行的完整实现——具体的CLI调用参数需要按当时你本机安装的工具版本核实：

```text
定义：MAX_RETRY = 3（达到上限后停止，不无限循环）

函数 判断测试是否通过(测试命令的输出):
    尝试将输出解析为结构化格式（如 JSON 测试报告）
    如果解析失败（说明这次运行本身就有问题，而不是测试失败）：
        返回"异常"，不当作"失败"处理，直接停止循环等待人工介入
    读取结构化数据里的通过/失败用例数
    返回 失败用例数 == 0

循环 最多 MAX_RETRY 轮：
    调用 AI 生成/修复代码，写入文件
    调用测试命令，拿到输出
    根据"判断测试是否通过"函数处理结果：
        通过 → 结束，记录本轮日志
        异常 → 停止循环，打印详情，等待人工介入（不算作一次失败重试）
        失败 → 把结构化的失败详情（不是整段原始输出）作为下一轮的输入，继续循环
    若达到 MAX_RETRY 仍未通过 → 停止，明确提示"已达重试上限，需要人工介入"，不要静默失败
```

### 10.4 为什么不在本手册仓库里放真正能跑的脚本
- 本手册仓库是纯文档项目，没有可供测试的业务代码，这类脚本放在这里没有实际执行对象
- 这类脚本会真实调用AI服务的API（产生费用）、真实执行生成的代码，属于需要环境隔离和人工监督的操作，不适合作为仓库里默认存在的文件
- 与编辑器/Agent 规则的适配原则一致：本节只提供参考模板，真正要用时，把第10.3节的结构复制到你当时具体在开发的业务项目里，按那个项目的技术栈和CLI版本补全成可执行代码
