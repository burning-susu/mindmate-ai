# TEST-METHODOLOGY
> 文档类型：Capability
> Capability ID：CAP-TEST-METHODOLOGY
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G3、G8、G9、G10、G11
> 激活条件：项目需要系统设计功能、接口或验收测试场景

## 0. 定位
本文 Capability 用于测试场景设计。是否启用由项目 Assessment / REQ 决定；启用后，它提供设计方法，不绑定具体自动化工具。

解决的问题：当前 REQ 的 `test-cases.md` 里的 TC 表格只给了"正常路径/边界值/非法输入"这几个场景标签，但没有说明"怎么系统化地把场景想全，不遗漏"。本文档补的就是这一层方法论；测试用例具体填在哪个文档、自动化怎么做，仍然看 `test-cases.md`、自动化测试 Capability、性能测试 Capability、安全测试 Capability——本文档是这些文档共用的底层设计方法。

## 1. 测试生命周期与流程
一个功能从提需求到测试完成，标准顺序是：
**需求分析 → 测试计划 → 测试设计（写用例）→ 测试执行 → 测试评估**

对应到当前项目文档体系：
- 需求分析：对应写 `spec.md` 时同步想清楚"这个功能到底要测哪些点"
- 测试计划：对应 `plan.md`（轻量需求可以省略这一步，直接进入设计）
- 测试设计：对应写 `test-cases.md` 的 TC 表格，本文档第2节讲怎么设计
- 测试执行：跑用例（人工点/自动化跑），记录 pass/fail
- 测试评估：对应 `acceptance.md` 的验收判定

## 2. 用例设计方法论（核心）

### 2.1 等价类划分：先把输入空间分类，而不是随手编几个值
把所有可能的输入划分成"有效等价类"（合理、符合预期的输入）和"无效等价类"（不合理、应该被拦截的输入），每类只需要挑一个代表值测试，不需要穷举。

判断怎么划分等价类，看输入条件属于以下哪种情况：
- **规定了取值范围**（如年龄0-150）：1个有效等价类（范围内），2个无效等价类（小于下限、大于上限）
- **规定了一个固定集合**（如省份只能是34个省市之一）：1个有效等价类（在集合内），1个无效等价类（不在集合内）
- **输入是布尔量**（如"是否同意协议"）：1个有效等价类（勾选），1个无效等价类（不勾选）
- **规定了必须遵守的规则**（如必须是正整数）：1个有效等价类（符合规则），N个无效等价类（从不同角度违反规则——负数、小数、零，各算一类）
- **同一等价类内部处理方式不同**（如分数0-100按区间返回不同等级）：应该把这个等价类继续拆细，拆成"每种处理方式对应一个有效等价类"

**用法**：写 `test-cases.md` 的 TC-001~TC-003 时，先把该字段的输入按上面规则分类，确保每个有效等价类和每个无效等价类都至少有一条对应的 TC，而不是凭感觉编几个测试数据。

### 2.2 边界值分析：等价类划分完之后，专门测边界
边界值分析和等价类划分是配套使用的，不是替代关系：等价类划分决定"测哪几类输入"，边界值分析决定"每一类里具体测哪个值"。

**核心思路**：取正好等于边界、比边界大一点、比边界小一点的值，因为边界处最容易出错（比如用 `>` 还是 `>=` 写错，导致边界值被误判）。

举例：字段要求"长度不超过200字符"，边界值应该测：200字符（正好等于，应该通过）、201字符（刚超过一点，应该被拦截）、199字符（边界内一点，应该通过）、0字符/空字符串（另一个边界）。

### 2.3 场景法：测试完整业务流程，而不是单个字段
前两种方法测的是"单个输入字段对不对"，场景法测的是"一整条业务流程走不走得通"，适用于登录、下单、支付这类多步骤的流程。

**做法**：把业务流程画成一张流程图，标出主路径（最常见的走法）和备选路径（各种分支，如支付方式选微信/支付宝/银行卡、验证失败重试等），每条路径设计至少一条测试用例，确保所有分支都被覆盖到，不是只测"一路顺利走到底"这一条路径。

**举例**（不是要照抄这个例子本身，是理解这种设计思路）：一个"下单支付"流程，主路径是"选商品→登录→选择支付方式→支付成功→下单成功"；备选路径要覆盖"支付失败重试后成功""支付失败达到上限后账户锁定""未登录时先跳转注册流程再支付"等分支，每条分支单独列一条 TC。

### 2.4 因果图法：多个条件组合时用（了解即可，非高频场景）
当一个功能的结果由多个独立输入条件组合决定时（比如"是否会员"+"是否首单"+"是否使用优惠券"三个条件组合出不同的价格结果），穷举所有组合会有 2^n 种，因果图法通过分析条件之间的因果关系、约束关系，画出判定表，减少不必要的重复组合，只测有意义的组合。这个方法论对个人开发者使用场景有限（更适合条件组合非常多的复杂业务），了解思路即可，不强制要求每次都画因果图，简单的组合直接用等价类+场景法就够。

## 3. 测试用例的标准要素
每条测试用例应包含以下字段（`test-cases.md` 的 TC 表格是这些字段的精简版，字段含义如下）：
- **用例编号**：唯一标识（TC-001 这种格式）
- **测试场景/标题**：一句话说清楚测什么，同一功能模块下标题不能重复
- **重要级别**：高/中/低（帮助在时间不够时决定先测哪些）
- **预置条件**：执行这条用例前必须满足的前提（如"用户已登录"），没有前提就不用写
- **测试输入**：具体输入什么数据
- **操作步骤**：按顺序描述怎么操作
- **预期结果**：结果必须是唯一确定的描述，不能写"应该正常显示或提示错误"这种模糊表述——预期结果只能有一个明确答案，否则无法判定 pass/fail

## 4. Bug 记录规范

### 4.1 判断一个现象是不是 Bug
四种典型情况都算 Bug：
- 功能没有实现需求要求的内容
- 出现了需求里明确说不该出现的错误
- 功能做了需求范围之外的事（超出范围本身也是问题，不是"做多了更好"）
- 既未写入 Spec/Contract、又无法找到已批准的项目约定或验收基线的行为，不应仅凭“常理”直接判定为 Bug；应先登记 TBD / Open Item（如注册成功后应该跳转，需求没写但用户体验上必须有）

判断依据优先级：Spec / Contract / 已批准验收口径 > 项目现有约定 > 可明确引用的通用规范 > 主观判断。不要仅凭个人感觉判定"这样做不好"就算 Bug，先检查 Spec 有没有明确说，没有的话再看是否违反通用惯例。

### 4.2 Bug 记录字段与生命周期
项目缺陷/问题台账 目前的字段（编号/关联REQ/现象/根因/修复状态/回归结果）基础上，"修复状态"应遵循以下生命周期流转，不是随意写"已修复/未修复"两态：

**新建 → 确认（复现且判定为真Bug）→ 修复中 → 待验证（已修复，等待回归）→ 已关闭（回归通过）**
（若确认阶段发现不是缺陷，或已知问题暂不修复，可使用项目既定的“已拒绝/延期/待定”等状态，并写明原因）

回归验证时，不能只验证"报告里描述的那个操作步骤"，还要检查修复有没有引入新问题（顺带做一次该模块周边功能的快速回归）。

### 4.3 严重程度分级（帮助排优先级）
- **严重（Critical）**：核心功能完全不可用、数据丢失/错误、安全漏洞
- **高（High）**：主要功能受影响但有替代路径，或影响范围较大
- **中（Medium）**：次要功能异常，不影响主流程
- **低（Low）**：视觉细节、文案错误等不影响功能的问题

## 5. 测试计划的核心要素（中高影响变更适用）
低影响变更不一定需要独立测试计划；涉及业务逻辑调整、架构变化或较大影响面时，`REQ-TEMPLATE-plan.md` 可以补充以下测试相关维度：
- **测试范围**：这次改动涉及哪些功能模块，哪些是核心必测、哪些是次要可选测
- **测试策略**：这次要做哪几类测试（功能测试/性能测试/安全测试...），对照本手册各按需声明文档逐一判断
- **测试目标**：测到什么程度算可以上线（不是"测到没有Bug"，而是"核心路径通过+已知问题都在可接受范围"）

## 6. 没有独立测试人员时的结构化自查机制
多人团队里"用例评审"是让其他人帮你发现设计盲区。个人全权负责的场景下没有"别人"可以评审，但不能因此跳过这一步，而是用结构化自查代替：

- **时间隔离自查**：写完用例后不要立刻自查，间隔一段时间（哪怕只是先做别的任务半小时）再回来看一遍，跳出刚写完时的思维定式，更容易发现漏洞
- **对照等价类清单自查**：针对每个输入字段，重新过一遍第2.1节的等价类划分规则，检查是否所有"有效等价类"和"无效等价类"都有对应的 TC，尤其容易漏掉的是"规则的反面"（比如测了必填校验，忘了测超长输入）
- **对照 Spec 第5节"异常处理"逐条自查**：确保每一条异常处理规则都能在 TC 表格里找到对应的验证用例，一条对不上就是漏测
- 本条自查清单与项目治理中的执行校准清单配合使用，不是替代关系

## 7. 与其他文档的关系
- 本文档提供**设计方法**（怎么想全场景）
- 当前 REQ 的 `test-cases.md` 是**记录场所**（把设计出的场景填进 TC 表格）
- 自动化测试 Capability / 性能测试 Capability / 安全测试 Capability 是**执行方式**（这些场景里哪些要自动化、怎么测性能、怎么测安全）
- 项目缺陷/问题台账 是**缺陷记录场所**，字段规范见本文档第4节
