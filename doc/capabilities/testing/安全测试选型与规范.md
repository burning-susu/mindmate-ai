# 安全测试选型与规范
> 文档类型：Capability
> Capability ID：CAP-TEST-SECURITY
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G3、G8、G9、G10、G11
> 激活条件：涉及身份认证、权限、支付、个人信息、敏感数据、公开 API、管理后台或其他高风险资产

## 0. Capability 元数据
- **目标**：提供前端、接口、认证授权、敏感信息与常见注入问题的基础安全验证方法，以及升级到专业安全测试的边界。
- **输入**：安全风险分类、数据敏感度、外部可达性、权限模型、平台/合规要求。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。
## 0.1 定位
本文档回答两个问题：
1. 要不要给这个 REQ / 项目做安全测试？给出判断依据
2. 要做的话，测哪些点、前端和后端各自负责什么？给出可执行规范

**本身不是强制规则**：是否需要安全测试，由项目 Assessment 与对应 REQ/Spec 的“是否需要安全测试”声明决定。内部工具、无用户数据的展示页面可根据风险声明“不适用”；对外服务、账号、支付、个人信息、权限管理等场景通常需要覆盖。

**特别说明（个人全权负责场景）**：当项目没有专业安全团队或尚未进入专业渗透测试阶段时，本 Capability 提供一套工程团队可自行执行的基础安全检查清单；它不是完整渗透测试，也不能替代高等级安全评估。

## 1. 要不要做安全测试：判断依据

### 1.1 必须覆盖
- 涉及用户注册/登录/身份认证的功能
- 涉及支付、订单、金额计算的功能
- 涉及用户个人信息（手机号、身份证、地址等敏感数据）的存储和传输
- 后台管理系统（一旦被攻破，影响面是全站数据，风险远高于单个页面）
- 对外公开访问、任何人都能触达的接口/页面

### 1.2 可以声明不适用
- 纯内部工具、访问范围受控（如仅公司内网访问）
- 纯展示型页面，不涉及用户输入、不涉及数据提交
- 一次性练习/Demo，不会真实上线

### 1.3 声明模板（可直接复制填入 REQ 的 spec.md）
```text
【安全测试声明】
本 REQ 测试范围：{{前端基础防护 / 接口安全（越权+注入基础检测） / 前端+接口 / 不适用}}
判断依据：{{如：涉及用户登录态和个人信息展示，需要覆盖越权访问检测 / 内部工具，访问范围受控，暂不测}}
```

## 2. 前端能自己验证的点

### 2.1 XSS（跨站脚本攻击）基础防护
- 任何用户输入的内容，渲染到页面时不能被当作 HTML/脚本执行。现代前端框架（Vue/React 等）默认对插值内容做转义，但要警惕框架提供的"绕过转义"的写法（如 `v-html`、`dangerouslySetInnerHTML`），只有确定内容来源可信（如后端已做过消毒处理的富文本）才能使用，用户可直接输入的内容不能直接走这类接口
- 检查方式：在任意文本输入框尝试输入 `<script>alert(1)</script>` 或 `<img src=x onerror=alert(1)>`，提交后如果页面弹出弹窗，说明存在 XSS 风险，需要检查该处渲染逻辑

### 2.2 敏感信息不能出现在前端代码/请求中
- 前端打包后的代码（包括 sourcemap）任何人都能下载查看，绝对不能把密钥、密码、内部接口凭证写在前端代码里
- 检查方式：打包后搜索源码里是否含有 `secret`、`password`、`apikey` 等明文字符串；检查网络请求面板，确认没有把不该暴露的内部字段（如其他用户的完整信息）一起返回给前端

### 2.3 前端权限控制只是体验优化，不是安全边界
呼应 `RESTful API设计规范.md` 第6.4节：前端隐藏/禁用某个按钮不能防止有技术能力的用户绕过前端直接调接口。前端做权限判断的目的是让普通用户有更好的体验（不该看到的操作不要展示），不能作为安全防线本身来验收，安全测试的真正验证点在后端接口。

### 2.4 CSRF（跨站请求伪造）基础认知
- 如果项目用 Cookie 存储登录态（而非纯 Token 放在请求头），需要确认接口对状态变更类请求（POST/PUT/DELETE）有 CSRF 防护机制（如 SameSite Cookie 属性、CSRF Token 校验）
- 纯 Token 放在 `Authorization` header 里传递（本手册 RESTful 规范默认推荐的方式）天然不容易受 CSRF 影响，因为攻击者的跨站请求拿不到这个 header

### 2.5 部署资料与构建产物中的敏感信息

安全检查不能只看业务源码，还必须扫描以下范围：

- Git 已跟踪文件、未跟踪文件、历史提交和构建产物；
- `.env`、`application.yml`、Docker Compose、部署 README 和 Prompt 记录；
- 压缩包、备份目录、服务器登录说明、SSH 私钥和支付证书目录；
- 前端打包产物、日志、错误截图和 CI 输出。

重点搜索：密码、AppSecret、Token、API Key、API v3 Key、商户号、证书序列号、私钥、SSH 密钥、数据库连接信息和高权限账号。

发现真实值时的处理顺序：

1. 立即按已泄露处理，轮换凭据并检查使用日志；
2. 用占位符替换资料中的真实值，保留变量名和配置结构；
3. 从 Git 历史、压缩包和备份中清理旧值，不能只改当前工作区；
4. 通过 Secret 管理或运行时环境注入真实值；
5. 在验收记录中写明轮换时间、影响范围和复核结果，但不记录新凭据。

`.gitignore` 只能阻止未来未跟踪文件进入 Git，不能清除已经提交的敏感值，也不能保护已打包的 ZIP 或复制目录。

## 3. 接口/后端要验证的点

### 3.1 越权访问：安全测试里最容易被忽视、也最常见的问题
分两种，检查方式不同：

**水平越权**：A 用户能否访问/修改 B 用户的数据（同级别用户之间）。
检查方式：用用户A登录拿到token，尝试访问用户B的资源（如 `GET /users/B的id/orders`），如果能拿到数据，说明接口只校验了"是否登录"，没校验"登录的人是否有权访问这条具体数据"。

**垂直越权**：低权限用户能否执行高权限操作（如普通用户能否调用管理员专属接口）。
检查方式：用普通用户的token，直接请求管理端接口（如 `DELETE /admin/users/1`），确认接口会返回 403 而不是执行成功。

**本手册的默认要求**：任何返回"某个具体资源"的接口，都必须在后端校验"当前登录用户是否有权访问这个具体资源ID"，不能只校验"有没有登录"。这一条应作为接口开发的默认习惯，不是安全测试阶段才检查的事后补救。

### 3.2 输入校验：不能只信任前端已经校验过
前端做的校验（必填、格式、长度）是用户体验层面的，**后端必须重复做同样的校验**，因为请求可以绕过前端直接发给接口。检查方式：绕过前端页面，直接用请求工具（如 Postman）向接口发送前端本该拦截的非法数据（超长字符串、错误类型、SQL特殊字符如单引号），确认接口能正确拒绝，而不是直接报错崩溃或者被错误地存进数据库。

### 3.3 SQL 注入基础检测（若自己写后端SQL查询）
- 检查代码里是否用字符串拼接的方式构造SQL语句（如 `"SELECT * FROM users WHERE name = '" + input + "'"`），这种写法一旦input里包含特殊构造的内容就可能改变SQL语义，是最常见的注入方式
- 正确做法：使用参数化查询/预编译语句（几乎所有主流数据库驱动和ORM都支持），让输入内容始终被当作数据处理，不会被解释成SQL语法的一部分
- 检查方式：在任意会被拼进SQL查询的输入框尝试输入 `' OR '1'='1`，确认不会绕过校验逻辑或导致异常的查询结果

### 3.4 认证与限流基础检查
- 确认登录接口对暴力破解（连续尝试大量密码）有限制（如连续失败N次后锁定一段时间），呼应 `RESTful API设计规范.md` 第6.4节"必须有限流机制"
- 确认敏感操作（改密码、改绑手机号）不能仅凭登录态完成，应要求二次验证（原密码/验证码），防止用户token被盗后攻击者能随意接管账号

## 4. 参考框架说明
业界有成熟的公开安全风险分类框架（如覆盖常见Web应用风险的OWASP Top 10、专门针对API的OWASP API Security Top 10），本文档第2、3节的检查点是从这些公开框架里挑选出"工程团队最容易遇到且可自行验证"的一部分，不是完整覆盖。如果项目安全等级要求更高（如涉及金融、医疗数据），应寻求专业安全测试或渗透测试支持，本文档的检查清单只作为基础及格线。

## 5. 验收关联
若某 REQ 声明"安全测试：前端基础防护"或"接口安全"或"前端+接口"，验收时额外检查：
- [ ] 用户输入内容渲染到页面前已确认无 XSS 风险（对照第2.1节）
- [ ] 前端代码/打包产物中未出现明文密钥、密码等敏感信息（对照第2.2节）
- [ ] 涉及具体资源ID的接口已做水平越权检测（用不同账号互相访问验证，对照第3.1节）
- [ ] 涉及权限分级的接口已做垂直越权检测（低权限账号尝试高权限操作，对照第3.1节）
- [ ] 后端接口已重复做前端已有的输入校验，不完全信任前端传来的数据（对照第3.2节）
- [ ] 若自己编写SQL查询，已使用参数化查询，未见字符串拼接SQL的写法（对照第3.3节）
- [ ] 登录/敏感操作接口已有限流或二次验证机制（对照第3.4节）
- [ ] Git、压缩包、部署文档、Prompt 记录和构建产物已完成敏感信息扫描（对照第2.5节）
- [ ] 历史泄露凭据已轮换，未只依赖 `.gitignore` 或删除当前文件
- [ ] 生产配置与 Demo/测试配置已分离，默认值不会指向真实支付或生产数据

若项目基于风险评估声明“不适用”：本节跳过，但应保留“不适用”的判断依据和责任边界。
