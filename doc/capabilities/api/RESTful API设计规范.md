# RESTful API设计规范
> 文档类型：Capability
> Capability ID：CAP-API-RESTFUL
> 文档版本：V2.0
> 文档状态：通用基线
> 适用阶段：G8、G9、G10、G11
> 激活条件：新建 HTTP API、需要统一 API 契约、评审 REST 风格存量接口，且项目未选择 GraphQL/RPC 等替代协议作为主要事实源

## 0. Capability 元数据
- **目标**：决定是否采用 RESTful，并在采用后提供 URI、HTTP 方法、状态码、认证授权、响应结构、复杂查询、版本和迁移的可执行规范。
- **输入**：原始需求 / API Contract / 已有接口样例 / 项目架构决策。
- **输出**：项目在当前 Capability 下可执行的方案、规则、检查项与 Evidence。
- **治理方式**：本文件不是全项目无条件生效的全局规则。是否启用由 v3.2 的 `PROJECT_PROFILE`、`ASSESSMENT`、`CAPABILITY ACTIVATION` 与具体 REQ/Spec 决定。
- **项目化位置**：具体框架、平台、Provider、路径、版本、阈值和团队约定写入项目自身的 Profile / Spec / ADR / Rule，不在这里写死。

## 0.1 使用方式
1. 先判断项目是否适合采用 RESTful，不要因为“标准”二字就强行改造现有接口。
2. 若项目已有明确接口风格，先登记现状，再决定新接口是否跟随现有风格。
3. 选定 REST 后，本文件第 3～12 节才作为具体执行规则。
4. 若只对接第三方 API，则重点使用“契约对账、错误处理、认证、版本和测试清单”，不要求改造第三方接口。

## 1. 核心原则回顾
REST（Representational State Transfer）不是协议，是一组设计约束。前端即使不写后端代码，也常常是这套约束的实际执行者和评审者（判断"这个接口设计得规范吗"、自己设计 Mock/BFF 接口）。核心原则：
- **资源为中心**：一切数据建模成资源，每个资源用唯一 URI 标识
- **无状态通信**：服务端不保存客户端状态，每个请求自包含所需信息（如认证令牌、分页参数），前端不能假设"服务端记得上次请求的状态"
- **统一接口**：用标准 HTTP 方法表达操作意图，用 JSON 等格式传输资源表述
- **可缓存性**：响应应明确标记是否可缓存
- **客户端-服务端分离**：前端管 UI，后端管数据和业务逻辑，两者独立演化

## 2. 是否要求 RESTful：判断依据

### 2.1 适合要求/推动 RESTful 规范
- 新建后端服务，接口从零设计
- 团队内部/跨团队协作的中大型项目，需要长期维护和多人协作
- 需要良好的 HTTP 缓存收益（CDN、浏览器缓存）
- 数据模型相对稳定，以标准 CRUD 为主

### 2.2 不必强求 / 应声明沿用现状
- 对接第三方已有接口，接口风格由对方决定，前端无法也不该要求改造
- 老项目存量接口是非 REST 风格（如统一走 `POST` 的 RPC 风格），全面重构成本远大于收益时，新增接口跟随既有团队约定即可，不必强行插入一套不一致的风格
- 项目已采用 GraphQL 作为主要数据层，此时应遵循 GraphQL 自己的设计规范，不套用本文档
- 前端数据需求高度复杂多变（一次要聚合多个资源、字段经常变化），此时可考虑在已有 REST 接口之上包一层 GraphQL 做 BFF，而非强行把所有聚合逻辑压回 REST 端点里

### 2.3 成熟度自评模型（评估现有/第三方接口时用）
遇到"这个接口算不算RESTful"这种模糊判断时，可以用 Richardson 成熟度模型分级评估，而不是简单二元判断：
- **Level 0**：所有操作走同一个 URL，全部用 POST（最原始的 RPC 风格）
- **Level 1**：为不同资源拆分了独立的 URI，但方法仍然统一用 POST
- **Level 2**：用上了 HTTP 方法语义（GET/POST/PUT/DELETE 对应不同操作），本文档第3~5节的规范大致对应到这一级
- **Level 3**：在 Level 2 基础上加了 HATEOAS（本文档第7.2节），严格意义上的 RESTful 对应这一级

**用法**：对接第三方或评审老接口时，先判断它目前在哪个级别，再决定"要不要、值不值得推动它往上一级"，而不是笼统地说"这个接口不是RESTful"。多数工程实践停留在 Level 2 已经足够，Level 3 是可选项（参见第7.2节的采用建议）。

```text

```

## 3. URI 设计规范
- 用名词复数表示资源集合：`/users`（用户列表）、`/products`（商品列表）
- 层级关系用路径嵌套表达从属关系：`/users/123/orders`（某用户的订单列表）、`/products/456/reviews`（某商品的评论）
- **URI 中不出现动词**，动作交给 HTTP 方法表达：
  - ❌ `/getUser?id=123` → ✅ `GET /users/123`
  - ❌ `/users/delete/123` → ✅ `DELETE /users/123`
  - ❌ `/users?action=delete&id=123` → ✅ `DELETE /users/123`
- 单数 vs 复数：统一用复数形式，`/user/123` 不如 `/users/123` 规范
- 单词间的分隔符统一用中线 `-`，不用下划线或驼峰：`/children-books` 优于 `/children_books`、`/childrenBooks`，中线在 URL 里的可读性和视觉效果更好，也是大多数规范文档的共识
- 版本号前置且不要多加冗余路径段：`/v1/users` 优于 `/api/v1/users`（`api` 这个词是冗余的，如果项目已有域名/路径前缀区分了 API 服务，不需要再加一层）
- URI 一旦发布应保持稳定，不应因为后端技术栈变化而改变

### 3.1 "当前用户"资源：单数化的特例
对于"当前登录用户自己"的相关接口（获取/修改个人信息、查看自己发布的内容），身份信息已经通过认证令牌传给了后端，不需要把用户 id 拼进 URL，此时可以用单数形式表示"当前用户"这一特殊资源：
- `GET /user`：获取当前用户的个人信息
- `PUT /user`：更新当前用户的个人信息
- `GET /user/posts`：当前用户发布的内容列表（也有项目用 `/me` 代替 `/user`，两种写法均可，项目内统一即可）

这是复数化原则的一个例外，不代表破坏了规范，而是用单数明确表达"这不是资源集合里的某一项，而是通过身份令牌隐式定位的唯一资源"。

## 4. HTTP 方法的正确语义

| 方法 | 语义 | 幂等性 | 请求体 |
|---|---|---|---|
| GET | 读取资源 | 幂等 | 无 |
| POST | 创建资源 | 不幂等 | 有（新资源数据） |
| PUT | 全量替换资源 | 幂等 | 有（完整资源表述，未修改字段也要传） |
| PATCH | 部分更新资源 | 视实现而定 | 有（仅需修改的字段） |
| DELETE | 删除资源 | 幂等 | 通常无 |

常见误用对照：
- ❌ `GET /deleteUser?id=123`（用 GET 执行有副作用的操作，违反 GET 的安全性约束）
- ✅ `GET /products?category=books&page=1&limit=20`（GET 带过滤和分页参数，这是规范用法）
- ❌ 把所有操作都写成 `POST`，丢失方法本身的语义，前端也无法再依赖"GET/PUT/DELETE 可以安全重试"这条幂等性保证

**幂等性对前端的实际意义**：网络超时后，GET/PUT/DELETE 可以安全重试；POST 不能盲目重试，需要前端自己做防重复提交（禁用按钮、生成幂等键放在 Header 里传给后端去重）。

### 4.1 非标准业务操作的处理方式
严格的"资源+CRUD"模型能覆盖大部分场景，但业务里总有一些操作不完全贴合这个模型。以下是几种常见情况的处理方式，以及"什么时候可以豁免严格资源语义"的判断边界。

#### 4.1.1 同一资源按详细程度拆分端点
当同一资源在不同场景下需要返回不同粒度的数据时（如列表页只需要基础字段，详情页需要完整字段），可以拆分成两个端点，而不是用查询参数强行控制字段：
- `GET /users/1`：返回基础信息（姓名、头像等）
- `GET /users/1/detail`：返回详情页需要的完整信息（简介、关联链接等）

#### 4.1.2 用"资源路径+动作词+POST"表达无法用 PUT/PATCH 描述的状态变化
有些操作不是简单的字段更新，而是触发一个业务流程（可能连带多个副作用，如生成记录、发送通知），此时对单一资源做 PUT/PATCH 已经不够用，可以在资源路径后加一个动作端点，用 POST 调用：
- `PUT /orders/100`：更新订单本身的信息（常规字段更新）
- `POST /orders/100/postpone`：订单延期收货（这是一个业务动作，会触发状态变更和相关副作用，不是简单字段修改）

动作词是否要名词化（如 `cancellation` 而非 `cancel`）在业界存在争议，两种写法都有实践案例，项目内部统一一种写法即可，不必强求。

#### 4.1.3 全局搜索与单资源集合查找要区分
- 针对某个具体资源集合的查找，用 `GET` 带查询参数即可：`GET /books?keyword=xxx`
- 不针对任何具体资源集合的全站/全局搜索，语义上更接近"用关键词创建了一次搜索请求并拿到结果"，用 `POST /searches?keyword=xxx`（请求体通常还会带更多查询条件）

#### 4.1.4 明确的豁免边界：这些场景直接用 POST，不强行套资源模型
以下几类操作的共同特点是"需要留痕、涉及多个资源的联动变更、且不是简单的增删改查"，遇到这类场景不必纠结怎么设计成"资源化"的 URI，直接用 POST 即可：
- 转账类操作（会同时改变多个账户的余额，还要生成交易记录）：`POST /transfers`
- 需要留存历史版本的修改（如发票红冲重开，原记录保留不动，而是生成一条新记录）：`POST /invoices/1/reissue`
- 合同/协议/法律条款类需要留痕的确认操作（同意用户协议、确认租赁合同、生成电子合同）：统一用 POST

## 5. HTTP 状态码使用规范

**2xx 成功**
- `200 OK`：GET/PUT/PATCH 成功
- `201 Created`：POST 创建成功，响应头应包含 `Location` 指向新资源地址
- `202 Accepted`：请求已接受但尚未处理完成，用于异步任务场景（如提交一个报表生成请求，后端丢进队列异步处理），响应体通常带上任务状态查询地址
- `204 No Content`：请求成功但无返回内容（如 DELETE 成功）

**3xx 重定向（API 场景用得较少，但要认识）**
- `303 See Other`：POST/PUT/DELETE 操作完成后指向另一个资源地址，浏览器不会自动跳转，由前端决定下一步。区别于 302/307（用于 GET 请求的临时重定向）

**4xx 客户端错误**
- `400 Bad Request`：请求参数格式错误
- `401 Unauthorized`：未认证（令牌缺失/无效）
- `403 Forbidden`：已认证但权限不足
- `404 Not Found`：资源不存在
- `405 Method Not Allowed`：该资源不支持此 HTTP 方法（如对一个只读资源发 DELETE）
- `406 Not Acceptable`：客户端要求的响应格式服务端提供不了（如请求 `Accept: application/xml` 但服务端只支持 JSON）
- `409 Conflict`：资源冲突（如创建了已存在的唯一字段）
- `410 Gone`：资源曾存在但已被永久移除，不同于 404（未知是否存在过）
- `415 Unsupported Media Type`：请求体的 `Content-Type` 服务端无法处理
- `422 Unprocessable Entity`：请求格式正确但业务语义校验不通过
- `429 Too Many Requests`：触发限流

**5xx 服务端错误**
- `500 Internal Server Error`：未处理的服务端异常
- `503 Service Unavailable`：服务暂时不可用

**硬性要求**：禁止用 `200 OK` 包一个 `{"error": "无权限"}` 来表达失败——这类语义错误应该用对应的 4xx 状态码，让前端可以直接用 HTTP 语义判断成功/失败，而不必解析响应体才知道请求有没有成功。

## 6. 认证与授权设计

### 6.1 认证：JWT 是最常见的无状态方案
- 结构：`Header（算法声明）.Payload（用户信息）.Signature（签名）`，三段式，用 `.` 分隔
- **关键认知：Payload 只是 Base64 编码，不是加密**，任何人拿到 token 都能解码看到内容，敏感信息（密码等）不能放进 Payload
- 前端通过 `Authorization: Bearer <token>` 携带
- 令牌有效期不宜过长（业界惯例 15~30 分钟），配合 refresh token 机制做静默刷新

### 6.2 认证：第三方授权登录场景用 OAuth
- 典型场景："用 GitHub/微信账号登录"
- 核心流程：用户在授权页确认 → 应用换取访问令牌 → 用令牌调用 API
- 当前主流版本 OAuth 2.1 默认包含 PKCE（防止授权码被截获）和刷新令牌轮换机制

### 6.3 授权：两种权限判断模型
- **RBAC（基于角色）**：用户分配角色（`admin`/`editor`），角色绑定权限（`users:read`/`orders:write`），适合权限结构相对固定的场景
- **ABAC（基于属性）**：综合用户属性（部门、级别）和资源属性（创建者、敏感度）动态判断，粒度更细，适合复杂权限场景

### 6.4 安全基线
- 所有涉及认证/敏感数据的接口必须走 HTTPS
- 必须有限流机制（Rate Limiting）防止暴力请求
- 前端权限控制只是体验优化（隐藏/禁用按钮），**不能替代后端的权限校验**，关键操作必须让后端做最终判断

## 7. 请求/响应格式规范

### 7.1 统一的响应结构（团队内部约定，REST 本身不强制格式，但工程实践中建议统一）

成功响应：
```json
{
  "code": 0,
  "data": { "id": 1, "name": "示例" },
  "message": "ok"
}
```

错误响应：
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "用户输入验证失败",
    "details": [
      { "field": "email", "message": "格式无效，请输入正确的邮箱地址" }
    ]
  }
}
```

列表响应（带分页信息）：
```json
{
  "data": [ { "id": 1 }, { "id": 2 } ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "totalItems": 42,
    "totalPages": 5
  }
}
```

前端封装请求层时应基于这个统一结构做错误处理，而不是每个接口单独解析错误格式。

### 7.2 HATEOAS（可选，按项目需要采用）
严格 REST 建议响应体里带上相关资源的操作链接，让客户端能"顺着链接导航"，不用自己拼接/硬编码 URI 规则。两种常见写法：

**写法A：简单的 `_links` 键值对**（适合链接关系单一的场景）
```json
{
  "id": "123",
  "name": "示例",
  "_links": {
    "self": "/v1/users/123",
    "roles": "/v1/users/123/roles"
  }
}
```
分页场景可以在 `pagination` 里加 `_links.next`/`_links.prev` 指向上下页地址，前端翻页时直接用链接而不用自己拼接查询参数。

**写法B：`links` 数组，每条包含关系名/方法/地址**（更贴近工程实践，能表达同一资源的多种可操作动作，GitHub API 采用类似模式）
```json
{
  "status": "In progress",
  "links": [
    { "rel": "cancel", "method": "delete", "href": "/api/status/1000" },
    { "rel": "edit", "method": "put", "href": "/api/status/1000" }
  ]
}
```
写法B 比写法A 表达能力更强，能同时说明"这个链接对应哪个操作、用什么方法调用"，适合一个资源有多个可执行动作的场景（如订单可以取消、可以编辑）。项目内选定一种写法后统一使用，不要混用。

**是否采用**：多数团队不强制做到这一步，"资源化 URI + 合理方法语义 + 统一响应格式"这三条做到，已能满足大部分工程需求。数据关系复杂、需要减少文档维护成本的项目可以考虑采用。

## 8. 复杂查询设计规范

### 8.1 过滤
- 简单过滤：`/products?category=electronics`
- 范围过滤：`/products?price[gte]=100&price[lte]=500`（价格在100到500之间）

### 8.2 排序
- 单字段：`/users?sort=createdAt`（默认升序）或 `/users?sort=-createdAt`（降序，减号前缀）
- 多字段：`/users?sort=createdAt:desc&sort=name:asc`（具体语法按项目约定，两种写法选一种统一用）
- **建议**：如非必要，排序逻辑优先放在客户端做（前端拿到数据后自己排），而不是每次排序都发请求让服务端处理，这样能减轻服务端压力，尤其是数据量不大、已经整页拿到手的场景

### 8.3 字段投影（减少不必要的数据传输）
`/users?fields=id,name,email`：只返回指定字段，适合列表页只需要展示部分信息的场景。

### 8.4 分页：两种模式的选择
- **Offset 分页**（`page=2&limit=10`）：实现简单，支持"跳到第N页"，但数据量大或频繁增删时会有性能问题和页码错位风险
- **Cursor 分页**（`cursor=<编码后的定位标识>&limit=10`）：用上一页最后一条记录的标识作为游标定位，性能稳定，适合无限滚动、大数据量场景，但不支持跳页

**选择依据**：常规的管理后台列表用 Offset 分页足够；社交媒体时间线、无限滚动的商品流优先用 Cursor 分页。

## 9. API 版本管理

| 方式 | 示例 | 优势 | 劣势 |
|---|---|---|---|
| URI 路径版本 | `/v1/users` → `/v2/users` | 简单直观，易调试 | 版本多了 URI 会膨胀 |
| Header 内容协商 | `Accept: application/vnd.company.v1+json` | URI 保持干净，同一 URI 多版本共存 | 不直观，客户端实现稍复杂 |
| 查询参数版本 | `/users?version=1` | — | 不推荐，容易被缓存忽略，违反 URI 设计原则 |

**建议**：优先选 URI 路径版本或 Header 版本，不用查询参数做版本。字段废弃前应提前预告，可在响应头加 `X-Deprecated: true` 提示客户端该接口/字段即将废弃。

### 9.1 旧接口迁移与契约对账

项目从旧路径、旧响应结构或 Mock 接口迁移到版本化接口时，不得只改前端请求地址。必须同时建立：

- 旧接口 → 新接口的映射清单；
- 请求字段、响应字段、错误码和鉴权方式的差异说明；
- 兼容期、下线日期和调用方迁移状态；
- 数据库迁移脚本、回滚方式和测试环境验证记录；
- Mock Provider、测试 Provider、真实 Provider 的切换条件。

若项目当前存在 `/api/...` 与 `/api/v1/...` 两套入口，应在 Spec/接口契约中声明哪一套是当前事实源，另一套是兼容层还是待废弃接口。未经对账，不得仅凭“前端已经能请求成功”认定接口迁移完成。

## 10. 常见的"伪 RESTful"反模式（评审接口设计时可用这份清单）
- 所有操作都用 `POST`，URI 里塞满动词（`/createOrder`、`/updateUser`）
- 用 `200 OK` 状态码但响应体里自定义一套 `code` 表示失败，前端无法用 HTTP 语义直接判断成功/失败
- 删除操作返回的不是 `204`/`200`，而是把整个已删除的资源又原样返回一遍
- 分页/排序参数每个接口风格不一致（有的叫 `page`，有的叫 `pageNum`；有的用 `sort=-field`，有的用 `sort=field:desc`）
- 用查询参数表达操作意图（`?action=delete&id=123`），而不是用对应的 HTTP 方法

## 11. 接口测试用例设计清单
本节回答"接口设计好之后该怎么测"，是 `TEST-METHODOLOGY.md` 通用方法论（等价类/边界值）在接口场景下的具体落地，写接口测试用例时按以下几类逐一过一遍，而不是只测"传对参数、拿到期望结果"这一条路径。

### 11.1 参数校验类
- **必填校验**：每个必填字段分别留空/不传，确认接口拒绝而不是用默认值悄悄放过
- **类型校验**：传入错误类型（如数字字段传字符串、字符串字段传对象），确认接口返回 `400`，不是服务端直接抛未处理异常
- **长度/范围边界**：对照 `TEST-METHODOLOGY.md` 第2.2节边界值分析，测最小值、最大值、超出边界一点

### 11.2 认证与授权类
- **未携带认证信息**访问需要登录的接口，应返回 `401`
- **携带过期/无效 token**访问，应返回 `401`，不是当作正常请求处理
- **水平越权**：用A用户的token访问B用户的资源，应被拒绝（对照 `安全测试选型与规范.md` 第3.1节）
- **垂直越权**：普通用户token访问管理端专属接口，应返回 `403`

### 11.3 业务逻辑类
- **正常路径**：符合业务规则的输入，返回符合 Spec 描述的结果
- **状态冲突**：对已处于某状态的资源做不允许的操作（如对已支付订单再次发起支付），应返回 `409` 或明确的业务错误码，不是静默成功或报未知错误
- **幂等性验证**（对照第4节）：GET/PUT/DELETE 同一请求重复发送，结果应保持一致；POST 若设计了幂等键，重复提交应被识别为同一次操作

### 11.4 响应结构类
- 成功响应的字段结构、类型与 Spec 第3节数据结构定义一致，不多返回敏感字段（如密码哈希、内部ID），不少返回业务必需字段
- 错误响应符合项目已声明的统一错误结构；若项目使用 `code` 字段，则不同错误场景的 `code` 值应稳定（同样的错误原因应该稳定返回同样的错误码，不是随机变化）

## 12. 验收关联
若某 REQ 声明启用本 Capability，验收时额外检查：
- [ ] URI 使用名词复数，不含动词
- [ ] HTTP 方法语义正确使用（GET 无副作用，POST 创建，PUT/PATCH 更新，DELETE 删除）
- [ ] 响应状态码符合本文档第5节的分类，未出现"200包错误"的反模式
- [ ] 错误响应符合项目已声明的统一错误结构（如项目采用 `code`/`message`/`details`，则三者应稳定一致）
- [ ] 支持分页/过滤/排序的接口，参数命名在项目内保持一致
- [ ] 涉及认证的接口，敏感信息未出现在 JWT Payload 里
- [ ] 涉及权限的接口，前端权限判断不是唯一防线，关键操作后端有二次校验
- [ ] 未出现第10节列出的任一反模式
- [ ] 若该接口对应的 REQ 声明需要接口测试覆盖，已按第11节清单逐类检查，不是只测了正常路径

若声明"沿用现有接口风格"或"不适用"：本 Capability 的 REST 专项检查跳过，但仍应依据项目既有接口契约完成接口一致性验收。
