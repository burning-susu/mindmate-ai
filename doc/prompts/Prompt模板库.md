<a name="prompt-page" id="prompt-page"></a>

### 页面模板

> 适用场景：新建一个页面/功能模块的常规开发任务。写之前先确认对应 REQ 的 `spec.md` 是否已经定稿——本模板假设 Spec 已存在，不是用来代替 Spec 讨论的。

```text
【Goal】
根据 {{页面名称}} 和 {{功能描述}} 完成页面开发，对应需求 {{REQ编号}}。

【Constraints】
1. 严格以 {{REQ-XXX.spec.md 路径}} 为唯一事实源，不擅自扩大或缩小范围
2. 使用项目现有技术栈，不新增第三方依赖（如确需新增，先说明理由等我确认）
3. 不修改本次任务无关的文件
4. 命名、注释、可维护性遵循 `docs/00-治理/CODE-STANDARDS.md`（全局强制，不需要额外声明）
5. 类型定义完整，TS 不使用 any（关键数据结构需要 interface/type）
6. 组件保持单一职责：能用一句不含"并且/然后"的话说清楚这个组件在做什么
7. {{若 Spec 第0节声明了 CSS 技术方案/响应式清单/接口规范等，把对应约束条目复制到这里，不要遗漏}}

【Context】
项目目录：{{目录}}
关联 Spec：{{spec.md 路径}}
相关文件：{{已有的可复用组件/工具函数路径，避免重复实现}}

【Acceptance-criteria】
1. 页面可运行，功能符合 Spec 第1/2节的范围边界
2. Spec 第5节"异常处理"里列出的每一种异常场景都已处理，不是只测正常路径
3. 无明显控制台报错/警告
4. {{若 Spec 声明了自动化测试/响应式/性能/安全测试范围，逐条列出对应验收项}}

【Output-Format】
先列改动文件清单，再给完整代码，再给验证步骤；输出末尾主动自检是否有违反 CODE-STANDARDS 的地方（如魔法数字、重复代码未提取），有风险点主动标注。
```

<a name="prompt-bug-fix" id="prompt-bug-fix"></a>

### Bug 修复模板

> 适用场景：修复一个已确认的报错/异常行为。核心原则：只修复当前问题，不借机重构无关代码——这是 `AGENTS.md` 第6节红线里"不允许擅自重构正常代码"的具体落地。

```text
【Goal】
修复 {{报错现象}}，对应需求 {{REQ编号，如有}}。

【Constraints】
1. 只修复当前问题，不做无关重构，不顺手"优化"报错范围之外的代码
2. 先定位根因再动手改，不要看到报错就试探性改动
3. 如果根因涉及需求理解偏差（不是纯代码bug），先和我确认 Spec 里的业务规则，不要自行改业务逻辑
4. 修复后补一条对应的测试用例（对照 `docs/00-治理/TEST-METHODOLOGY.md` 第4节，防止同一个问题再犯——这是回归测试的核心价值）
5. 若该 REQ 声明了自动化测试范围，修复后需要在 `bugs-backlog.md` 补记这条 Bug（严重程度、根因、修复状态按该文档字段规范填写）

【Context】
报错日志/现象：{{日志或复现步骤}}
关联文件：{{怀疑涉及的文件路径}}
关联 REQ 的 Spec：{{路径，如有}}

【Acceptance-criteria】
1. 问题消失，原有功能保持正常，未引入新报错
2. 已补充对应的回归测试用例（或人工测试用例，视该 REQ 声明的测试范围）
3. 是否为同类问题的普遍模式（如同一段逻辑在别处也有同样的坑），如是需要一并说明，但不擅自扩大修复范围

【Output-Format】
先说根因（不是"改了哪里"，是"为什么会这样"），再给修改点，再给验证方式，最后说明是否需要补充测试用例。
```

<a name="prompt-spec" id="prompt-spec"></a>

### Spec 模板

> 适用场景：把一段需求描述转成规范的 Spec 文档。生成后应落到 `docs/01-需求模板/REQ-XXX-功能名/REQ-XXX.spec.md`，不是聊天里临时用完就丢。

```text
【Goal】
请基于下面的需求描述，生成一份符合 `docs/01-需求模板/REQ-TEMPLATE/REQ-TEMPLATE.spec.md` 结构的 Spec 文档。

【Constraints】
1. 必须包含第0节"适用范围声明"——是否涉及UI、是否需要响应式清单/CSS技术方案/接口设计规范/自动化测试/性能测试/安全测试，每一项都要给出判断依据，不能全部留空或全部照抄默认值
2. 若判断需要某项（如CSS用Tailwind、接口用RESTful），需要引用对应的 `04-设计资源/` 判断依据文档，不能凭感觉下结论
3. 范围边界要明确写"不实现"的部分，不能只写"需要实现"
4. 异常处理要覆盖空值/边界值/非法输入/依赖失败等场景，参照 `docs/00-治理/TEST-METHODOLOGY.md` 第2节的等价类划分方法把场景想全，不要只写一两条应付

【Context】
需求描述：{{原始需求}}
{{如有参考的类似 REQ，给出路径}}

【Acceptance-criteria】
生成的 Spec 包含：第0节适用范围声明、功能目标、范围边界、数据结构、业务规则、异常处理、验收标准，共7节，缺一不可。

【Output-Format】
先给完整 Spec 文档内容，再说明第0节里每一项判断的理由（尤其是声明"不适用"的项，要说明为什么不适用，不是不假思索地全填否）。
```

### 响应式与浏览器兼容开发模板

> 适用场景：开发一个需要适配不同设备、多浏览器兼容的 UI 组件/页面。仅在对应 REQ 的 `spec.md` 第0节声明"需要执行响应式与浏览器兼容清单"为"是"或"部分执行"时使用；纯后端/接口任务不适用本模板。

```text
【Goal】
{{开发目标，如：新增XX页面/组件}}

【Constraints】
1. 布局使用相对单位（%、rem、flex、grid），禁止固定 px 写死容器宽度
2. 断点：移动端<768px，平板768-1024px，桌面>1024px
3. 颜色只使用 {{项目选定的配色方案名称}} 里的 token，禁止手写规范外色值
4. 不引入未做兼容处理的实验性 CSS/JS 特性
5. {{若 Spec 已声明 CSS技术方案为 Tailwind：遵循 docs/04-设计资源/CSS方案选型与Tailwind规范.md，如禁止任意值语法、断点需覆盖默认配置 / 若声明其他方案：删除本条}}
6. {{其他项目专属约束}}

【Context】
项目背景：{{项目背景}}
目标浏览器：{{Chromium系（默认） / 需额外覆盖Firefox（须说明理由，如信创终端） / 其他}}
相关文件：{{相关文件}}
参考规范：docs/04-设计资源/响应式与浏览器兼容清单.md

【Acceptance-criteria】
1. 移动端和桌面端断点下布局均正常，无溢出/错位
2. Chromium 系浏览器打开验证一次，布局/交互/控制台均正常（{{仅当Context声明需要Firefox时，才追加Firefox验证}}）
3. 控制台无报错
4. 人工目视确认视觉效果符合预期（间距、层次、配色统一）

【Output-Format】
先列改动文件清单，再给实现说明，再列出已在哪些浏览器/尺寸下验证过，最后主动自检适配/审美/兼容/代码优化四项是否达标，有风险点主动标注。
```

<a name="prompt-session-default" id="prompt-session-default"></a>

### 会话级默认约束模板（兼容性+审美+代码优化，一次性贴在会话开头）

> 适用场景：**仅当**对应 REQ 的 `spec.md` 第0节声明"需要执行响应式与浏览器兼容清单"为"是"或"部分执行"时才使用。与上面的"响应式与浏览器兼容开发模板"不同：那个是针对单次具体任务的5要素模板，这个是新开一个会话时一次性贴上、覆盖整个会话周期的兜底约束，适合连续开发多个页面/组件时减少重复输入。纯后端/接口项目、已声明"否"的 REQ 不要用。

```text
# 开发硬性约束-兼容性与视觉规范

## 1、多设备适配要求
开发完成的页面必须保证在不同尺寸、不同型号设备上布局稳定，无元素错位、溢出、遮挡、文字截断问题；
Web项目保证不同分辨率、大屏/小屏自适应正常（断点：移动端<768px，平板768-1024px，桌面>1024px）；
所有布局禁止写死固定 px 宽高，优先使用相对单位（%、rem、flex、grid）。
（若为小程序项目，本条不适用，改用 rpx 自适应单位，见 docs/04-设计资源/设计稿转代码流程.md 第6节）

## 2、视觉审美规范
颜色只使用项目已选定的配色方案 token，不得手写规范外色值；
间距、圆角、字号统一协调，视觉层级清晰，主次分明；
严格遵循项目已有的设计稿、Design Token、配色规范，不得私自修改视觉风格。

## 3、浏览器兼容性要求（Web端）
**默认只保障 Chromium 系浏览器（Chrome/Edge/百度/360/QQ 等同内核），不做 Firefox 测试与兼容处理**，除非 Spec 明确声明需要（判断依据见 `docs/04-设计资源/响应式与浏览器兼容清单.md` 第 3.0 节）：
- 避免使用未做兼容处理的实验性 CSS/JS 新特性，必要时用 autoprefixer 统一处理前缀。这条**不因不测 Firefox 而放宽**——它是静态代码检查，改一次永久生效，不产生重复成本；
- 开发完成后在 Chromium 系浏览器打开自查一次，确认布局、动画、交互正常，无样式错乱、功能失效；
- 移动端视口至少验证一档，重点是触屏下导航菜单能否展开这类**功能性失效**，优先级高于纯样式差异。

## 4、代码优化要求
- 结构清晰，组件合理拆分；
- 清理冗余代码、重复样式、无用变量；
- 样式复用，避免大量重复硬编码；
- 遵循项目现有编码规范。

请在输出每一段代码后，主动自检以上4项是否达标；如有兼容风险点，主动标注并说明降级方案。
```

### 网站内容修改与排版模板（改版场景）

> 来源：一次真实门户网站项目复盘沉淀，原文件见 `04-设计资源/无设计稿双参考异源模式-实操SOP.md` 关联素材。适用场景：网站已存在，只是要改内容/排版，不是从零搭建。

```text
一、背景
【一句话说明现状】公司/团队已有一版【网站类型】，但存在以下问题：
- 【问题1，如：页面结构杂乱、层次不清晰】
- 【问题2，如：文字内容偏简单，信息密度不够】
【说明信息来源】相关资料【已整理成文档提供 / 需要AI自行从现有网站提取 / 尚未整理】

二、本次任务范围
- 重点改动对象：【列出具体页面清单】
- 不改动但可引用的材料：【说明哪些资料不直接改，但可作为佐证】
- 明确排除的范围：【避免AI擅自扩大范围，如：本次不改导航栏/不改配色体系】

三、网站/页面的核心目的
（按优先级列1-3条，后续所有结构决策都要服务于这些目标）
目标受众：【谁会看这个页面】

四、硬性要求（必须包含，不能缺）
每个【页面类型】至少要包含以下板块：【板块清单】

五、内容深度扩展要求
内容至少覆盖：【概述/技术路径/解决的痛点/优势亮点/与其他产品的联动/可选维度】

六、应用场景/案例的横向扩展（如任务涉及）
基于产品能力边界推演潜在场景，AI先给候选方向，双方一起筛选，不能编造不实用例。

七、结构与排版设计要求
- 是否要沿用现有CSS/组件库/设计规范文件（写明路径）
- 已有交互功能改动前需要确认绑定的类名/脚本，避免误改导致功能丢失
- 图片/图标素材的来源和使用规范

八、素材来源与内容合规处理原则
- 素材优先级冲突时以【指定来源】为准
- 敏感内容只做识别标注，不做泛化改写后直接使用
```

```text
1. 分引擎按影响大小排序执行，不要平铺成一个大清单：

   G2 结构化数据：Organization / Product / BreadcrumbList
   G3 图片体积：先量化 WebP 收益再决定做不做，30% 以上才值得动那么多文件引用
   G4 Twitter Card；404 页加 noindex,follow
   【共用】
   C0 sitemap 补 lastmod 并自动排除 noindex 页面、canonical 与 URL 规范化

4. title/keywords 写用户真会搜的词，不是内部产品代号

6. 改前先备份全部HTML和CSS（静态站往往无版本控制）
7. {{如涉敏感行业，声明：做SEO会主动把内容推向公开索引，
   需先逐页确认哪些适合进索引，不适合的加 noindex}}

【Context】
{{网站根目录路径}}
{{站点域名}}

【Acceptance-criteria】
```

<a name="prompt-local-access" id="prompt-local-access"></a>

### 本地网站对外访问模板（同局域网 / 跨局域网）

> 来源：真实项目里的高频句式——本地静态网站开发到一定阶段，需要让别人（甲方/同事）临时访问预览效果，不需要正式部署上线。两种子场景本质都是"让别人方便访问"，但适用范围不同，第0步先判断走哪条：
> 
> - **对方和你在同一个局域网/同一个 WiFi 下**（比如同办公室、同一个路由器）→ 走"3a 同局域网访问"，不需要装任何额外工具，直接用本机 IP + 端口
> - **对方不在同一个局域网**（比如甲方在外地、要发一个能直接点开的链接）→ 走"3b 跨局域网访问（内网穿透）"，需要 cloudflared
>   判断错场景是最常见的踩坑：局域网内的场景硬套内网穿透，多装了一个工具还多一层依赖；跨局域网的场景给一个局域网 IP，对方永远打不开。

#### 3a. 同局域网访问（本机 IP + 端口，无需额外工具）

```text
【Goal】
给当前网站起一个本地 HTTP 服务，让同一局域网（同 WiFi/同路由器）下的其他设备可以直接访问。

【Constraints】
1. 先确认网站目录下有没有需要构建的框架（React/Vue等），有构建步骤的先确认是否已构建出静态产物，直接用 `python -m http.server` 起的是**纯静态文件服务**，不会跑构建/热更新；无构建步骤的纯 HTML/CSS/JS 项目可以直接起
2. 用 `cd "{{网站目录}}" && python -m http.server {{端口，默认8000}}` 启动服务，端口如被占用需换一个并告知用户
3. 必须查出本机在当前局域网下的实际 IPv4 地址（Windows 用 `ipconfig` 找"IPv4 地址"，不要用 `127.0.0.1`/`localhost`，那两个只能本机自己访问），拼成 `http://{{本机局域网IP}}:{{端口}}` 才是能给别人访问的地址
4. 如果对方连不上，提醒两个最常见原因：(a) 系统防火墙拦截了该端口的入站连接，需要放行或临时允许 Python 通过防火墙；(b) 对方设备确实没有连在同一个局域网/WiFi 下
5. 这个地址只在本机这次服务进程运行期间有效，且只在同一局域网内可访问，不能给局域网外的人用（那是下面3b的场景），也不需要考虑内网穿透
6. 说明如何停止服务（前台运行的话 Ctrl+C；后台运行需要给出对应的终止方式）

【Context】
网站目录：{{绝对路径}}
是否有构建步骤：{{有/没有，有的话构建产物目录是哪个}}

【Acceptance-criteria】
1. 拿到形如 `http://192.168.x.x:8000` 的地址（不是 localhost/127.0.0.1）
2. 同局域网内的另一台设备（手机/其他电脑连同一 WiFi）能正常打开，内容和本机一致
3. 已告知用户如何停止服务

【Output-Format】
先给出识别到的本机局域网IP和使用的端口，再给出实际执行的命令，再给出拼好的访问地址，最后说明如果对方打不开该怎么排查（防火墙/是否同网）、如何停止服务。
```

#### 3b. 跨局域网访问（内网穿透）

> 适用场景：本地开发环境（如本机用 `python -m http.server`、`live-server`、`vite` 等起的本地服务）需要临时对外暴露给不在同一局域网的人；不适用于长期稳定对外提供服务（内网穿透生成的地址通常是临时的，进程结束或重启后会变化，正式上线应走正式部署流程，不要用本模板代替）。

```text
【Goal】
用 cloudflared 内网穿透工具，给当前网站生成一个网址供他人跨局域网访问。

【Constraints】
1. 先确认本机是否已安装 cloudflared；未安装则给出对应操作系统的安装方式（Windows/macOS/Linux 分别说明），装完成功后再继续
2. 先确认当前网站本地服务是否已在运行（哪个端口），没有运行的话先起本地服务，再对该端口做穿透，不要凭空猜测端口号
3. 使用免登录的快速隧道方式（`cloudflared tunnel --url http://localhost:{{端口}}`），不需要用户提供 Cloudflare 账号/域名，除非用户明确要求绑定自己的域名
4. 生成的地址是临时地址，进程关闭或重启后会失效并换新地址，需要明确告知用户这一点，不要让用户误以为是永久地址
5. 此地址会让当前局域网内的静态网站内容对公网可访问，如果网站内容涉及未发布的内容或敏感信息，需要提前提醒用户注意，不要默认可以公开
6. 命令在后台长期运行时，需要说明如何停止该隧道进程，不要让用户不知道怎么关掉

【Context】
项目本地服务地址/端口：{{如 http://localhost:5500，未知则先探测}}
操作系统：{{Windows / macOS / Linux}}

【Acceptance-criteria】
1. 成功拿到一个 `https://xxx.trycloudflare.com` 形式的公网地址
2. 该地址在其他设备/跨局域网环境下可以正常打开，页面内容和本地一致
3. 已告知用户该地址的临时性，以及如何停止隧道

【Output-Format】
先给安装/环境确认结果，再给出实际执行的命令，再给出生成的访问地址，最后说明如何停止隧道进程、地址会在什么情况下失效。
```

### 已有项目复盘反哺手册模板（双路：未用过手册 / 用过手册）

> 来源：军事门户网站项目的复盘请求（`桌面/【背景】.txt`），并吸收了同一需求下另一份计划方案（`桌面/codex计划方案.txt`）里的"先流程建模、再反向校验"思路。
> 适用场景：手上有一个**已经做完或做到一定阶段**的项目，想拿它来完善手册（SOP、Prompt 模板、习惯画像、反思日志），同时反向得出该项目自身的待补清单。
> 
> **先判断走哪条路，两条路不是同一模板换参数，产出和约束都不同：**
> 
> |       | 路A：项目**未**用过手册        | 路B：项目**用过**手册            |
> | ----- | --------------------- | ------------------------ |
> | 手册的角色 | **被检验对象**（可行性未经验证）    | **已生效标准**（执行依据）          |
> | 核心问题  | 手册**缺**什么             | 手册哪条规则在真实执行中**不成立**      |
> | 主要动作  | 从真实过程反推流程骨架 → 比对手册找空白 | 声明值 vs 实际执行逐项对账 → 找失效规则  |
> | 典型产出  | 缺口清单、新增章节、工作流 SOP     | 符合性报告、规则修订、废弃条目          |
> | 最大风险  | 把项目的偶然做法当成通用规范写进手册    | 只查"有没有做"，不查"这条规则本身是否值得做" |
> 
> 两条路的**共通部分**（第 4~6 项约束、5要素提取、返工反思、习惯提取）在两个模板里表述一致，可直接复用。

#### 路A：项目未使用过手册（反向验证 + 补齐缺口）

```text

1. 补齐手册里缺失的流程环节（如{{列出你已知的缺口，如测试、性能调优、主题色、浏览器兼容、

【Acceptance-criteria】
```

#### 路B：项目已使用过手册（符合性对账 + 规则修订）

```text
【Goal】
我有一个**全程按"开发手册"做的**{{项目类型}}项目，现在要复盘。
目的按优先级排：
1. 符合性对账：Spec 第0节的声明值与实际执行是否一致，不一致的说明原因
2. 找出手册里**实际执行不下去或执行了没价值**的规则——这类问题只有真正用过才暴露得出来，
   比"手册缺什么"更难发现，是本次的核心价值
3. 补齐执行中发现的手册空白
4. 历史提示词过"5要素Prompt工具"提取可复用模板；分析返工根因；提取编程习惯

【Constraints】
1. **不要只查"有没有做"，要查"这条规则是否值得做"**。三类要分开：
   - 该做且做了 → 确认有效，记为已验证规则
   - 该做但没做 → 查原因：忘了？做不到？还是当时判断不必要？
   - 做了但没价值 → **这类最重要**，说明规则本身要修订或降级为可选
2. **以 Spec 第0节的适用范围声明为对账基准**。声明"否/部分执行"的项，不算违规，
   但要检查当初的声明依据是否成立——事后看，该声明是否判断错了
3. 手册规则与实际冲突时，**默认怀疑规则而不是怀疑执行**。手册是我事后总结的产物，
   本身未经充分验证；但也不要因为一次执行不便就删规则，要区分"规则错"和"这次场景特殊"
4. 不要读原始素材。基于项目文档（spec/progress-log/acceptance/changelog）与提示词记录分析，
   需要细节时向我提问
5. 产出落到具体文件与章节，不停在泛泛结论

【Acceptance-criteria】

2. **手册规则修订清单**——分三类给出：
   - 已验证有效（可提升为硬性要求）
   - 需修订（给出具体改法与依据）
   - 建议降级为可选或废弃（说明为什么在真实场景里没价值）
```

#### 两条路都要注意的三件事

1. **"先给计划再动手"不是客套**。这类任务的返工成本极高——一旦基于错误前提写了几千字手册修改，
   推翻的代价远大于先花一轮对齐。历史上就出现过误判时序前提（以为手册指导了项目，实际手册是事后写的）
   导致整个方案作废的情况。
2. **反向审查项目待补清单时，不要把"手册有这条"直接等同于"项目必须补"**。手册的适用范围声明机制
   本身就允许声明"否"。正确做法是：列出项目未覆盖项 → 逐项判断是该补还是该在 Spec 里补一条声明。
3. **提取模板时"重复次数"是硬依据**。只出现一次的指令再漂亮也不建模板，否则模板库会膨胀成
   一次性语句仓库，反而让人找不到真正高频的那几个。
