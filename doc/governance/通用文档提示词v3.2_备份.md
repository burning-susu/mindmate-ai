# 通用文档提示词 v3.2

## 文档信息

- 版本：v3.2.1
- 大版本：v3.2
- 状态：Draft
- 用途：在任意新项目或已有项目中建立从项目画像、治理评估、定制化流程路由、资料投放、PRD、技术设计、可选 UI 约束到开发交付的文档驱动流程
- 继承关系：完整继承既有 v3.1 治理能力，并在其基础上增加项目画像、治理评估、Capability 激活、Workflow Blueprint、Stage Contract、Runtime Context、Evidence 和 Workflow Rebase
- 使用边界：这是通用模板；项目名称、技术栈、负责人、时间、业务规则和视觉结论未确认时必须保留为 `TBD`

## 文档迭代说明

### v3.2.1

- 新增“受控文档提前产出”原则：阶段 Gate 继续控制批准、基线和执行，但不再机械阻止基于足够证据生成 `Draft`。提前 Draft 不改变 `PROJECT_STAGE`，未知项必须标记 `TBD / Assumption / Proposed`。
- G6 允许在 PRD 尚未 Approved、但需求与项目事实已足以形成有意义架构分析时提前生成工作 Draft；总体架构要升级为 Approved/Baselined、或进入依赖该结论的实施门禁前，仍必须满足正式阶段条件。
- 新增结构化 `TECH_DECISION`（编号 `TECH-DEC-XXX`，避免与现有 `TD-XXX` 技术设计冲突）：技术领域 → 项目约束 → 候选 → 单项分析 → 兼容性 → 组合方案 → 比较 → 推荐 → 待确认 → 状态。
- 技术候选数量不再固定为 2～3 个；TECH_DECISION 必须覆盖实质可行候选和有意义的组合方案，推荐可以是单项、`A+B`、主辅组合或分层方案。
- 技术栈总览必须由 TECH_DECISION/ADR 汇总形成，不得先凭经验给出总栈再倒推理由。
- 明确 TECH_DECISION 与 ADR 边界：TECH_DECISION 保留候选、组合和取舍分析；已确认且形成长期架构约束的结论再写入 ADR。
- 上游需求或约束变化时，对受影响 TECH_DECISION 执行 `KEEP / REVALIDATE / INVALIDATE / ADD / REMOVE`，不无差别推倒重写架构 Draft。

### v3.2.0

- 保持 G0～G11 生命周期阶段、原有阶段语义和既有治理机制，不新增 G 阶段。
- 增加 `PROJECT_PROFILE`：在执行项目定制化流程前，统一记录项目类型、场景、生命周期、规模、业务、风险、技术、UI 和交付画像。
- 增加 `ASSESSMENT`：不使用单一总分决定流程，而是按规模、风险、生命周期、平台、业务和交付等维度识别复杂性，并产生可解释的 Trigger。
- 增加 `CAPABILITY ACTIVATION`：把小程序、UI 实现、自动化测试、安全、性能等专项 SOP 归入可按项目触发的 Capability；Capability 分为 `REQUIRED/CONDITIONAL/OPTIONAL/DISABLED`。
- 增加 `WORKFLOW_BLUEPRINT`：在统一 G0～G11 骨架上，根据 Scenario、Profile、Assessment、Capability 和 Stage Policy 生成本项目当前执行蓝图；项目定制化不再通过复制多套流程实现。
- 增加 `STAGE_CONTRACT`：每个阶段明确目的、进入条件、必读输入、允许动作、禁止动作、输出、证据、退出条件和回滚/恢复要求。
- 增加 `RUNTIME_CONTEXT`：每次执行任务前计算当前 Workflow、Stage、Capability、Rule、Baseline、允许动作和写入权限，避免 AI 读取全部规则后自行猜测当前适用范围。
- 增加 `EVIDENCE_MODEL`：将“完成”与“有证据证明完成”分开，工作日志、测试、验收、Git、发布记录等作为证据来源统一登记。
- 强化 `TRACE_MATRIX`：继续作为关系追踪真源，明确与 Evidence 的分工：TRACE 记录关系，Evidence 记录证明。
- 增加 `WORKFLOW_CHANGE / REBASE`：项目中途画像或风险变化时，流程通过受控变更和 Rebase 升级，不允许 AI 静默切换流程或推倒重来。
- 增加 Workflow 生成后的用户确认门禁：会改变必经阶段、强制能力、生产门禁或写入权限的流程差异按高影响决策处理。
- 保持 `INFORMED_DECISION_PROTOCOL`、CR/ADR/UI-DEC、变更稿、UI 分层规范、开发批次、进度和交接语义不变。

## 提示词使用说明

下面的“主提示词”用于新项目第一次建立文档体系，或用于已有项目补建完整文档治理体系。

使用方法：

1. 复制“主提示词”完整内容发送给 AI，不要只复制其中一小段。
2. 首次使用时，只填写已经确定的项目变量；未知变量保留 `TBD`。
3. 项目还未确定时，保持 `PROJECT_STAGE=BOOTSTRAP`，AI 只能创建目录、规则和模板。
4. 业务资料投放期间不要要求 AI 提前生成最终 PRD。
5. PRD Approved 后只生成 UI 逻辑范围；正式应用目录在技术架构和 `PROJECT_STRUCTURE.md` 确认后生成。
6. 不启用 UI 规范时，项目仍可继续生成技术设计和开发批次。
7. 若启用 UI 规范，只有 `Approved/Baselined` 的 `UI_SPEC.md` 才能进入正式开发约束。
8. UI 原始素材不能直接替代 PRD，也不能直接作为正式开发规则。
9. 完整的阶段口令和不同场景操作方式见《通用文档提示词v3.2完整使用说明.md》。
10. G6/G7 默认保留强制参与和决策确认机制；但 G6 Draft 可按受控提前产出原则在未决项明确标记时先行形成。只有把 Proposed 升级为正式结论、完成阶段出口或进入依赖该结论的实现时，才强制满足对应确认/应用门禁。
11. 所有需要用户回答、选择、裁决或批准的提示词均必须遵循 `INFORMED_DECISION_PROTOCOL`；**只在会话窗口用正文提问**，禁止弹框/问卷卡。会话中的初次选择只表示候选意向，不等于最终确认。
12. 每个开发批次结束时，若有已确认的逐条业务改动尚未写入 PRD，必须先起草 CR 并收入 PRD，再开始下一批次；细则见《通用文档提示词v3.2完整使用说明.md》第 36A 节。
13. 需要和同事错开改正式文档时，使用变更稿：先第 39A 节铺路（每文档根目录一次），再第 39B 节写入临时袋，再第 39C 节纳入。一人做到底可不用。G0 不生成说明书全文。

- 高保真页面的视觉验收和回归要求
- 可选变更稿：临时袋不入库，纳入时走原有需求变更流程（使用说明第 39A～39C 节）

上述流程中凡需要用户作出选择、裁决、批准或状态授权，均插入
`INFORMED_REVIEW → INFORMED_CONFIRMATION → DECISION_APPLY`，
不得把第一次回答直接当作已确认结论。

核心原则：

1. 所有正式结论必须有来源。
2. 已确认、现状、候选、推断和待确认必须分开。
3. PRD 与技术实现必须分层。
4. PRD 是业务目标、规则、流程和验收的唯一真源。
5. API、数据、工程规范和 UI 规范分别使用各自唯一真源。
6. UI 规范只能约束视觉、布局、组件和交互表现，不能改变业务规则。
7. 每项需求必须可追溯到来源、决策、设计、批次和测试。
8. 未经用户明确批准不得跨越阶段门槛。
9. 未知信息使用 TBD，不得虚构。
10. 代码完成不等于功能完成，验收通过才算正式交付。
11. 项目进度必须有文档、Git、测试或验收证据。
12. 人员交接必须支持下一位开发者从准确断点继续。
13. 不得记录密码、Token、私钥或生产凭证。
14. 任何业务、技术、UI、交付或治理决策存在选择时，必须遵循知情决策协议；用户确认前保持 `TBD`，不得把推荐方案包装成已批准结论。
15. 单条“生成架构”或“生成模块边界”口令不能自动覆盖参与模式和决策状态门禁。
16. 高影响决策每轮只处理 1 项；低影响决策每轮最多 2 项，不得用短选项列表替代必要解释。
17. 用户第一次选择后必须先复述其选择、限制条件、被拒方案和影响；完成二次确认后才允许受控写入。
18. 用户表示不理解、要求继续解释、取消、跳过、暂停或未明确确认时，不得记录决定、修改正式文档或提高状态。
19. 开发批次结束、进入下一批次前，必须盘点本批逐条已确认业务改动；尚未写入 PRD 的须先完成 CR 并收入 PRD，不得跳过。
20. 变更稿是可选会话模式，不是新阶段；不得用它改写 PROJECT_STAGE。未纳入的临时袋草稿不是已应用 DEC/CR。
21. 阶段门禁主要约束批准、基线、跨阶段和执行；只要输入已足以形成有意义分析，允许提前生成受控 Draft。提前 Draft 不改变 PROJECT_STAGE，不得把 `Proposed / Assumption / TBD` 提升为已确认事实。
22. 重要技术选型必须先形成 `TECH-DEC-XXX` 分析；候选数量由实际可行性决定，并检查技术层次、兼容性和组合方案。技术栈总览不得脱离 TECH_DECISION/ADR 独立产生。

==================================================
二-B、项目定制化流程路由模型
==================================================

v3.2 不再通过“轻量/中型/重量级”单轴分级直接选择整套流程。

统一模型：

PROJECT_SCENARIO
→ PROJECT_PROFILE
→ ASSESSMENT
→ TRIGGER
→ CAPABILITY_ACTIVATION
→ STAGE_POLICY
→ WORKFLOW_BLUEPRINT
→ USER_CONFIRMATION
→ RUNTIME_CONTEXT

PROJECT_PROFILE 只描述项目客观属性，不负责自行决定流程。

至少包含：

- project_type
- scenario
- lifecycle
- scale
- business
- risk
- technology
- ui
- delivery

ASSESSMENT 只负责：

1. 识别复杂性。
2. 识别高影响风险。
3. 识别会改变流程的 Trigger。
4. 生成 Capability 激活候选。
5. 生成 Stage Policy 建议。
6. 标记不足以判断的字段为 `TBD`。

禁止使用单一总分代替 Assessment。

Scale 只代表规模，不直接等于治理等级。

Trigger 分为：

- `HARD`：命中后必须激活。
- `SOFT`：命中后默认建议激活，允许用户明确关闭并记录理由。
- `INFO`：仅作为上下文信息，不直接激活能力。

每个 Trigger 必须记录：

- trigger_id
- 条件
- 来源
- 当前值
- 触发的 Capability
- 是否 HARD/SOFT/INFO
- 解释
- 排除条件（如有）

CAPABILITY_ACTIVATION 必须至少记录：

- capability_id
- 状态
- 激活原因
- 关联 Trigger
- 来源 SOP/规范
- 适用 G 阶段
- 需加载的 Rule
- 进入条件
- 退出条件
- 所需 Evidence

Capability 是专项能力，不是第二套生命周期。

示例结构：

```yaml
capability:
  id: WECHAT_MINIPROGRAM_DELIVERY
  status: CONDITIONAL
  trigger:
    - project_type contains wechat_mini_program
  stages:
    G2: [platform_constraints]
    G8: [permission_and_upload]
    G10: [real_device_validation]
    G11: [experience_and_production_gate]
```

项目可启用的 Capability 必须来自已存在的能力库或经用户确认建立的能力定义。不存在依据时保持 `TBD`，不得虚构 SOP。

WORKFLOW_BLUEPRINT 由以下输入组装：

- Base Lifecycle：固定 G0～G11 骨架
- Scenario
- Project Profile
- Assessment
- Active Capabilities
- Stage Policy
- 当前 Baseline
- 当前交付目标

Workflow 只允许调整：

- 阶段是否启用
- 阶段执行级别 L0～L4
- 当前项目启用的 Capability
- 阶段附加 Gate
- 阶段之间的前置依赖
- 某阶段需要的 Evidence

Workflow 不允许：

- 创建第二套 G0～G11 生命周期
- 静默删除已有治理门禁
- 将未确认方案写成正式规则
- 因规模较小自动关闭 HIGH/CRITICAL 风险门禁
- 改写已批准 PRD、ADR 或正式基线

当 Workflow Blueprint 会改变必经阶段、强制能力、生产门禁、数据/资金/权限风险或写入权限时，必须先按 `INFORMED_DECISION_PROTOCOL` 完成解释、影响复述、二次确认和受控应用。

Workflow 版本必须唯一，例如：

`WF-001 v1`

当前执行只能引用一个 `WORKFLOW_ID + WORKFLOW_VERSION`。

==================================================
二-C、Stage Contract、Runtime Context 和 Evidence 模型
==================================================

### STAGE_CONTRACT

每个启用阶段至少定义：

```yaml
stage:
  id: G10
  level: L3

  purpose: ...

  entry:
    - condition

  required_context:
    - current_baseline
    - workflow
    - active_capabilities

  required_reads:
    - ...

  allowed_actions:
    - ...

  forbidden_actions:
    - ...

  outputs:
    - ...

  evidence_required:
    - ...

  exit:
    - ...

  rollback_or_recovery:
    - ...
```

Stage Contract 的优先级高于临时口头要求。

用户可以改变 Workflow，但改变后必须生成新版本并重新计算当前阶段的 Entry/Exit 条件。

### RUNTIME_CONTEXT

每次执行具体任务前必须计算：

- project profile
- assessment
- workflow ID/version
- current stage
- stage level
- active capabilities
- active rules
- current baseline
- open items
- allowed actions
- forbidden actions
- write permissions
- required evidence

工作模式与权限必须分离：

```text
WORK MODE
≠
PERMISSION
```

例如 `CODE_WRITE` 不代表允许修改整个仓库；实际可写范围由 `RUNTIME_PERMISSION_PROFILE` 决定。

如果 Runtime Context 与项目文档不一致：

1. 停止写入。
2. 标记 Context 为 `STALE`。
3. 重新读取 Workflow、Baseline 和 Stage Contract。
4. 必要时执行 Workflow Change / Rebase。

### EVIDENCE

Evidence 用于证明“做过、通过、已批准或已发布”。

至少记录：

- evidence_id
- type
- claim
- relates_to
- source
- result
- verifier
- timestamp
- scope
- status

Evidence 状态：

- AVAILABLE
- VERIFIED
- REJECTED
- STALE

以下内容可以成为 Evidence：

- Git Commit/PR
- 测试报告
- 自动化测试结果
- 人工验收记录
- 发布记录
- 截图/录屏
- 日志
- CI/CD 结果
- 文档批准记录
- 代码或数据库检查结果

没有 Evidence 不得提高对应的完成状态或进度。

### TRACE 与 EVIDENCE

`TRACE` 回答：

> “这些对象为什么关联？”

`EVIDENCE` 回答：

> “这个状态凭什么成立？”

二者必须同时保留，不得把 TRACE_MATRIX 变成没有证明能力的状态表，也不得把 Evidence Register 扩展成第二套关系图。

==================================================
二-D、Workflow Change / Rebase
==================================================

以下情况必须重新评估 Workflow：

- 项目目标发生变化
- 生命周期目标从 Demo/测试转为生产
- 风险从 LOW/MEDIUM 升为 HIGH/CRITICAL
- 增加资金、权限、隐私、离线、平台审核等高影响能力
- 技术架构或交付方式变化导致原 Stage Policy 失效
- 新资料证明原 Profile 不准确
- 当前 Workflow 不能覆盖新需求

流程：

```text
CHANGE SIGNAL
→ ASSESSMENT UPDATE
→ Workflow Impact Analysis
→ WCR
→ INFORMED_DECISION
→ WORKFLOW v2
→ REBASE
→ Runtime Context 更新
```

Rebase 至少逐项标记：

- KEEP：保持原结论
- REVALIDATE：需要重新验证
- INVALIDATE：原节点不再有效
- ADD：新增节点、Capability 或 Gate
- REMOVE：仅可在有明确依据且不降低强制治理能力时使用

Rebase 不得删除历史 Workflow。

未完成 Rebase 前：

- 原 Workflow 继续有效；
- 新需求保持 `TBD / Pending` 或按既有 CR 机制处理；
- 不得由 AI 静默切换到新流程。

==================================================
二-E、受控文档提前产出与 TECH_DECISION
==================================================

本机制不新增 G 阶段。它解决“公司需要先看到方案文档，但需求/技术决定尚未全部收敛”的现实场景。

EARLY_DOCUMENT_OUTPUT_POLICY：

- `CONTROLLED_DRAFT`：默认。输入足以形成有意义分析时，可以提前生成 Draft。
- `STAGE_ONLY`：项目明确要求严格等到正式 Stage Entry 后才允许生成文档。

受控提前 Draft 的共同条件：

1. 已有足够来源说明项目目标、主要场景或当前问题，能够形成非空泛的分析。
2. 已确认事实、暂定假设、推断和 TBD 已分开。
3. 会导致完全不同架构方向的重大业务矛盾已识别；无法继续时明确阻断，不凭猜测选边。
4. 文档元信息状态保持 `Draft`，并记录 `generation_context=EARLY_DRAFT`。
5. 提前 Draft 不改变 `PROJECT_STAGE`、Workflow、Approved/Baselined 状态和代码写入权限。
6. 后续上游变化只对受影响章节和决策执行 Revalidation，不机械整篇重写。

Stage Gate 的解释统一为：

- Gate 控制“能否把阶段视为完成、能否批准/基线、能否让下游把结论当正式输入”；
- Gate 不自动等于“此前一字不能写”。

技术选型使用 `TECH_DECISION`：

`技术领域 → 决策问题 → 项目约束 → 候选发现 → 单项分析 → 层次/兼容关系 → 组合方案 → 比较 → 当前推荐 → 待确认 → 决策状态`

TECH_DECISION 规则：

1. 编号使用 `TECH-DEC-XXX`；现有 `TD-XXX` 继续保留给技术设计。
2. 候选数量不固定。只列实质可行方案；只有一个时说明其它常见方案被排除的原因。
3. 必须先判断候选是否真的互斥。规范、实现库、展示工具、调试工具等可能是不同层次的互补项。
4. 存在有效组合时，将 `A+B`、主辅组合、分层方案或阶段性方案作为独立组合进行比较。
5. 推荐状态默认为 `PROPOSED`；用户确认并应用前不得写成 `CONFIRMED`。
6. 每项标记 `BLOCKING / DEFERABLE / INFORMATIONAL`，并给出最晚确认点。
7. 技术栈总览只能从 TECH_DECISION/ADR 汇总产生，不得独立成为“默认栈”。
8. 已确认且形成长期架构约束的 TECH_DECISION 应按治理要求落为 ADR；低影响、可逆选择可不建 ADR。
9. 上游事实变化时，对受影响 TECH_DECISION 标记 `KEEP / REVALIDATE / INVALIDATE / ADD / REMOVE`。
10. 若仓库提供以下通用资产，G6 应按需读取：
    - `doc/capabilities/architecture/technical-selection.md`
    - `doc/templates/TECH-DECISION-TEMPLATE.md`
    - `doc/handbook/architecture/通用技术架构选型说明书_公司版_V3.2.md`

二、AI 工作边界
==================================================

1. 文档阶段默认只能修改 {{DOC_ROOT}}。
2. 未经授权不得修改业务代码、配置、数据库和基础设施。

CURRENT_BASELINE：

==================================================
二-A、知情决策全局强制协议
==================================================

协议标识：`INFORMED_DECISION_PROTOCOL`，简称 `IDP`。

适用范围：

1. 业务冲突、候选需求、PRD 规则和开放问题。
2. 架构参与模式、总体架构、模块边界、技术方案和迁移方案。
3. UI 约束、素材取舍、UI-CONFLICT、高保真等级和替代方案。
4. CR、ADR、DEC、UI-DEC、阶段批准、基线化和其它状态变更。
5. 任何需要用户在多个可行方案中选择，或需要用户承担风险、成本和后果的问答。

纯事实收集问题也必须说明“为什么需要、接受什么格式、未知时能否保持 TBD”，
但只有事实回答会触发业务或状态变化时，才进入完整三阶段决策流程。

决策影响分级：

- `HIGH`：金额、支付、退款、结算、权限、账号、状态机、数据归属、
  删除、迁移、隐私、安全、合规、不兼容变更、PRD 业务规则、
  架构拓扑、模块边界、Approved/Baselined 状态和跨阶段门禁。
- `LOW`：可逆且不改变业务含义的命名、文档组织、展示顺序、进度说明
  和低风险 UI 细节。
- `HIGH` 每轮只允许 1 项；`LOW` 每轮最多 2 项。
- 一轮不得混合 1 个高影响决策和其它决策。
- 同轮包含 2 个低影响决策时，必须为每项分配独立决策 ID，
  分别提问、分别复述、分别二次确认，并在 APPLY 中逐项列明；
  不得用一次合并确认替代两个独立确认。

阶段一：`INFORMED_REVIEW`，只读呈现。

**呈现介质（强制）：** 知情决策必须写在**当前会话窗口的正文消息**里。禁止使用弹框、问卷、结构化选项表、原生确认卡片、IDE 表单或任何把选项收成「点一下」的控件。用户关闭弹框、取消表单、只点一次选项，一律不构成初选或确认。

在提出选择问题前，必须按下列结构写完，缺一块就不得提问：

1. **决策背景与问题描述**：这个决策在决定什么；当前卡在哪；不决定会阻塞什么；相关 PRD、来源、DEC、ADR、现码事实和治理约束。
   若本决策涉及「功能」（人能碰到的行为，或系统办完后人在某页能看见的结果），本块必须含紧挨着的「功能在哪看到」，并强制套下面人话 6 问；缺一问不得提问。禁止只用字段名、文件名当背景。表结构、接口路径、SQL 编号、部署不受此约束。

   **功能在哪看到 / 人话 6 问**（知情决策、CR、对 bug 说话，凡描述功能都用这一套）：

   1. 哪一端、哪一业态：平台后台 / 商家后台 / 店小程序 / 共益优选 / 入驻 H5。多端分行。四业态不同就分行。禁止只写「系统里」「后台」。
   2. 谁，或谁也不用点：人写身份；机器写「不用人点，支付成功后 / 每天跑批后」。
   3. 怎么走进来：后台写侧栏「一级 → 二级 → 页签」（现码菜单名）；小程序写底部或「我的 / 订单」；H5 写从哪页哪个按钮进来。没有入口写「现在无处可进」或「侧栏没有但还能打开某页」。名称吃不准就写页面标题并标明待核对。
   4. 人在哪看见：列表哪一列、详情哪一段、哪个按钮、哪句文案、导出文件哪一列、哪条短信。没有界面就写「过程看不见，结果在【哪一端哪一页哪一块】能看见」。
   5. 怎么操作，或怎么触发：从打开到看见的步骤；要哪类单据。自动任务写什么事件触发。删功能写现在怎么点还能看见它。无权限、没数据时分别怎样。
   6. 现在怎样 / 改完怎样：只写眼睛（或短信、导出文件）看到的变化。删除：现在能看见什么，改完这里不该再有。字段名必须出现时放括号里。

   短句模板：
   【哪一端·哪业态】里，【谁 / 不用人点】，从【怎么走进来】到【人在哪看见】。【怎么操作或触发】之后：现在是……；改完是……。
2. **生动形象的解释**：用生活化例子或一条完整运行流程讲清楚；专业术语先用白话解释。高影响项至少举一个能对照真实用户/商家/平台的例子。生动例子必须能按人话 6 问走一遍；禁止只用字段名、文件名当背景。
3. **备选方案对比**：普通非技术决策通常选择少量、差异清晰的真实可行方案；**技术选型类 TECH_DECISION 不固定候选数量**，必须覆盖实质可行候选，并先识别“互斥 / 可替代 / 依赖 / 互补”关系。存在职责互补时，应把 `A+B`、主方案+辅助方案或分层组合本身作为可比较方案。不得为凑数制造伪候选，也不得遗漏明显组合。每个保留方案按适用范围评估：
   - 实际如何运行，请求、状态或数据如何流动
   - 数据归属、权威写入方和租户/用户边界
   - 上下游依赖、第三方和基础设施依赖
   - 事务、一致性、幂等、补偿和失败结果
   - 具体优点和缺点
   - 业务、技术、运维、安全、隐私和合规风险
   - 开发成本、认知复杂度、运维复杂度和性能影响
   - 对交付、兼容、迁移和现有数据的影响
   - 测试、发布、灰度、降级和回滚方式
   - 适用条件和不适用条件
4. **推荐选择与核心理由**：明确写出推荐哪一案或哪一组合，以及为什么推荐、为什么不选其它仍可行方案；若为组合，必须说明各组件职责和组合必要性。不得用「推荐」二字代替理由。
5. **开发技术决策清单**：若选各案（至少覆盖推荐案），编码时要改什么、不改什么、在哪个批次改、本窗是否允许改代码；待配置不得编造。
6. 某个维度确实不适用时标记 `N/A` 并说明原因，不得静默省略。
7. 每个决策最后只提出一个明确问题，请用户**在本会话用文字**回复方案字母或 `{{DECISION_ID}}={{OPTION}}`；同一轮包含两个低影响决策时，分成两个编号问题。允许用户回答：
   `继续解释`、`换个例子`、`比较指定方案`、`暂不决定` 或选择某方案。

用户要求继续解释时，必须停留在 `INFORMED_REVIEW`，针对不理解点补充说明；
不得同时推进下一个决策，不得把用户的追问解释为反对或确认。

阶段二：`INFORMED_CONFIRMATION`，只读复述。

用户初次选择后，不立即写文件。先复述：

1. 决策 ID 和主题。
2. 用户选择的方案。
3. 用户补充的限制条件。
4. 被拒绝或未选择的方案。
5. 对业务、数据、架构、UI、安全、成本、交付、迁移、测试、
   发布和回滚的实际影响。
6. 继续保持 `TBD` 或延期的内容。

复述后只提出一个二次确认问题。存在歧义时只问一个澄清问题。

以下不构成有效确认：

- “我倾向于”“可以考虑”“大概可以”“先这样”“你决定吧”。
- 用户表示不理解、没看懂、要求继续说明或换例子。
- 用户取消问卷、关闭弹框、跳过、暂停、沉默、切换话题或撤回选择。
- 仅点击一次选项、使用结构化表单点选但尚未在会话正文完成影响复述和二次确认。
- AI 根据推荐方案、历史偏好或默认值自行推断用户选择。

有效确认必须满足以下之一：

- 用户在影响复述后明确回复“确认该决策”或等价且无歧义的确认。
- 用户使用 `确认该决策：{{DECISION_ID}}={{OPTION}}`，
  并给出 `限制条件：{{CONSTRAINTS 或 NONE}}`。
- 用户对已经完成评审和影响复述的明确版本、范围和状态直接发出批准口令。

阶段三：`DECISION_APPLY`，受控写入。

1. 只有完成 `INFORMED_CONFIRMATION` 且获得明确应用授权后才能执行。
2. 根据决策类型写入 DEC、ADR、CR、UI-DEC、受控决策登记或状态记录。
3. 只应用已确认范围，不得附带未展示、未解释或未确认的方案。
4. `APPLY` 过程中发现新权衡时停止写入，回到 `INFORMED_REVIEW`。
5. 业务规则、技术决策、纯视觉决策和需求变更分别使用正确记录类型，
   不得相互替代。
6. 部分应用标记 `PARTIAL`；全部必选决策完成确认并应用后，
   才能标记对应 `REVIEW_STATUS/APPLY_STATUS=COMPLETED`。
7. 用户取消或拒绝后，当前项保持候选或 `TBD`，评审状态保持
   `NOT_STARTED/IN_PROGRESS`，不得提高文档、阶段或批准状态。

标准问答顺序：

`DISCOVERY → INFORMED_REVIEW → INFORMED_CONFIRMATION → DECISION_APPLY`

其中 `INFORMED_REVIEW` 和 `INFORMED_CONFIRMATION` 默认不得修改正式文档、
项目变量和进度状态；问答与应用必须分离。

四、文档元信息、状态和编号
==================================================

正式文档顶部至少包含：

- 文档名称
- 文档编号
- 版本
- 状态
- 负责人
- 创建日期
- 更新时间
- 关联来源
- 关联需求
- 关联决策
- 适用版本
- 替代文档

正式文档状态：

Draft → In Review → Approved → Baselined

附加状态：

- Needs Review：上级规范、PRD 或素材变化后需要复核
- Superseded：被新版本替代
- Deprecated：已废弃但仍保留追踪
- Archived：仅作历史参考

没有用户明确批准不得标记 Approved。
没有形成完整交付基线不得标记 Baselined。
历史基线不得删除或静默覆盖。

结论标签：

- 已确认
- 现状
- 候选
- 推断
- 待确认
- 已废弃

开放项状态：

- 无
- 待配置
- 待评审

需求变化状态：

- 新增
- 修改
- 保留
- 废弃

问题等级：

- P0：阻断下一阶段
- P1：必须在当前阶段修复

==================================================
五、来源和规则优先级
==================================================

业务冲突优先级：

用户最新明确决定
→ Approved/Baselined PRD
→ 新版正式需求资料
→ 新版设计图明确可见事实
→ CURRENT_BASELINE 代码
→ 旧需求、旧设计和历史代码

涉及金额、支付、退款、结算、权限、账号、状态、数据归属、
数据删除、迁移、隐私和不兼容变更时，必须按 `INFORMED_DECISION_PROTOCOL`
作为高影响决策逐项解释、复述和二次确认。

UI 规范有效优先级：

页面级 Approved/Baselined UI_SPEC
→ 功能模块级 Approved/Baselined UI_SPEC
→ 设备级 Approved/Baselined UI_SPEC
→ 前端应用级 Approved/Baselined UI_SPEC
→ shared Approved/Baselined UI_SPEC

UI 合并规则：

1. 先筛选适用项目、终端、模块、页面和目标版本。
2. 从低层级向高层级加载。
3. 子级未声明内容继承父级。
4. 子级明确声明的可覆盖内容替换父级。
5. PRD、权限、安全、隐私和可访问性硬约束不得被 UI 规范覆盖。
6. 父级标记 locked 的规则必须通过 UI-DEC 才能覆盖。
7. 同一层级有两个有效版本时不得按日期自动裁决，必须按
   `INFORMED_DECISION_PROTOCOL` 完成比较和确认。
8. Draft、Needs Review 和 AI 重建未确认内容不能约束正式开发。
9. 原始设计图和规范材料只作为 UI_SPEC 来源，不直接参与开发合并。

==================================================
六、阶段门禁
==================================================

统一前置路由门禁：

1. 新项目或新治理上下文先建立 `PROJECT_PROFILE`。
2. 需要项目定制化流程时完成 `ASSESSMENT`。
3. 根据 Trigger 激活 Capability。
4. 生成 `WORKFLOW_BLUEPRINT` 并确认。
5. 将当前 Workflow、Stage、Capability、Rule、Baseline 和权限装入 `RUNTIME_CONTEXT`。
6. 后续 G0～G11 只按当前 Workflow Blueprint 中的 Stage Policy 执行。

以上为跨阶段路由机制，不新增 G 阶段。

G0 文档初始化
G1 资料投放
G2 来源和决策基线
G3 PRD 准入审计
G4 PRD Draft
G5 PRD 评审和批准
G5.5 根据 Approved PRD 生成或同步 UI 逻辑范围
G6 总体技术架构
G7 技术模块划分
G8 模块详细技术设计
G9 API、数据和编码规范
G9.1 根据应用架构和 PROJECT_STRUCTURE 生成正式 UI 应用目录
G9.5 可选生成和批准 UI 设计规范
G10 开发批次、有效 UI Contract 和交付
G11 实施、测试、发布和维护

G5.5 规则：

- GENERATE_UI_REFERENCE_TREE=true 时总是执行。
- 只生成 ui-design 根目录、UI_SCOPE_MAP、逻辑终端范围和追踪。
- application_id、application_slug 和 repository_path 保持 TBD。
- 不根据 PRD 提前创建 admin、miniapp 等正式 products/ 子目录。

G6 规则：

- 默认 `ARCHITECTURE_PARTICIPATION_MODE=MANDATORY`，默认 `EARLY_DOCUMENT_OUTPUT_POLICY=CONTROLLED_DRAFT`。
- 在正式进入 G6 前，只要满足二-E的受控提前 Draft 条件，可以先形成架构/技术选型工作稿；该动作不改变 PROJECT_STAGE。
- `MANDATORY` 不再等于“所有决策确认前禁止写 Draft”。生成 Draft 前必须至少建立重要 `TECH-DECISION` 清单、候选/组合分析、Blocking/Deferable 和当前状态；未确认项写 `PROPOSED/TBD`。
- `ARCHITECTURE_DECISION_REVIEW_STATUS=COMPLETED` 与 `ARCHITECTURE_DECISION_APPLY_STATUS=COMPLETED` 是**G6 正式出口、Approved/Baselined 或依赖这些阻断结论的下游门禁**，不是普通 Draft 的机械前置。
- `OPTIONAL` 允许用户选择先看 Draft 再逐项确认，或先确认再完善 Draft；两条路径均不得静默确认。
- `DIRECT_DRAFT` 只表示把逐项确认延后，仍必须识别 TECH_DECISION、假设、未决项和风险，不得跳过候选/组合分析。
- 单条生成口令不得把评审/应用状态自动设为 Completed。
- Draft 必须记录生成上下文、未决项、风险、最晚确认点和恢复/复核路径。

G7 规则：

- `MODULE_BOUNDARY_PARTICIPATION_MODE=INHERIT` 时继承 G6 参与模式。
- 允许在总体架构 Draft 已足以支持边界分析时先生成受控 MODULE_BOUNDARIES Draft；未确认边界保持 `PROPOSED/TBD`。
- `MANDATORY` 表示边界真实性和正式出口受控，不再要求所有争议在 Draft 前全部确认；进入 G8 前，与当前详细设计有关的 Blocking 边界决策必须完成确认和应用。
- `DIRECT_DRAFT` 仍须登记拆分争议、依赖、风险和最晚确认点，不得跳过分析。
- MODULE_BOUNDARIES Draft 仍须独立评审和明确批准，不能因为“已经写出来”自动进入 G8。

G9.1 规则：

- GENERATE_UI_APPLICATION_TREE=true 时执行。
- 输入必须包括已确认应用架构和 PROJECT_STRUCTURE。
- products/{application_slug} 与实际前端应用交付单元对应。
- 例如代码路径 app/admin_front 对应 products/admin_front。
- 只生成真实存在的前端应用，不生成假设终端。
- 后端服务没有页面交付单元时不生成 UI 应用目录。

G9.5 规则：

- ENABLE_UI_SPEC_GENERATION=false 时跳过。
- 跳过 G9.5 不得阻断开发。
- 启用时通过素材登记、知情决策问答、Draft、评审和批准生成 UI_SPEC。
- 前端批次有有效 UI_SPEC 时必须生成 EFFECTIVE_UI_CONTRACT。

项目未知时只执行：

2. 创建 AI_DOCUMENTATION_GUIDE。

9. 不选择技术栈。

==================================================
八、G1 资料投放
==================================================

用户说“这是第 N 批资料”时：

1. 分配来源编号。
2. 登记名称、路径、类型、版本、日期、范围和优先级。
3. 检查完整性、可读性和重复。
4. 摘要新增、修改、保留和废弃内容。
5. 分离业务资料、技术资料和 UI 资料。
6. 识别冲突、风险和缺口。
7. 生成批次摘要。
8. 更新 SOURCE_REGISTER 和资料处理进度。
9. 不生成最终 PRD。
10. 不确定最终架构。
11. 不修改业务代码。

图片只能确认：

- 页面名称
- 可见入口
- 可见字段
- 可见按钮
- 可见状态
- 明确文案
- 可见布局、颜色、字体、图标和组件

单张图片不能证明：

- 完整权限
- 完整状态机
- 后端调用流程
- 金额结算
- 异常流程
- 数据归属
- 未展示页面状态

用户没有明确说“材料投放完成”前，不进入整体归纳。
资料范围未冻结时，文档总进度显示 N/A。

==================================================
九、G2 来源和决策基线
==================================================

材料投放完成后生成：

1. 来源盘点
2. 决策基线
3. 版本差异
4. 冲突矩阵
5. 待确认问题
6. 需求一致性审计

所有待确认问题按 `INFORMED_DECISION_PROTOCOL` 执行：

1. P0/P1、业务规则、金额、权限、状态和数据归属按高影响决策处理，每轮只评审 1 项。
2. 低影响问题每轮最多 2 项；同轮 2 项必须按各自 ID 分别提问、
   复述、二次确认和应用。
3. 先解释约束、术语、方案和完整影响，再提出一个选择问题。
4. 用户初次回答后只复述选择及影响，不形成 DEC、不修改文件。
5. 完成二次确认并获得应用授权后，才形成 DEC 并同步来源、
   基线、冲突、待确认问题和项目看板。
6. 不重复询问已经完成二次确认的问题；上游变化时标记 `STALE` 后重新评审。

==================================================
十、G3 PRD 准入审计
==================================================

生成 PRD 前检查：

1. P0/P1 是否为 0。
2. 金额是否唯一可计算。
3. 权限是否有角色和数据范围。
4. 状态是否有合法流转。
5. 账号生命周期是否完整。
6. 数据归属是否明确。
7. 异常和重复操作是否有结果。
8. 需求是否能写成 Given/When/Then。
9. 技术和 UI 实现问题是否错误混入 PRD。
10. 已确认 DEC 是否互相冲突。

存在 P0/P1 时，先按 `INFORMED_DECISION_PROTOCOL` 逐项完成评审、
二次确认和 DEC 应用，再重新审计；门禁通过前不生成 PRD。

==================================================
十一、G4 PRD Draft
==================================================

PRD 只描述：

- 为什么做
- 为谁做
- 做什么
- 业务规则
- 流程
- 状态
- 权限
- 异常
- 怎样验收

PRD 不描述：

- 数据库表
- 类名和函数名
- 框架和组件库
- 缓存和消息实现
- 部署实现
- 像素、颜色和具体 CSS 实现

总 PRD 至少包含：

1. 文档元信息
2. 项目背景和问题陈述
3. 产品目标和指标
4. 用户和角色

11. 风险和依赖
12. 开放项
13. 验收和上线范围
14. 来源与追踪

1. 需求编号

==================================================
十二、G5 PRD 评审和批准
==================================================

候选需求、待评审需求和业务冲突必须按 `INFORMED_DECISION_PROTOCOL`
逐项处理。改变业务规则的事项按高影响处理，每轮只评审 1 项；
初次选择不得修改 PRD，二次确认并受控应用后才形成 DEC。

状态流转：

Draft → In Review → Approved → Baselined

进入 In Review 前：

- 所有需求有编号、来源和验收标准
- 候选和待评审明确
- P0/P1 为 0
- 追踪矩阵完整
- 终检通过

进入 Approved 前：

- 用户明确批准
- 待评审为 0
- 业务冲突已裁决
- 所有高影响问答均已完成知情决策二次确认和受控应用
- 待配置项不改变业务模型
- 变更记录完整

未经用户明确回复批准，不得标记 Approved。

十三、G5.5 根据 PRD 同步 UI 逻辑范围
==================================================

当 PRD Approved 且 GENERATE_UI_REFERENCE_TREE=true 时：

1. 读取 PRD 功能地图、模块 ID、目标终端和页面范围。
2. 创建或更新 UI_SCOPE_MAP，登记 PRD 模块需要的逻辑页面终端。
3. application_id、application_slug 和 repository_path 暂时保持 TBD。
4. 使用稳定 PRD 模块 ID，例如 M02-auth，不使用中文名称作为唯一标识。
5. 只创建 ui-design 根目录、shared 通用入口、登记和追踪模板。
6. 不根据 PRD 创建固定 admin、miniapp 或其他正式 products/ 子目录。
7. 不根据 PRD 虚构颜色、布局、组件和视觉方案。
8. 更新 UI_DESIGN_REGISTER 和 UI_TRACE_MATRIX。
9. PRD 模块改名、拆分或废弃时同步逻辑范围和替代关系。
10. 在应用架构确认前，新增原始 UI 素材先登记到 sources/inbox/，
    或登记为 application_id=TBD，不能强行归入假设应用目录。

==================================================
十四、G6 总体技术架构
==================================================

总体架构只有在满足正式 G6 门禁后才能升级为 Approved/Baselined；**架构 Draft 可以更早产生**。当 PRD 尚未 Approved、但项目目标、主要范围和关键约束已足以形成有意义分析时，可按二-E生成受控工作 Draft，未确认内容必须保持 `Assumption / Proposed / TBD`，且不得推进 PROJECT_STAGE。

G6 支持三种执行模式：

1. `MANDATORY`：默认模式。先建立完整的 TECH_DECISION 决策清单和分析；Draft 可在决策确认过程中生成，Blocking 决策必须在正式出口前确认并应用。
2. `OPTIONAL`：AI 解释“先 Draft 后确认”与“先确认后完善 Draft”的差异，由用户选择节奏。
3. `DIRECT_DRAFT`：用户要求先快速形成工作稿；逐项确认延后，但 TECH_DECISION 清单、候选/组合分析、Assumption/TBD 仍然必需。

参与模式选择本身属于高影响决策，必须先按 `INFORMED_DECISION_PROTOCOL`
解释三种模式的门禁、风险和恢复成本，再让用户选择并二次确认。

任何“生成总体架构”口令执行前必须预检：

1. 读取 `ARCHITECTURE_PARTICIPATION_MODE`。
2. 读取 `ARCHITECTURE_DECISION_REVIEW_STATUS` 和 `ARCHITECTURE_DECISION_APPLY_STATUS`。
3. 读取 `ALLOW_ARCHITECTURE_DRAFT_WITH_TBD`。
4. 建立/读取 `TECH-DECISION` 清单，核对候选、组合、Blocking/Deferable、状态和最晚确认点。
5. 判断本次是 `EARLY_DRAFT`、普通 G6 Draft、G6 Exit/Approved 还是 Baselined；不同目的使用不同门禁。
6. 只有当前动作需要依赖某个 Blocking 结论且尚未确认时才阻断；仅生成受控 Draft 时不得把“尚未全部确认”本身当作阻断理由。

`ARCHITECTURE_DECISION_REVIEW` 是 G6 内的受控评审步骤，不新增阶段编号。执行时：

- 重点分析总体架构与技术选型；可以生成/更新 `TECH-DEC-XXX` 分析，但在用户确认前不创建代表最终结论的 ADR。
- 按技术栈、应用与服务拆分、仓库和项目结构、多租户与数据隔离、认证权限与安全、数据/缓存/搜索/文件、支付退款分账与一致性、消息任务通知、部署监控容灾回滚等主题整理决策。
- 先区分 `BLOCKING / DEFERABLE / INFORMATIONAL`，并给出最晚确认点。
- 技术选择先判断候选层次与兼容关系，再构建有效组合；候选数量不固定。
- 会改变架构拓扑、数据归属、安全边界、长期技术基线或迁移路径的决策按 HIGH 处理；普通、可逆、低成本工具选择可按 LOW 处理。需要用户确认时按 `INFORMED_DECISION_PROTOCOL` 对应数量规则执行。
- 除 PRD 约束、方案和生活化解释外，必须覆盖数据归属、依赖、事务、
  安全隐私、成本、复杂度、性能、交付、迁移、测试、发布和回滚。
- 存在明显权衡时不得替用户选择；用户确认前保持 `TBD`。
- 用户初次回答后进入 `ARCHITECTURE_DECISION_CONFIRMATION`，
  只复述选择、限制条件、被拒方案、影响和剩余 TBD，不立即修改文件。

`ARCHITECTURE_DECISION_CONFIRMATION` 是二次确认步骤：

- 用户表示不理解、取消或要求继续解释时，返回评审步骤。
- 只有用户在影响复述后明确确认，才能把该项计为已确认。
- 尚有任一必选项未完成二次确认时，评审状态保持 `IN_PROGRESS`。

`ARCHITECTURE_DECISION_APPLY` 是独立写入步骤：

- 只有存在 `ARCHITECTURE_DECISION_CONFIRMATION` 证据且用户明确授权应用时才能执行。
- 将确认结果写入 ADR 或受控决策记录，并同步状态和追踪。
- 部分应用时 `ARCHITECTURE_DECISION_APPLY_STATUS=PARTIAL`。
- 全部必选决策已确认并写入后，评审和应用状态才能分别变为 `COMPLETED`。
- AI 不得因生成了 ADR 候选清单或架构 Draft 自动把状态设为 Completed。

生成总体架构 Draft 时：

- `MANDATORY`：必须先完成技术决策清单和足够的候选/组合分析；评审和应用状态可以是 `IN_PROGRESS/PARTIAL`，但所有未确认选择只能以 `PROPOSED/TBD` 出现在 Draft 中。
- `OPTIONAL`：按用户选择的参与节奏生成，不能把未确认推荐升级状态。
- `DIRECT_DRAFT`：仍需登记 TECH_DECISION 清单、Assumption、未决项、风险和最晚确认点。
- `ALLOW_ARCHITECTURE_DRAFT_WITH_TBD=true` 时允许存在显式未决项；若项目将其设为 false，则回到严格决策先行模式。
- 所有模式下新产物状态只能先为 Draft，不得自动标记 Approved 或 Baselined。
- 当准备 G6 Exit、Approved/Baselined 或进入依赖 Blocking 结论的下游动作时，Blocking TECH_DECISION 必须完成确认与受控应用。

若架构 Draft 在决策完成前已经生成：

- 不删除 Draft，不覆盖历史。
- 将其标记为带未决项的 Draft，并恢复/保持评审状态为 `IN_PROGRESS`。
- 回到逐项决策评审。
- 完成 `ARCHITECTURE_DECISION_APPLY` 后，再执行架构同步和一致性复核。

架构至少包含：

- 输入成熟度、Assumption/TBD 与 TECH_DECISION 清单
- 架构目标和质量属性
- 系统上下文和外部依赖
- 应用、组件和数据架构
- API 和通信
- 认证、授权和数据隔离
- 缓存、任务和消息
- 第三方服务
- 安全、隐私和审计
- 性能、容量、可用性和容灾
- 部署、环境、灰度、降级和回滚
- 当前实现、目标实现、差距和迁移
- ADR

每项架构能力必须引用 PRD 编号。

十五、G7 技术模块划分
==================================================

G7 默认继承 G6 的参与模式；用户可以显式设置
`MODULE_BOUNDARY_PARTICIPATION_MODE` 覆盖。覆盖模式的选择本身属于
高影响决策，必须按 `INFORMED_DECISION_PROTOCOL` 先解释门禁、风险
和恢复成本，再完成二次确认。

任何“生成 MODULE_BOUNDARIES”口令执行前，必须预检参与模式、评审状态、应用状态、直接 Draft 授权和未决拆分争议。门禁不满足时停止生成。

`MODULE_BOUNDARY_DECISION_REVIEW` 是 G7 内的受控评审步骤，不新增阶段编号。执行时：

- 只分析模块边界候选，不生成或修改正式 MODULE_BOUNDARIES 和模块详细技术设计。
- 模块边界属于高影响决策，按 `INFORMED_DECISION_PROTOCOL` 每轮只评审 1 个拆分争议。
- 每项先解释相关 PRD/架构约束、术语和实际运行例子，再比较候选方案。
- 必须说明数据所有权、依赖方向、事务一致性、安全隐私、成本复杂度、
  性能、独立测试、部署、发布、迁移和回滚影响。
- 用户确认前，模块名称、稳定 ID、拆分关系和部署关系保持候选或 `TBD`。
- 用户初次回答后不修改文件，进入 `MODULE_BOUNDARY_DECISION_CONFIRMATION`。

`MODULE_BOUNDARY_DECISION_CONFIRMATION` 是独立二次确认步骤：

- 复述所选边界、职责/非职责、数据所有权、依赖、事务和交付影响。
- 列出被拒方案、限制条件和仍延期的内容。
- 用户表示不理解或取消时，返回评审步骤，不记录决定。
- 用户明确确认后，该项才计入评审完成证据。

`MODULE_BOUNDARY_DECISION_APPLY` 是独立写入步骤：

- 只应用已完成二次确认的拆分决策，写入受控决策记录并同步状态。
- 部分应用时标记 `PARTIAL`；全部必选项确认并应用后，
  才能把评审和应用状态设为 `COMPLETED`。
- 不在应用步骤生成 MODULE_BOUNDARIES、详细设计、API、数据模型或代码。

生成 MODULE_BOUNDARIES Draft 时：

- `MANDATORY`：必须先识别拆分争议、数据所有权/依赖/事务影响及 Blocking/Deferable；评审/应用状态可处于 IN_PROGRESS/PARTIAL，未确认边界只能写 `PROPOSED/TBD`。
- `OPTIONAL`：按用户选择的参与节奏生成，不能把未确认边界升级状态。
- `DIRECT_DRAFT`：仍须登记争议、依赖、风险和最晚确认点。
- `ALLOW_MODULE_BOUNDARIES_DRAFT_WITH_TBD=true` 时允许存在显式未决争议；进入 G8 前，相关 Blocking 决策必须完成确认和应用。
- Draft 仍须独立评审和明确批准，不能自动进入 G8。

详细设计前必须生成 MODULE_BOUNDARIES，至少包含：

- PRD 业务模块
- 技术模块和 ID
- 职责和非职责
- PRD 到技术模块映射
- 数据所有权
- 依赖方向
- 事务和一致性边界
- 独立测试、发布和回滚能力
- 技术设计文档清单
- 拆分争议和候选方案

原则：

- 高内聚、低耦合
- 同状态和数据生命周期尽量集中
- 强事务能力不要随意拆分
- 不按页面数量或数据库表机械拆分
- 不提前按微服务过度拆分
- 业务模块、技术模块和部署服务不必一一对应

MODULE_BOUNDARIES 必须完成知情决策评审、影响复述、二次确认和独立批准。

十七之二、G9.1 生成正式 UI 应用目录
==================================================

10. 更新 UI_DESIGN_REGISTER 和 UI_TRACE_MATRIX。
11. 应用目录后续改名时登记迁移和替代关系，不静默覆盖历史路径。

UI_APPLICATION_MAPPING 至少记录：

- application_id
- application_slug
- repository_path
- application_type
- devices
- prd_modules
- architecture_source
- project_structure_source
- status
- version

高影响决策处理；初次选择不得直接写入 UI-DEC 或 UI_SPEC。

UI 规范层级：

shared
→ 前端应用交付单元
→ 设备
→ 功能模块
→ 页面

每份 UI_SPEC 至少包含：

1. 规范编号、层级、范围、版本和状态
2. 关联 PRD、原始素材和父级规范
3. 设计目标
4. 继承内容、覆盖内容和 locked 规则
5. 组件库和版本
6. Design Token
7. 色彩、字体、圆角、阴影、间距和图标
8. 页面布局和页面模式
9. 组件使用规范
10. 交互规范
11. Loading、Empty、Error、Disabled、No Permission、Offline、Success
12. 响应式和设备适配
13. 可访问性
14. 高保真要求
15. 必须遵守、推荐实践和禁止事项
16. 视觉验收标准
17. 待确认问题

还原等级：

- F0：无设计图，只使用页面规格或组件库
- F1：风格参考
- F2：结构参考
- F3：高保真
- F4：固定环境下的视觉基准

如果 UI 规范未启用：

- 不阻断开发。
- 不要求补设计图。
- 继续按 PRD、技术设计、编码规范、组件库和现有 UI 基线开发。
- UI 规范不计入当前文档计划分母。

设计与 PRD 冲突：

1. PRD 优先。
2. 停止冲突部分。
3. 创建 UI-CONFLICT。
4. 按知情决策协议解释冲突、方案和影响，并完成二次确认。
5. 纯视觉问题在 `DECISION_APPLY` 阶段形成 UI-DEC。
6. 影响业务时在 `DECISION_APPLY` 阶段创建 CR。
7. 只有受控应用完成后才能更新设计、PRD 或 UI_SPEC。

- Figma、Sketch、PSD 等可编辑设计源
- PNG、JPG、WebP 等设计图
- SVG、PNG、WebP 等图标和视觉资产
- PDF 设计规范
- 组件库和设计系统说明
- 字体、品牌、Logo 和色板资料
- Lottie JSON、GIF 等动画素材

原始素材规则：

1. 原始素材只作为 UI_SPEC 的输入，不直接作为业务规则。
2. 素材放入最具体、最适用的层级，避免重复存放。
3. 同一素材被多个节点复用时只保存一份，通过来源 ID 引用。
4. AI 必须区分素材明确事实、推断和待确认内容。
5. AI 通过文件路径、版本、哈希、Active/Superseded 状态和影响范围检测变化。
6. 新版本素材不得静默覆盖旧版本。
7. 未确认版权或来源的素材不得直接进入生产资产。

==================================================
二十、图标和视觉资产规则
==================================================

图标来源分为：

1. 原始矢量或设计工具导出资产
2. 原始透明位图
3. 标准组件库图标
4. 从设计截图裁剪的位图
5. AI 根据截图近似重建的图标

推荐优先级：

原始 SVG
→ 设计工具直接导出的 PNG/WebP
→ 已确认的标准组件库图标
→ 从截图裁剪的位图
→ AI 近似重建

可编辑设计源：

- Figma、Sketch、PSD 等文件可以用于导出 SVG、PNG、WebP、PDF
  和不同倍率的透明图片。
- 能从原始设计文件导出时，不应优先从截图裁剪。

PNG/JPG 截图：

- AI 可以识别图标位置、裁剪位图、匹配标准图标库或近似重绘 SVG。
- 截图无法准确恢复原始路径、描边、透明区域、原始尺寸和矢量细节。
- AI 重建图标必须标记 source_type=reconstructed、status=Needs Review。
- 未经人工确认，AI 重建图标不能作为原始设计资产或 F4 视觉基准。

推荐支持格式：

- SVG：首选矢量母版
- PNG：透明背景和广泛兼容
- WebP：体积较小
- ICO：favicon 或桌面图标
- iconfont：仅在现有项目已采用时保留
- Lottie JSON：动态图标
- GIF：简单动画，不推荐用于普通图标

不建议使用 JPG 保存图标，因为不支持透明背景且缩放容易失真。

标准组件库图标：

- 不必重复提交图标文件。
- 必须登记组件库包名、版本、组件名和许可。
- 示例：library=@ant-design/icons，component=UserOutlined。

目标平台：

- Web/PC 可优先使用经过安全检查的 SVG。
- 小程序能否直接使用 SVG 取决于目标运行时和构建工具。
- 可以保留 SVG 作为母版，再导出 PNG、WebP、图标组件或平台兼容资源。
- 不得假设所有终端都支持同一种图标交付格式。

图标目录：

materials/assets/icons/
├── source/                  # SVG 等原始母版
├── reconstructed/           # AI 重建，等待人工确认
├── exports/
│   ├── web/
│   └── miniapp/
└── ICON_MANIFEST.yaml

ICON_MANIFEST 至少记录：

- asset_id
- name
- source_type
- source_file
- output_files
- format
- library 和 component
- version
- targets
- status
- license
- checksum
- usage
- replaced_by

高保真页面要求：

- 自定义图标应额外提交原始 SVG 或透明位图。
- 只有设计截图但缺少原始图标时，必须明确允许裁剪、标准库替换或 AI 重建。
- 图标缺失且未获得确认时，页面不能声明达到 F4。

二十一、UI 素材增量更新

基本原则：

只重新生成直接变化节点，并审计所有继承该节点的下级节点和开发批次。
素材变化引发的取舍、冲突、替代方案或验收基准变化必须按

页面素材变化：

页面 UI_SPEC 更新
→ 引用该页面的 UI Contract 更新

功能模块素材变化：

功能模块 UI_SPEC 更新
→ 审计模块下页面
→ 更新受影响批次 UI Contract

设备规范素材变化：

设备 UI_SPEC 更新
→ 审计设备下所有功能模块

→ 继承节点标记 Needs Review
→ 执行影响分析
→ 更新实际受影响规范和 UI Contract

不允许：

- 无条件重新生成全部 UI 文档
- 永远只更新当前目录而忽略继承影响
- 静默覆盖旧 UI_SPEC
- 将未评审的新素材直接带入正在开发的批次

每个批次必须：

1. 只围绕一个业务目标。
2. 引用当前 WORKFLOW_BLUEPRINT、Stage Contract 和激活 Capability。
2. 引用需求和技术设计。
3. 可独立开发、测试、验收和回滚。
4. 说明前置依赖。
5. 说明代码、数据、API 和配置影响。
6. 包含测试、人工验证、灰度和回滚。
7. 不重构无关模块。
8. 明确本批需要产生的 Evidence。
9. 不得执行当前 Runtime Context 之外的动作。

批次状态：

Planned
→ Ready
→ In Progress
→ Code Complete
→ Testing
→ Accepted
→ Released
→ Closed

Blocked 作为附加状态。

进入下一批次前：盘点本批用户逐条确认并已落地的业务规则。若相对盖章/当前 PRD 有尚未收入的变化，必须先起草一张 CR 并收入 PRD（PRD 已 Approved/Baselined 时按变更流程升补丁版本，不覆盖旧基线）。没有此类改动则在 WORKLOG 写明“本批无待收口 PRD 变更”。纯实现细节不写入 PRD。未完成该盘点不得把下一批次升为 In Progress。

前端批次：

- UI_CONSTRAINT_MODE=NONE 时不生成正式 UI Contract，不得因此阻断 Ready。
- 存在有效 UI_SPEC 时，按 shared、前端应用、设备、功能模块、
  页面顺序合并生成 EFFECTIVE_UI_CONTRACT。
- 开发人员不需要自行拼接多层规范，以 EFFECTIVE_UI_CONTRACT 为当前批次唯一有效 UI 入口。
- EFFECTIVE_UI_CONTRACT 必须记录每条规则的来源层级、规范版本和素材编号。
- 同时生成 VISUAL_ACCEPTANCE 和 REFERENCE_MANIFEST。

二十四、需求变更和版本
==================================================

任何已批准需求的新增、修改或废弃不得静默覆盖。

流程：

新资料或诉求
→ SRC-CHANGE
→ CR
→ 影响分析
→ 知情决策评审
→ 影响复述和二次确认
→ DEC/ADR/UI-DEC 受控应用
→ 新版本 Draft
→ In Review
→ Approved
→ 同步技术设计、UI 目录、UI_SPEC、批次和测试
→ Baselined

不同阶段：

- 资料投放中：作为新批次登记。
- PRD Draft/In Review：先登记 CR；CR 内决策按 IDP 确认和应用后，
  才修改当前版本并重新审计。
- PRD Approved：保留已批准版本；变更范围和版本级别按 IDP 确认后，
  才创建新版本 Draft。
- PRD Baselined：原基线只读；范围、兼容、迁移和回滚按 IDP 确认后，
  新版本重新走完整流程。
- 开发中实现偏离需求：缺陷。
- 目标业务行为改变：登记 CR，业务选择按 IDP 完成后应用。
- 开发批次结束：盘点本批逐条改动；已确认业务行为已偏离当前 PRD 且尚未收入时，必须先起草一张 CR 并收入 PRD，再进入下一批次。无此类改动则记录后继续。
- PRD 歧义：登记澄清型 CR，裁决按 IDP 完成。
- 技术实现变化但业务不变：按 IDP 确认后形成 ADR 或技术设计变更。
- 纯 UI 变化：按 IDP 确认后形成 UI-DEC 和 UI_SPEC 新版本；
  影响业务时升级为 CR。
- 已上线常规变更：登记 CR，决策内容按 IDP 完成。
- 可选变更稿：第 39A 节铺路一次；第 39B 节只写临时袋；第 39C 节按当前 PRD 状态走本节上列 Draft/Approved/Baselined 路径纳入。未纳入草稿不得当成已应用决策。
- 紧急变更：可在用户或预先批准的事件响应机制明确授权后执行最小止损
  并登记 HOTFIX-CR；事前授权至少明确故障对象、最大修改范围和回滚点，
  不得以沉默或模糊表达代替授权，不得无授权扩大范围；
  上线后补齐 IDP 二次确认证据、文档和追踪。

版本规则：

- v1.0.1：不改变行为的修正和澄清
- v1.1：向后兼容的新功能或增强
- v2.0：不兼容业务、状态、权限、资金或数据归属变化

旧基线不得覆盖。

÷
Σ（当前版本计划文档权重）

Not Started=0

÷

已验收工作项权重
÷
当前版本全部工作项权重

4. PR 创建不等于合并。
5. 合并不等于发布。
6. 发布不等于验收完成。

12. Capability 激活不是 Evidence；必须能追溯到 Trigger 和来源。
13. Stage 完成必须同时满足 Exit 条件和 Evidence 要求。
14. UI 规范关闭时不计入文档计划分母。
15. UI 规范启用后按实际计划纳入进度。
16. 开发批次结束时，未完成“逐条改动 → CR → 收入 PRD”盘点（或已记录本批无此类改动）前，不得把下一批次进度当作已开工。

7. 新决定替代旧决定时保留记录。
8. 缺少信息时不得虚构。
9. 未经批准不得跨越阶段。
10. 每次完成后报告当前阶段、修改文档、新增来源和决策、
