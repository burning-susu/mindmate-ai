## 1. 使用原则

v3.1 由两个部分组成：

1. 主提示词：建立长期有效的项目文档规则、目录、阶段门禁和追踪体系。
2. 阶段提示词：在具体阶段告诉 AI 当前输入、允许动作和预期输出。

推荐使用顺序：

1. 首先发送《通用文档提示词v3.2.md》中的完整主提示词。
2. 然后根据当前项目阶段，从本文选择对应的阶段提示词。
3. 每次只执行一个明确阶段或一个开发批次。
4. 不要同时发送互相冲突的阶段提示词。
5. 提示词中的 `{{变量}}` 必须替换为真实值；未知值保留 `TBD`。
6. 如果 AI 当前对话已经加载并遵循主提示词，可以只发送对应的阶段提示词。
7. 第 18～19 节的安全默认模式仍为 `MANDATORY`，但“MANDATORY”约束的是决策真实性和正式阶段出口，不再机械要求所有技术决策在 Draft 前完成确认。
8. G6 可按第 2E 节先生成受控 Draft：先建立 TECH_DECISION 清单、候选/组合分析、Blocking/Deferable 和 Assumption/TBD。只有把 Proposed 结论升级为正式决定、或进入依赖该 Blocking 决策的下游门禁时，才必须完成确认与应用。
9. Cursor 的 Plan/Agent 交互模式与本文的架构参与模式是两套机制；是否切换 Cursor 模式不代表用户放弃架构决策权。
10. 所有需要用户选择、裁决、批准或授权状态变化的提示词，均须按第 2A 节知情决策协议执行。知情决策只写在会话正文，禁止弹框/问卷卡。
11. 会话中的初次文字选择只代表候选意向；AI 完成影响复述且用户二次确认后，才能进入写入步骤。关闭弹框、只点一次选项不构成初选或确认。
12. 新对话窗口没有上一窗聊天记忆。续做时发送第 1A 节提示词，以 `{{DOC_ROOT}}` 下看板、待确认问题和已应用 DEC 为准，不要另建口头语流水账。
13. 每个开发批次结束时，若本批有已确认的逐条业务改动尚未写入 PRD，必须先按第 36A 节起草 CR 并收入 PRD，再开始下一批次。

## 1A. 新窗口继续工作

### 提示词使用说明

关闭当前对话、新开窗口、换模型或隔一段时间再继续时使用。AI 不会自动记得上一窗内容。进度真源是 `{{DOC_ROOT}}` 里已写入的看板、待确认问题、已应用 DEC/ADR/CR 和工作日志，不是聊天记录。

不要为续聊单独维护「口头语」文档。未二次确认的口头约定不得写成 DEC。

每次只续做文档标明的**下一步一项**（高影响每轮 1 项）。不要重做 G0，不要重放已冻结资料，不要在 P0/P1 未清时生成 PRD。

```text
请完整加载并严格遵循：
@docs/governance/common_prd_v3.2/通用文档提示词v3.2.md
中的「主提示词」全文，以及
@docs/governance/common_prd_v3.2/通用文档提示词v3.2完整使用说明.md
中的阶段门禁和第 2A 节知情决策协议。
功能描述按第 2A 节人话 6 问。

这是新对话窗口续做，不是新项目初始化。

文档根目录：{{DOC_ROOT，默认 docs/project/}}
进度数据真源：{{DOC_ROOT}}/progress/PROGRESS_REGISTER.yaml
人类可读进度：{{DOC_ROOT}}/progress/PROJECT_DASHBOARD.md
待确认问题：{{DOC_ROOT}}/baseline/05_PENDING_QUESTIONS.md
已应用决策：{{DOC_ROOT}}/baseline/DEC-*.md（以及 decisions/ 下已批准项）

请先只读上述文件和项目变量 {{DOC_ROOT}}/PROJECT_VARIABLES.md，然后：

1. 用一两句话汇报：当前 PROJECT_STAGE、已应用 DEC 编号、剩余 P0/P1、文档标明的下一步。
2. 只执行该「下一步」一项。高影响走 INFORMED_REVIEW，只读，不写 DEC，不生成 PRD。
3. 不要重做 G0/G1，不要重写已冻结来源，不要作废已应用 DEC。
4. 不要根据「可能聊过」的内容补写口头结论；只采用已写入文档的结论。
5. ALLOW_CODE_CHANGES 以项目变量为准；文档阶段不得改业务代码。

若看板上一步是知情评审，直接进入该项 INFORMED_REVIEW。
若看板上一步是用户已选方案待二次确认，停留在 INFORMED_CONFIRMATION，不要 APPLY。
若看板上一步是已确认待应用，且用户本条已给出「确认该决策」口令，才进入 DECISION_APPLY。

若存在 {{DOC_ROOT}}/changes_temp/BAG.md：先用一两句话汇报临时袋状态（开着与否、未纳入条数）。袋内草稿不得当成已应用的 DEC/CR。
```


## 1B. 项目定制化流程路由

### 提示词使用说明

新项目、已有项目继续、需求变更、缺陷修复、重构或发布前需要判断“本次到底该走什么治理深度”时使用。

本节不是新的生命周期阶段，而是 G0～G11 之外的跨阶段路由机制。

核心顺序：

```text
Scenario
→ PROJECT_PROFILE
→ ASSESSMENT
→ CAPABILITY ACTIVATION
→ WORKFLOW_BLUEPRINT
→ USER_CONFIRMATION
→ G0～G11
```

不要把项目分级简化成一个总分。`Scale` 只描述规模；`Risk`、`Lifecycle`、`Scenario`、`Delivery`、`UI` 等维度共同影响能力和阶段深度。

```text
建立项目画像
→ 标记 CONFIRMED / PROVISIONAL / TBD
→ 计算 Assessment
→ 输出 Trigger
→ 激活 Required/Conditional Capability
→ 生成 Stage Policy
→ 生成 Workflow Blueprint
→ 对会改变强制门禁的差异按第 2A 节确认
→ 写入当前 Workflow
```

### 可复制提示词

```text
请建立当前项目的 v3.2 PROJECT_PROFILE，并基于已提供资料完成治理评估。

先只读：
- 当前项目文档根目录
- PROJECT_VARIABLES.md
- 当前 SOURCE_REGISTER
- 当前 baseline/ 中已确认内容
- 当前代码现状（如已有代码且允许读取）

请输出：
1. PROJECT_PROFILE：
   - scenario
   - project_type
   - lifecycle
   - scale
   - business
   - risk
   - technology
   - ui
   - delivery
2. 每项标记 CONFIRMED / PROVISIONAL / INFERRED / TBD。
3. 生成 ASSESSMENT：
   - complexity
   - risk dimensions
   - HARD/SOFT/INFO triggers
   - Trigger 来源和理由
4. 生成 Capability 候选：
   - REQUIRED
   - CONDITIONAL
   - OPTIONAL
   - DISABLED
5. 识别哪些 TBD 会改变 Workflow；只询问这些问题。
6. 不生成代码。
7. 未完成评估和确认前，不得把候选 Workflow 当成当前正式 Workflow。
```

## 1C. Workflow Blueprint 确认

### 提示词使用说明

项目 Profile 和 Assessment 已建立后使用。

Workflow Blueprint 必须基于统一 G0～G11 骨架生成，不得复制一套独立生命周期。

```text
请基于当前：

- PROJECT_PROFILE
- ASSESSMENT
- CAPABILITY_ACTIVATION
- 当前 Baseline
- 当前交付目标

生成 WORKFLOW_BLUEPRINT Draft。

要求：
1. 保留 G0～G11 生命周期骨架。
2. 为每个阶段设置 L0～L4 执行级别。
3. 列出当前启用 Capability 及其适用阶段。
4. 列出额外 Gate、Evidence 和依赖。
5. 明确哪些阶段保持、弱化、增强或按条件启用。
6. 解释每个非默认差异的来源和触发原因。
7. 不静默删除资金、权限、安全、隐私、生产等强制治理门禁。
8. 不修改 PRD、ADR、CR 或代码。
9. 当前状态只能为 Draft / In Review。
```

确认口令：

```text
确认当前 WORKFLOW_BLUEPRINT：
{{WORKFLOW_ID}}={{VERSION}}
限制条件：{{CONSTRAINTS 或 NONE}}
```

只有完成必要的知情确认后，才能将其状态改为 `CONFIRMED/ACTIVE`。

## 2. v3.2 阶段总览

```text
G0    文档初始化
G1    资料投放
G2    来源和决策基线
G3    PRD 准入审计
G4    PRD Draft
G5    PRD 评审和批准
G5.5  根据 PRD 同步 UI 逻辑范围
G6    总体技术架构

G11   开发、测试、发布和维护
```

其中：

- `G5.5` 默认执行，只建立 UI 逻辑范围，不确定真实应用目录名。
- `G6` 默认使用结构化技术决策分析；允许在输入成熟度足够时先生成受控 Draft。Blocking TECH_DECISION 必须在 G6 正式出口、Approved/Baselined 或依赖该结论的下游门禁前完成确认和应用。
- `G7` 默认继承 G6 参与模式，模块拆分争议未确认时不能静默生成 MODULE_BOUNDARIES。
- `G9.1` 根据已确认的应用架构和 `PROJECT_STRUCTURE.md` 生成正式应用目录。
- `G9.5` 是可选阶段。
- 不投放 UI 素材、不生成 UI_SPEC，也可以继续开发。
- 一旦某个批次声明使用 UI 规范，该批次必须使用合并后的 `EFFECTIVE_UI_CONTRACT.md`。
- G2、G5、G6、G7、G9.5、CR 和 UI 冲突中的所有决策问答均遵循第 2A 节。
- 变更稿（第 39A～39C 节）是可选会话模式，不是新的 G 阶段，不得改写 `PROJECT_STAGE`。一人做到底可不用。

## 2A. 知情决策全局协议

本协议简称 `IDP`。

### 适用范围

凡需要用户选择方案、裁决冲突、确认候选、批准版本、接受风险或授权状态变化，
均必须执行本节。包括但不限于：

- P0/P1 冲突和候选需求；
- 架构参与模式、G6 架构决策和 G7 模块边界；
- UI 规范、素材替代、高保真等级和 UI-CONFLICT；
- CR、DEC、ADR、UI-DEC、Approved、Baselined 和阶段门禁。

纯事实收集问题不要求提供多个方案，但 AI 必须先说明为什么需要该信息、
接受什么格式、未知时是否可以保留 `TBD`。事实回答会改变业务结论或状态时，
仍须转入完整知情决策流程。

凡描述功能（知情决策、CR、对 bug 说话）：人能碰到的行为，或系统办完后人在某页能看见的结果，
必须按本节人话 6 问写完。不约束表结构、接口路径、SQL 编号、部署。

推荐项目变量：

```text
INFORMED_DECISION_MODE=MANDATORY
```

`SIMPLIFIED` 仅可由用户明确启用并用于低影响决策；高影响决策不能简化。
本协议没有 `OFF` 模式。

### 影响分级和每轮数量

高影响决策包括：

- 金额、支付、退款、分账、结算；
- 账号、身份、权限、数据范围、隐私和安全；
- 状态机、数据归属、删除、迁移和不兼容变更；
- PRD 业务规则、总体架构、模块边界；
- Approved/Baselined、跨阶段门禁和生产风险。

高影响决策每轮只允许 1 项。低影响、可逆且不改变业务语义的决策每轮最多 2 项。
不得在同一轮混合高影响和其它决策。
同轮包含 2 个低影响决策时，必须为每项分配独立决策 ID，
分别提问、分别复述、分别二次确认，并在 APPLY 中逐项列明；
不得用一次合并确认替代两个独立确认。

### 阶段一：INFORMED_REVIEW

知情决策必须写在**当前会话窗口的正文消息**里。禁止弹框、问卷、结构化选项表、原生确认卡片、IDE 表单或把选项收成「点一下」的控件。关闭弹框、取消表单、只点一次选项，不构成初选或确认。

在本会话提出选择问题前，AI 必须按下列结构写完，缺一块不得提问：

1. **决策背景与问题描述**：决定什么；当前卡在哪；不决定会阻塞什么；相关 PRD、来源、DEC、ADR、现码事实和治理门禁。
   若本决策涉及「功能」（人能碰到的行为，或系统办完后人在某页能看见的结果），本块必须含紧挨着的「功能在哪看到」，并强制套下面人话 6 问；缺一问不得提问。禁止只用字段名、文件名当背景。表结构、接口路径、SQL 编号、部署不受此约束。

   **功能在哪看到 / 人话 6 问**（知情决策、CR、对 bug 说话，凡描述功能都用这一套）：

   1. 哪一端、哪一业态：平台后台 / 商家后台 / 店小程序 / 共益优选 / 入驻 H5。多端分行。四业态不同就分行。禁止只写「系统里」「后台」。
   2. 谁，或谁也不用点：人写身份；机器写「不用人点，支付成功后 / 每天跑批后」。
   3. 怎么走进来：后台写侧栏「一级 → 二级 → 页签」（现码菜单名）；小程序写底部或「我的 / 订单」；H5 写从哪页哪个按钮进来。没有入口写「现在无处可进」或「侧栏没有但还能打开某页」。名称吃不准就写页面标题并标明待核对。
   4. 人在哪看见：列表哪一列、详情哪一段、哪个按钮、哪句文案、导出文件哪一列、哪条短信。没有界面就写「过程看不见，结果在【哪一端哪一页哪一块】能看见」。
   5. 怎么操作，或怎么触发：从打开到看见的步骤；要哪类单据。自动任务写什么事件触发。删功能写现在怎么点还能看见它。无权限、没数据时分别怎样。
   6. 现在怎样 / 改完怎样：只写眼睛（或短信、导出文件）看到的变化。删除：现在能看见什么，改完这里不该再有。字段名必须出现时放括号里。

   短句模板：
   【哪一端·哪业态】里，【谁 / 不用人点】，从【怎么走进来】到【人在哪看见】。【怎么操作或触发】之后：现在是……；改完是……。
2. **生动形象的解释**：白话讲清术语；高影响项至少给一个能对照真实用户/商家/平台的生活化例子或完整运行流程。生动例子必须能按人话 6 问走一遍；禁止只用字段名、文件名当背景。
3. **备选方案对比**：普通非技术决策使用少量、差异清晰的真实可行方案；TECH_DECISION 的候选数量不固定，必须覆盖实质可行候选，并先判断互斥、可替代、依赖和互补关系。存在有意义的组合时，把 `A+B`、主辅组合或分层方案作为可比较方案。不得为凑数制造伪候选。每个保留方案按适用范围说明：
   - 实际运行方式以及谁调用谁；
   - 数据、状态和权威写入方归谁；
   - 模块、系统、第三方和基础设施依赖；
   - 事务、一致性、幂等、补偿和失败结果；
   - 具体优点、缺点和主要风险；
   - 开发成本、认知复杂度、运维复杂度和性能影响；
   - 交付、兼容、迁移和现有数据影响；
   - 测试、发布、灰度、降级和回滚方式；
   - 安全、隐私、审计和合规影响；
   - 适用条件和不适用条件。
4. **推荐选择与核心理由**：写明推荐哪一案或哪一组合、为什么推荐、为什么不选其它仍可行方案；组合推荐必须说明各组件职责和组合必要性。不得用「推荐」二字代替理由。
5. **开发技术决策清单**：若选各案（至少覆盖推荐案），编码要改什么、不改什么、在哪个批次改、本窗是否允许改代码；待配置不得编造。

确实不适用的维度标记 `N/A` 并说明原因。不得仅给出短选项名称。

每个决策说明完成后只提出一个明确问题，请用户**在本会话用文字**回复方案字母或 `决策ID=方案`；同一轮包含两个低影响决策时，分成两个编号问题，不得合并成一个含糊问题。用户可以选择方案，也可以回复：

```text
继续解释
换个生活化例子
重点比较方案 A 和方案 B
暂不决定
```

用户要求解释时，AI 只补充当前决策，不推进下一项、不修改文件。

### 阶段二：INFORMED_CONFIRMATION

用户第一次选择只是候选意向。AI 必须先只读复述：

1. 决策 ID 和主题；
2. 选择的方案；
3. 用户增加的限制条件；
4. 被拒绝的方案；
5. 对业务、数据、架构、UI、安全、成本、交付、迁移、测试、
   发布和回滚的影响；
6. 继续为 `TBD` 或延期的事项。

然后只提出一个二次确认问题。推荐确认格式：

```text
确认该决策：
{{DECISION_ID}}={{SELECTED_OPTION}}
限制条件：{{CONSTRAINTS 或 NONE}}
```

以下情况不构成确认：

- “倾向于”“可以考虑”“差不多”“先这样”“你决定吧”；
- 用户表示不理解、要求继续说明或要求换例子；
- 取消问卷、关闭弹框、跳过、暂停、沉默、撤回选择或切换话题；
- 只点击一次选项或使用结构化表单点选，但 AI 尚未在会话正文复述影响；
- AI 根据推荐项或历史偏好自行推断。

发生上述情况时，当前项保持候选或 `TBD`，不得写入 DEC、ADR、CR、
UI-DEC，不得提高评审、批准或阶段状态。

### 阶段三：DECISION_APPLY

只有完成二次确认且用户明确授权应用后，才能执行写入：

1. 按类型写入 DEC、ADR、CR、UI-DEC 或受控决策登记。
2. 只应用已经解释和确认的范围，不扩大选择含义。
3. 发现新权衡时停止应用，回到 `INFORMED_REVIEW`。
4. 部分应用标记 `PARTIAL`。
5. 全部必选项完成确认和应用后，才能标记相关状态 `COMPLETED`。
6. APPLY 阶段不继续提出新的决策问题。

业务规则使用 DEC，技术和架构决策使用 ADR，纯视觉决策使用 UI-DEC，
业务行为变化使用 CR；不得用错误记录类型绕过门禁。

### 标准顺序

```text
DISCOVERY
→ INFORMED_REVIEW
→ INFORMED_CONFIRMATION
→ DECISION_APPLY
```

前两个阶段默认只读，不修改正式文档、项目变量和进度状态。
如果用户直接发出明确批准口令，只有在该版本、范围和影响已经完成评审及复述时，
才可视为二次确认和应用授权；否则先补充知情决策说明。

## 2B. 项目评估模型

Assessment 不使用单一总分决定流程。

维度至少包括：

```text
Scale
Requirement Complexity
Technical Complexity
Business Risk
Financial Risk
Privacy/Security Risk
Platform Risk
Data Risk
Offline/Geo Risk
Delivery Risk
UI/Visual Risk
External Dependency
```

每个维度：

```text
LOW
MEDIUM
HIGH
CRITICAL
TBD
```

Assessment 输出：

1. 当前复杂性描述。
2. HARD / SOFT / INFO Trigger。
3. Capability 激活集合。
4. Stage Policy。
5. 未知项。
6. 会改变 Workflow 的关键 TBD。

规则：

- Scale 只描述规模。
- Risk 独立于 Scale。
- `HIGH/CRITICAL` 风险不能因为项目规模小而自动关闭强制治理。
- 没有来源的评估不得写成 CONFIRMED。
- Assessment 被上游资料、Baseline 或交付目标影响后标记 `STALE`。

## 2C. Capability、Stage Contract 和 Runtime Context

### Capability

Capability 是专项能力，不是第二套生命周期。

典型 Capability 类型可以包括：

- 平台交付能力
- UI 实现能力
- 自动化测试
- 性能测试
- 安全
- 数据迁移
- 离线能力
- 监控和生产发布

具体能力来自能力库或项目已确认的专项规范。

### Stage Contract

每个阶段至少回答：

```text
这个阶段为什么存在？
什么时候可以进入？
必须读什么？
可以做什么？
不能做什么？
要产出什么？
什么证据才能证明完成？
什么时候可以退出？
失败后如何恢复？
```

### Runtime Context

每次开始一个实际动作前读取：

```text
Project Profile
→ Assessment
→ Workflow
→ Current Stage
→ Capability
→ Rules
→ Baseline
→ Permission
→ Evidence Requirements
```

工作模式和权限分离：

```text
READ_ONLY
PLAN_ONLY
DOC_WRITE
CODE_WRITE
REVIEW
RELEASE
```

不允许因为工作模式变化而自动扩大写入路径、代码范围、Git、数据库或发布权限。

## 2D. Workflow Change / Rebase

以下情况应触发 Workflow 重新评估：

- 项目目标变化
- 交付目标变化
- 风险升级
- 新增高影响能力
- 技术架构变化
- 现有 Workflow 覆盖不足
- 原 Profile 被新资料推翻

标准：

```text
CHANGE SIGNAL
→ ASSESSMENT UPDATE
→ IMPACT ANALYSIS
→ WCR
→ IDP
→ WORKFLOW v2
→ REBASE
→ RUNTIME_CONTEXT UPDATE
```

Rebase 标记：

```text
KEEP
REVALIDATE
INVALIDATE
ADD
REMOVE
```

没有完成 Rebase 前，旧 Workflow 仍然有效。

## 2E. 受控文档提前产出与 TECH_DECISION

### 2E.1 为什么需要提前 Draft

现实项目中，公司可能在需求尚未 100% 收敛时就需要技术方案、技术栈说明、资源预估或评审材料。v3.2.1 将“**能否写 Draft**”与“**能否把结论当正式基线执行**”分开：

```text
Draft Readiness
≠
Stage Exit / Approved / Baselined Readiness
```

阶段 Gate 继续控制批准、基线、下游正式依赖和代码执行；但 Gate 不再被解释为“此前一字不能写”。

### 2E.2 受控提前产出的最低条件

满足以下条件即可生成工作 Draft：

1. 已有来源足以说明项目目标、主要用户/场景或当前问题；
2. 当前事实能够支撑有意义的技术分析，而不是只生成空模板；
3. `Confirmed / Provisional / Assumption / Inferred / TBD` 已区分；
4. 会导致完全不同系统形态的重大业务矛盾已经识别；
5. 输出目的只是分析、沟通或评审，不冒充 Approved/Baselined；
6. 所有未确认内容都能追溯到开放项或 TECH_DECISION。

以下情况仍应 BLOCKED：
- 项目目标本身未知，无法判断系统类型；
- 两个未裁决业务规则会导致互斥的总体架构，而文档又要求给出单一“最终方案”；
- 用户要求直接写成 Approved/最终结论，但相应 Blocking 决策尚未确认；
- 用户要求据 Draft 直接实施高风险代码/数据/生产变更，正式门禁尚未满足。

### 2E.3 Draft 元信息

提前产出的文档至少写：

```text
status=Draft
generation_context=EARLY_DRAFT
input_maturity=PARTIAL|SUFFICIENT
open_assumptions=[...]
blocking_tech_decisions=[...]
deferable_tech_decisions=[...]
```

推荐内容使用 `Proposed`；已确认内容使用 `Confirmed`；未知使用 `TBD`。

提前 Draft **不会**：
- 自动改变 `PROJECT_STAGE`；
- 自动把 Workflow 向后推进；
- 自动提高 Review/Apply 状态；
- 自动获得代码写入、数据库或发布权限。

### 2E.4 TECH_DECISION

技术选型分析使用 `TECH-DEC-XXX`。不要使用 `TD-XXX`，因为 `TD-XXX` 在现有体系中已经表示模块技术设计。

标准分析链：

```text
技术领域
→ 决策问题
→ 项目实际需求/约束
→ 候选发现
→ 单项方案分析
→ 技术层次识别
→ 兼容/互斥/依赖分析
→ 组合方案构建
→ 方案比较
→ 当前推荐
→ 项目影响
→ 待确认/最晚确认点
→ 状态
```

规则：

1. 候选数量不固定。只列实质可行候选，不凑数，也不遗漏明显可行项。
2. 如果只有一个可行候选，说明其它常见方案的排除原因。
3. 先判断技术是否处于同一层次；协议、规范、实现库、展示工具和协作工具可能是互补关系。
4. 有效组合（如 A+B、主辅组合、分层组合、阶段性组合）本身要作为方案比较。
5. 推荐可以是单项，也可以是组合；组合必须写清每个组件职责。
6. 每个 TECH_DEC 标记 `BLOCKING / DEFERABLE / INFORMATIONAL` 和最晚确认点。
7. Draft 推荐状态为 `PROPOSED`；需要成为正式项目决定时再按第 2A 节确认和应用。
8. 已确认且构成长期架构约束的结果写入 ADR；TECH_DECISION 保留候选和取舍分析，不与 ADR 维护两套冲突结论。
9. 技术栈总览只能从 TECH_DECISION/ADR 汇总产生。

### 2E.5 上游变化后的复核

需求、预算、平台、团队、交期或其它技术决定变化时：

```text
CHANGE
→ 找出受影响 TECH_DECISION
→ KEEP / REVALIDATE / INVALIDATE / ADD / REMOVE
→ 重算受影响候选/组合
→ 更新 Draft
→ 必要时更新 ADR 和下游设计
```

不无差别推倒重写整套技术文档。

### 2E.6 配套通用资产

仓库存在以下资产时，技术选型应按需读取：

```text
doc/handbook/architecture/通用技术架构选型说明书_公司版_V3.2.md
doc/capabilities/architecture/technical-selection.md
doc/templates/TECH-DECISION-TEMPLATE.md
```

这些文件提供方法和模板，不是当前项目的技术事实。

```text
当前还不知道最终项目类型，也没有开始投放资料。

PROJECT_STAGE=BOOTSTRAP
```

## 5. 投放历史需求资料

### 提示词使用说明

投放旧版 PRD、旧需求说明、历史会议记录或已经废弃的材料时使用。必须明确它们只是历史参考，避免 AI 把旧行为自动当成新需求。

# 第四部分：总体架构和技术设计

## 18. 生成总体技术架构

### 提示词使用说明

本节用于形成和收敛总体架构。v3.2.1 不再要求“PRD 必须已经 Approved 才能写任何架构内容”，而是区分两类门禁：

1. **Draft Readiness**：当前输入是否足以形成有意义的架构/技术选型 Draft；
2. **G6 Exit / Approval Readiness**：Blocking 技术决策是否已经确认并应用，是否可以把 Draft 升级为正式技术基线并让下游依赖。

因此：
- PRD 尚未 Approved，但主要范围、关键场景和架构约束已足够时，可以按第 2E 节生成 `EARLY_DRAFT`；
- `Approved/Baselined`、G6 正式出口以及依赖 Blocking 技术结论的下游动作仍受严格门禁；
- 提前 Draft 不改变 `PROJECT_STAGE`。

### 架构参与控制变量

推荐安全配置：

```text
ARCHITECTURE_PARTICIPATION_MODE=MANDATORY
ARCHITECTURE_DECISION_REVIEW_STATUS=NOT_STARTED
ARCHITECTURE_DECISION_APPLY_STATUS=NOT_STARTED
ALLOW_ARCHITECTURE_DRAFT_WITH_TBD=true
EARLY_DOCUMENT_OUTPUT_POLICY=CONTROLLED_DRAFT
TECH_DECISION_METHOD=STRUCTURED
```

状态解释：

- `REVIEW_STATUS=NOT_STARTED`：尚未形成完整必选技术决策清单；
- `REVIEW_STATUS=IN_PROGRESS`：TECH_DECISION 已建立，仍有需要确认的 Blocking/Deferable 项；
- `REVIEW_STATUS=COMPLETED`：当前 G6 Exit 所需 Blocking 决策全部完成影响复述和二次确认；
- `APPLY_STATUS=NOT_STARTED/PARTIAL`：确认结果尚未或只部分写入正式受控记录/ADR；
- `APPLY_STATUS=COMPLETED`：当前 G6 Exit 所需 Blocking 决策已经全部应用；
- 任一状态为 `STALE`：上游变化，需要 Revalidation。

**生成 Draft 本身不再要求 REVIEW/APPLY 都为 COMPLETED。** 这些状态主要约束正式结论、阶段出口和依赖它们的下游动作。

### 步骤一：检查 Draft Readiness

```text
进入 ARCHITECTURE_DRAFT_READINESS。

本次只读，不修改项目阶段、决策状态或代码。

请读取：
- 当前需求/PRD及状态；
- 来源和 Pending Questions；
- PROJECT_PROFILE / ASSESSMENT；
- 现有代码/架构事实（如有）；
- 已确认 DEC/ADR；
- 公司架构手册与 technical-selection Capability（如存在）。

请输出：
1. 当前 input_maturity=INSUFFICIENT / PARTIAL / SUFFICIENT / COMPLETE。
2. 已确认事实、Assumption、Inferred、TBD。
3. 哪些未知会导致总体架构完全不同。
4. 当前是否足以生成 EARLY_DRAFT。
5. 如果可以，列出 TECH_DECISION 初始清单：
   - TECH-DEC ID
   - 技术领域/决策问题
   - impact=HIGH/LOW
   - blocking=BLOCKING/DEFERABLE/INFORMATIONAL
   - 最晚确认点
   - 当前状态
6. 不把推荐写成 Confirmed。
7. 不修改 PROJECT_STAGE。
```

`INSUFFICIENT` 时停止并说明缺什么；`PARTIAL/SUFFICIENT` 且能够形成有意义分析时可继续 Draft。

### 步骤二：建立技术决策清单和候选/组合分析

```text
进入 ARCHITECTURE_TECH_DECISION_ANALYSIS。

本轮允许创建/更新 TECH-DEC-XXX 分析稿，但不创建代表最终结论的 ADR。

基于当前项目事实，识别重要技术领域，例如：
- 客户端/小程序框架；
- Web 前端；
- 后端语言/框架与应用形态；
- 数据库；
- ORM/数据访问和 Schema migration；
- 对象存储；
- API 风格；
- API 契约、生成、展示和调试工具链；
- 认证、Token、Session、权限；
- 缓存、锁、消息和任务；
- 部署、网关、监控、容灾和回滚；
- 测试技术。

对每个需要实际决策的领域：
1. 先写“项目真正要解决什么问题”。
2. 列出所有实质可行候选，数量不固定。
3. 若只有一个可行候选，说明其它常见候选为何被排除。
4. 判断候选是否同层竞争，还是存在互补/依赖关系。
5. 构建有意义的组合方案：A+B、主辅、分层或阶段性方案。
6. 从数据归属、依赖、事务、安全、成本、复杂度、性能、交付、迁移、测试、发布和回滚比较。
7. 给出当前推荐，可以是单项或组合，但状态只能是 PROPOSED。
8. 标记 BLOCKING / DEFERABLE / INFORMATIONAL 和最晚确认点。
9. 检查与其它 TECH_DECISION 的兼容性。
10. 不生成“先拍脑袋的技术栈总览”。
```

### 步骤三：生成受控总体架构 Draft

当 Draft Readiness 通过且重要 TECH_DECISION 已至少形成分析后，可以生成 Draft，不要求 Blocking 决策已经全部确认：

```text
生成总体技术架构 Draft。

generation_context={{EARLY_DRAFT 或 STAGE_DRAFT}}
status=Draft
ALLOW_ARCHITECTURE_DRAFT_WITH_TBD=true

要求：
1. 生成/更新：
   - SYSTEM_CONTEXT
   - OVERALL_ARCHITECTURE
   - SECURITY_ARCHITECTURE
   - DEPLOYMENT_ARCHITECTURE
   - NON_FUNCTIONAL_REQUIREMENTS
   - TECH_DECISION 清单/明细
2. 每个技术结论显示来源和状态：Confirmed / Proposed / Assumption / TBD。
3. 技术栈总览必须从 TECH_DECISION 汇总；每项显示 TECH-DEC ID 和状态。
4. 组合方案必须写清各组件职责，不允许把不同层次工具错误做成单选。
5. 列出 Blocking、Deferable、最晚确认点和风险。
6. 未确认推荐不得写入正式 ADR。
7. 如果当前属于 EARLY_DRAFT，不改变 PROJECT_STAGE。
8. 不自动标记 Approved/Baselined。
9. 不生成依赖尚未确认 Blocking 结论的正式开发批次或代码。
```

### 步骤四：按需要进行 TECH_DECISION 知情评审

不要求“为了生成第一版 Draft 就把所有问题一次问完”。优先评审：
- 当前用户希望确认的技术选择；
- 阻断 G6 Exit 的技术选择；
- 即将被下游设计/开发依赖的技术选择。

高影响 TECH_DECISION 按第 2A 节每轮 1 项。低影响可逆工具选择按治理规则最多 2 项。

每项评审应说明：
- 决策问题；
- 当前项目约束；
- 候选与组合；
- 推荐及理由；
- 为什么不选其它仍可行方案；
- 数据、依赖、事务、安全、性能、成本、交付、测试、迁移和回滚影响；
- 重新评估触发条件。

用户初次选择后停止，进入 `ARCHITECTURE_DECISION_CONFIRMATION`。

### 步骤五：确认与应用

```text
进入 ARCHITECTURE_DECISION_CONFIRMATION。

本次不修改正式结论。
请复述：
1. TECH-DEC ID 和决策主题；
2. 用户选择的单项或组合；
3. 限制条件；
4. 未选择方案；
5. 对项目和其它 TECH_DECISION 的影响；
6. 仍保持 TBD/Deferable 的内容。
等待“确认该决策”。
```

完成二次确认后：

```text
进入 ARCHITECTURE_DECISION_APPLY。

只应用已经完成确认的 TECH_DECISION。

要求：
1. 将 TECH_DECISION 状态更新为 CONFIRMED/APPLIED。
2. 对形成长期架构约束的决定创建或更新唯一 ADR。
3. ADR 引用对应 TECH-DEC，不重新复制一套候选分析。
4. 同步受影响架构章节和技术栈总览。
5. 不应用未确认的推荐。
6. 部分应用保持 REVIEW_STATUS=IN_PROGRESS / APPLY_STATUS=PARTIAL。
7. 当前 G6 Exit 所需 Blocking 决策全部确认并应用后，才设为 COMPLETED。
```

### 步骤六：G6 Exit / Approval 门禁

准备把架构作为正式下游输入、标记 Approved/Baselined 或进入依赖 Blocking 技术结论的阶段时，执行：

```text
进入 ARCHITECTURE_EXIT_PREFLIGHT。

验证：
1. PRD/业务基线是否达到当前 Workflow 对 G6 Exit 的要求。
2. 所有 G6 Exit 所需 Blocking TECH_DECISION 是否 CONFIRMED/APPLIED。
3. ARCHITECTURE_DECISION_REVIEW_STATUS 是否 COMPLETED。
4. ARCHITECTURE_DECISION_APPLY_STATUS 是否 COMPLETED。
5. 技术栈总览是否全部可追溯到 TECH_DECISION/ADR。
6. 是否存在互相冲突的单项推荐或组合方案。
7. Deferable 项是否有明确最晚确认点且不阻塞下一阶段。
8. Assumption 是否仍有效。
9. 架构文档是否与当前需求、代码事实和 ADR 一致。

输出 PASS / BLOCKED。
BLOCKED 时只列阻断项和正确下一步，不提高文档状态。
```

只有该门禁 PASS 后，才可以按知情决策协议把架构升级为 Approved/Baselined 或让后续正式产物把这些结论作为强约束。

### 步骤七：上游变化后的 Revalidation

如果提前 Draft 之后需求或约束发生变化，不删除 Draft：

```text
进入 ARCHITECTURE_REVALIDATION。

1. 找出受影响 TECH_DECISION。
2. 标记 KEEP / REVALIDATE / INVALIDATE / ADD / REMOVE。
3. 将失效决定标记 STALE，不静默覆盖历史。
4. 只重算受影响候选、组合和架构章节。
5. 已确认 ADR 受影响时进入正式架构变更流程。
6. 更新技术栈总览状态。
```

## 36A. 结束开发批次时收口 PRD

### 提示词使用说明

一个开发批次准备标 Code Complete / Closed，或准备开始下一批次前使用。
检查的是：本批实施中用户逐条确认并已落地的业务规则，是否已经写入当前 PRD。
一般性需求变更仍走第 40～42 节；从临时袋纳入走第 39C 节。本节是批次门禁，不替代 CR 流程。
没有此类改动时不要创建空 CR。
盘点只对照已入库的 PRD/DEC；未纳入的临时袋草稿不算已收入。

```text
当前阶段：BATCH_PRD_CLOSE

本次只处理刚结束或准备收口的批次：{{BATCH_ID}} {{BATCH_NAME}}

不要开始下一批次。
不要把本批实现细节写入 PRD。

请盘点本批「逐条改动」：

1. 本批用户已二次确认并已落地的业务规则、对象范围、状态、权限、计费或费率口径、验收口径。
2. 对照当前 Approved/Baselined PRD：哪些尚未收入。
3. 已写入 DEC 但未同步 PRD 的条目必须列入。
4. 排除纯实现：操作按钮、SQL 文件编号、接口字段名、不冻结的示例数据清单、临时代码路径。
5. 未纳入的临时袋草稿不算已收入 PRD。

若清单为空：
- 在 WORKLOG 写明「本批无待收口 PRD 变更」
- 更新看板下一步
- 不得创建空 CR

若清单非空：
- 起草一张 CR（可汇总本批已确认口径；每条高影响决策仍按第 2A 节逐项确认）
- 按第 40～42 节和第 2A 节完成
  CR_DECISION_REVIEW → CR_DECISION_CONFIRMATION → CR_DECISION_APPLY
- 收入 PRD：已 Approved/Baselined 则升补丁版本并保留旧基线；仍为 Draft 则同步当前稿并登记来源
- 更新 TRACE_MATRIX、OPEN_ITEMS、CHANGELOG 和进度看板

未完成盘点，或清单非空但 CR 尚未收入 PRD 前：
- 不得将下一批次升为 In Progress
- 不得声称本批业务口径已与 PRD 对齐
```

- Required Evidence 是否已定义。
- PRD 是否 Approved/Baselined。
- 技术架构和模块设计是否完成。
- API、数据和编码规范是否有唯一真源。
- UI_SCOPE_MAP 是否与 PRD 同步。
- products/ 是否来自已确认的应用架构和 PROJECT_STRUCTURE。
- application_slug 是否映射真实 repository_path。
- 是否明确启用或跳过 UI 规范。
- 启用 UI 规范时，所需 UI_SPEC 是否 Approved/Baselined。
- 高保真页面的字体、图标、Logo 和设计版本是否齐全。
- 是否存在未解决的 UI-CONFLICT。
- 是否生成 EFFECTIVE_UI_CONTRACT。
- 所有高影响问答是否有第 2A 节影响复述、二次确认和受控应用证据。
- 技术栈总览是否逐项引用 TECH_DECISION/ADR；是否遗漏组合方案或把不同层次技术错误做成单选。
- 提前 Draft 是否正确标记 generation_context、Assumption/TBD，且没有错误推进 PROJECT_STAGE/Approved/Baselined。
- 是否误把取消问卷、未理解或初次选择记录为 DEC/ADR/CR/UI-DEC。
- 上一批次是否已完成第 36A 节：有待收口口径则 CR 已收入 PRD，否则已记录无待收口变更。
- 若存在未纳入的临时变更袋，是否误把袋内口径当成已基线 PRD。
- Workflow 是否存在未完成 Rebase。
- P0/P1 是否为 0。

## 49. UI 素材检查

- 每个素材是否有来源 ID。
- 是否登记版本、哈希、范围和状态。
- 原始素材是否与生成规范分开。
- SVG、PNG、WebP 等资产是否保留原文件。
- 标准组件库图标是否登记包名、版本和组件名。
- AI 重建图标是否放入 `reconstructed/`。
- AI 重建图标是否仍为 `Needs Review`。
- 被正式引用的 AI 重建或替代图标是否有知情决策二次确认证据。
- 小程序目标格式是否经过兼容验证。
- 版权或许可是否明确。
- 旧素材是否保留 Superseded 关系。

## 50. 开发完成前

- 当前 Runtime Context 是否仍有效。
- 代码是否映射到批次、需求和技术设计。
- 页面是否遵循 EFFECTIVE_UI_CONTRACT。
- 是否覆盖 Loading、Empty、Error、Disabled 和 No Permission。
- F3/F4 页面是否执行视觉验收。
- 是否误改非目标区域。
- API、数据、权限、状态和异常是否一致。
- 实施中新增的决策是否完成第 2A 节复述、二次确认和受控应用。
- 是否误把取消、不理解或初次选择作为实现依据。
- 本批逐条已确认业务改动是否已按第 36A 节盘点；有则 CR 已收入 PRD，无则已记录无待收口变更。
- 测试、视觉测试、回滚和人工验证是否完成。
- 进度是否有 Git、测试和验收证据，并已登记 EVD。
- TRACE 与 Evidence 是否同时完整。
- WORKLOG 和项目看板是否更新。

## 52. 最终原则

```text
PROJECT_PROFILE 描述项目是什么
ASSESSMENT 识别项目复杂性和触发条件
CAPABILITY 决定启用哪些专项能力
WORKFLOW_BLUEPRINT 决定本项目这一次怎么走
STAGE_CONTRACT 决定当前阶段什么时候能进入、允许做什么、何时算完成
RUNTIME_CONTEXT 决定当前任务可以读取什么、做什么和写什么
PRD 决定业务做什么
TECH_DECISION 决定技术候选、组合、取舍和当前推荐如何形成
ADR 记录已经确认且形成长期约束的架构决定
技术设计决定系统怎样实现
UI_SPEC 决定分层视觉和交互规则
EFFECTIVE_UI_CONTRACT 决定当前批次实际遵守什么
EVIDENCE 证明状态为什么成立
TRACE 记录对象为什么关联
原始素材提供输入和证据，但不能绕过评审直接控制开发
知情决策协议决定用户如何在充分理解影响后作出并应用选择；功能描述按第 2A 节人话 6 问
受控提前 Draft 决定文档何时可以先形成工作稿，但不能改变正式阶段和执行门禁
Workflow 发生变化时必须通过 Workflow Change / Rebase，不得静默切换
需要错开改正式文档时，变更稿决定需求先放临时袋还是直接写正式变更
```
