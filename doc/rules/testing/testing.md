# Testing Rules
> Rule ID：RULE-TESTING
> 生效：CONDITIONAL
> 激活条件：项目需要测试活动；具体测试级别由 Workflow / Capability 决定
> 定位：测试执行与质量门禁的运行规则，不强制某个工具

## 1. 测试不是“全部自动化”

测试活动可以包含：

```text
人工验证 / Unit / Component / Integration / API / E2E / Platform / Performance / Security
```

项目是否启用哪一种，由风险和交付口径决定。

## 2. 测试目标先于工具

先回答：

1. 要证明什么行为正确？
2. 哪些风险最高？
3. 哪些场景重复出现、适合自动化？
4. 哪些场景必须真实设备/真实 Provider 才能证明？

再选择工具。

不要从“项目已经安装某测试框架”反推测试目标。

## 3. 测试设计

测试场景应从正式事实源派生：

```text
Spec / Contract / Acceptance / 约束
        ↓
正常路径
边界值
无效输入
异常路径
状态变化
权限
并发/重复操作
环境差异
```

测试预期不得凭“通常产品应该这样”自行创造；若需求未定，应进入 TBD / Open Item。

## 4. 测试结构

推荐使用 AAA（Arrange / Act / Assert）或项目等价结构：

- Arrange：准备状态和输入；
- Act：执行单个主要行为；
- Assert：验证业务可见结果。

测试名称描述行为和结果，而不是实现细节。

## 5. 分层原则

### Unit

适合纯函数、转换逻辑、规则判断、复杂计算。

### Component

适合稳定、重要的 UI 行为与交互状态。

### Integration / API

适合验证模块之间、前后端或服务之间的真实契约。

### E2E

适合关键业务链路，不追求把所有页面操作全部自动化。

## 6. 稳定性

自动化测试应避免无意义随机失败：

- 时间、随机数、网络依赖应可控制；
- 外部 Provider 在单元层优先 Mock；
- 测试数据彼此隔离；
- 不依赖测试执行顺序，除非测试框架和项目明确设计了 fixture lifecycle。

出现 flaky test 时，应记录根因和处理，而不是简单重复运行直到通过。

## 7. 关键异步状态

涉及异步 UI 或 API 的场景至少考虑适用的：

```text
loading / success / empty / error / retry / timeout
```

## 8. 真实平台与真机

浏览器自动化不能替代真实平台验证。

涉及移动端/小程序/硬件/权限/第三方 Provider 时，应单独规划：

- 首次授权与拒绝；
- 权限关闭后重新进入；
- 在线 / 弱网 / 断网；
- 冷启动 / 重启；
- 真机特性；
- 第三方服务切换；
- 上传、失败、重试、重复提交。

## 9. 测试数据

- 测试数据应可复现；
- 与生产数据隔离；
- 敏感数据脱敏；
- 有状态机的业务要准备不同状态数据；
- 并发测试必须明确是否会共享同一资源，避免“数据互相污染”导致假失败。

## 10. 失败证据

测试失败时，尽量保留：

```text
命令 / 环境 / 输入 / 实际结果 / 预期结果 / 日志 / 截图或录屏（适用时）
```

没有运行证据的内容只能标记为待验证。

## 11. 门禁

CI / pre-merge / release 的具体门禁由项目决定。

不要在通用规则中写死：

- 某个固定覆盖率；
- 某一个测试框架；
- 所有项目必须 E2E；
- 所有提交必须跑完整回归。

但一旦项目明确声明门禁，就按项目门禁执行。

## 12. Review

- [ ] 测试来源是否可追溯到 Spec / Contract；
- [ ] 是否覆盖关键正常、边界、异常与状态路径；
- [ ] 自动化层级是否与风险匹配；
- [ ] 失败是否有证据；
- [ ] 是否把“未运行”误写成“通过”；
- [ ] 测试数据是否隔离、可重复。
