# Exception Handling Rules
> Rule ID：RULE-EXCEPTION-HANDLING
> 生效：CONDITIONAL
> 激活条件：项目存在网络、服务端、客户端或跨系统异常处理
> 定位：跨技术栈异常边界规则

## 1. 异常分类

至少能区分适用场景中的：

```text
Validation
Authentication
Authorization
Business Conflict
External Dependency
Network/Transport
Timeout
Unknown/System
```

分类目的是决定处理方式，而不是为了增加枚举数量。

## 2. 边界优先

异常应尽量在最接近问题边界的位置被识别并归类：

```text
外部输入 → 参数校验
网络边界 → Transport / API 错误
业务层 → Business rule
基础设施 → Infrastructure failure
```

不要等错误扩散到最上层后再猜它是什么。

## 3. 用户提示与内部诊断分离

用户需要：

```text
能做什么 / 是否需要重试 / 是否需要重新登录 / 如何继续
```

内部需要：

```text
堆栈 / 请求标识 / Provider 信息 / 原始异常
```

内部诊断信息不能无过滤地直接显示给用户。

## 4. 日志

关键异常应保留足够上下文，例如：

- 业务操作；
- 资源标识（脱敏后）；
- 失败类别；
- 请求/Trace 标识（若项目有）；
- 环境；
- 重试次数（适用时）。

禁止记录敏感凭据。

## 5. Retry

不是所有异常都能重试。

适合评估重试的通常是：

```text
临时网络故障
服务暂不可用
超时
```

必须谨慎重试：

```text
参数错误
权限错误
业务规则冲突
非幂等写操作
```

重试策略应考虑退避、上限、幂等性和用户体验。

## 6. 前端

前端错误处理至少考虑：

- 全局兜底；
- 页面级兜底；
- 请求失败提示；
- 登录失效处理；
- 网络恢复/重试；
- 空数据和错误数据的区别。

不要在每个页面复制一套完全不同的错误提示协议。

## 7. 后端

服务端应有统一异常映射策略：

- 校验错误；
- 认证/授权错误；
- 业务异常；
- 系统未知异常。

具体框架实现由技术栈 Rule 决定。

## 8. Fallback

关键 UI / 服务在可能情况下提供可控兜底：

```text
局部组件失败 ≠ 整页必须崩溃
```

但兜底不能掩盖关键业务已失败的事实；需要让用户知道当前操作结果。

## 9. 不吞异常

以下行为属于高风险：

- 空 catch；
- catch 后只打印日志但继续返回“成功”；
- 用默认空数据掩盖接口失败；
- 把未知错误转换成“成功”。

除非业务明确允许 fallback，否则应保留失败语义。

## 10. Review

- [ ] 异常分类是否足够支持处理策略；
- [ ] 用户提示与内部日志是否分离；
- [ ] 重试是否考虑幂等性；
- [ ] 是否存在吞异常；
- [ ] 是否可能泄露敏感信息；
- [ ] 关键页面/服务是否有合适兜底。
