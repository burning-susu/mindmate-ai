# API / Cross-endpoint Contract Rules
> Rule ID：RULE-API-CONTRACT
> 生效：CONDITIONAL
> 激活条件：存在前后端、服务间、SDK、事件或其他接口协作
> 定位：统一“契约一致性”运行规则；不强制 REST / GraphQL / RPC 等具体协议

## 1. 契约优先

接口协作至少应明确适用项：

```text
Endpoint / Method / Request / Response / Error / Auth / Pagination / Time / Idempotency / Version
```

具体字段由项目 Contract 决定。

## 2. 不强制一种协议

可采用：

- REST
- GraphQL
- RPC
- WebSocket / SSE
- 消息 / Event
- 第三方固定协议

本 Rule 只要求契约被明确记录并一致执行。

若项目已经存在接口风格，不得仅因“规范不同”就擅自推动全量重构。

## 3. 字段一致性

同一业务概念在不同端尽量保持一致名称和语义。

如果必须转换，例如：

```text
backend: created_at
frontend: createdAt
```

应在 mapping 层明确，而不是在页面中到处隐式转换。

## 4. 枚举与状态

状态值必须是契约的一部分。

新增/修改状态时同步检查：

- 后端状态机；
- 前端显示和按钮逻辑；
- 测试数据；
- 错误处理；
- 其他消费者。

不能只改数据库枚举就宣布接口完成。

## 5. 错误语义

成功/失败结构由项目 Contract 决定。

不要把下列任何一种当成跨项目强制标准：

```text
code=200
code=0
{ data, message }
```

真正要求是：调用方能稳定判断：

```text
成功 / 参数失败 / 未认证 / 无权限 / 业务冲突 / 系统错误 / 可重试
```

## 6. 请求与响应

必须关注：

- 必填 / 可选字段；
- 默认值；
- 类型；
- 长度 / 范围；
- null / undefined 语义；
- 大小限制；
- 时间与时区；
- 文件/二进制上传方式；
- 分页和排序规则（如适用）。

## 7. 幂等与重复提交

写操作需要根据业务判断是否应支持幂等。

尤其关注：

- 支付；
- 创建订单；
- 文件上传；
- 状态提交；
- 重试请求。

不能因为 UI 禁用了按钮，就认为接口不存在重复提交风险。

## 8. 版本与兼容

契约变化至少分辨：

```text
向后兼容
非兼容
新增字段
删除字段
字段重命名
语义变化
```

非兼容变更需要明确兼容策略、迁移范围和下线条件。

## 9. 第三方接口

第三方接口属于外部事实源：

- 不按内部规则随意改造对方契约；
- 在本地 adapter 层做映射；
- 记录 Provider 版本/环境/限制（若项目需要）；
- 测试环境和生产环境的差异进入 Evidence。

## 10. Contract Change Review

接口变化发生时至少搜索：

```text
调用方
类型定义
Mock
测试
文档
错误映射
权限逻辑
日志/监控字段
```

未经对账，不要把“接口能返回 200”当成迁移完成。

## 11. 与 Capability 的关系

更详细的 REST、GraphQL、RPC 等设计方法放在对应 Capability。

本 Rule 只定义运行时必须遵守的契约纪律，不复制某一协议的完整设计手册。
