# Java / Spring Boot Rules
> Rule ID：RULE-JAVA-SPRING
> 生效：CONDITIONAL
> 激活条件：项目使用 Java + Spring / Spring Boot
> 定位：通用 Java/Spring 工程规则；不绑定具体包名、模块名和业务实体

## 1. 分层边界

根据项目复杂度保持可识别的职责：

```text
Controller / Protocol
        ↓
Application / Service
        ↓
Domain / Business
        ↓
Repository / Infrastructure
```

不是要求每个项目必须建立四层，而是禁止让 Controller、Repository、业务规则和基础设施全部糊在一个类中。

## 2. Controller

- 负责请求边界、参数映射、权限边界和响应协议；
- 不承载大段核心业务流程；
- 参数校验尽量靠近边界；
- 对外协议变化应能被 API Contract / Spec 追踪。

## 3. Service / Application

- 编排用例和事务边界；
- 不把所有数据库细节直接暴露给 Controller；
- 复杂业务规则保持可测试、可定位；
- 同一业务决策不要复制到多个接口中。

## 4. Entity / DTO

是否分离 DTO 与持久化实体取决于复杂度、暴露风险和演进需求。

复杂项目中应避免直接把数据库实体当公共 API 契约，尤其是：

- 字段暴露范围不一致；
- 关联关系会导致 N+1；
- 内部字段不应对外；
- API 和数据库演进节奏不同。

## 5. 参数校验

请求输入必须在适当边界校验：

- required；
- format；
- range；
- enum；
- 状态前置条件。

仅依赖前端校验不构成后端安全边界。

## 6. 异常

- 使用项目统一异常处理机制；
- 区分业务异常、参数错误、认证授权错误、外部依赖异常和未知系统错误；
- 不在多个 Controller 各自拼不同的错误格式；
- 日志记录要有上下文，但不能把敏感信息写入日志。

## 7. 事务

事务边界围绕一个业务用例设计，而不是机械给所有方法加事务。

涉及多个持久化写操作、状态迁移或一致性要求时，应明确：

```text
事务范围 / 隔离要求 / 重试策略 / 幂等性
```

## 8. 数据库变更

- 结构变更优先采用可审查、可重复执行的迁移脚本或项目既定迁移机制；
- 高风险变更先备份和演练；
- 破坏性字段/表变更考虑兼容期；
- 生产数据操作必须有明确的止损/回滚策略。

## 9. 外部依赖

第三方 API、消息队列、对象存储、支付等外部服务应有清晰的 adapter/client 边界。

不要让业务代码到处直接调用第三方 SDK，除非项目规模足够小且这种选择已被明确接受。

## 10. 配置与 Secret

- 环境差异通过配置层管理；
- Secret 不进入源码和普通文档；
- 默认配置不得包含生产凭据；
- 新增配置应同步环境说明和部署文档（若项目有此类文档）。

## 11. 日志与可观测性

关键业务流程适当记录：

```text
事件 / 业务标识 / 结果 / 失败原因
```

日志中禁止记录密码、Token、完整身份证号等敏感数据，具体脱敏规则按项目安全基线执行。

## 12. Review

- [ ] Controller 是否越界承载业务；
- [ ] DTO / Entity 暴露是否合理；
- [ ] 输入是否在服务端验证；
- [ ] 异常是否统一；
- [ ] 事务和幂等性是否明确；
- [ ] DB migration 是否可审查与回退；
- [ ] 外部 Provider 是否有清晰边界；
- [ ] Secret / 日志是否安全。
