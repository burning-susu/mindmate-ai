# Engineering Principles
> Rule ID：RULE-CORE-ENGINEERING
> 生效：DEFAULT
> 适用：所有开发任务
> 定位：跨技术栈工程协作与实现原则

## 1. Source First

开始修改前先确认当前事实来源：

```text
项目治理 / Approved PRD / REQ Spec / ADR / API Contract / 当前代码 / 测试证据
```

不要把聊天中的临时讨论、旧截图或 AI 推测当成已确认事实。

## 2. 最小必要修改

- 先理解当前实现，再决定修改方案。
- 优先局部修复，不因为发现代码“不够漂亮”就顺手重构无关部分。
- 需要重构时，明确重构目标、范围和退出条件。
- 一个任务尽量保持一个主要目标，避免把多个无关变化揉成一个提交。

## 3. 复用优先，但不过度抽象

修改前先搜索：

- 已有组件；
- 公共函数；
- Domain / Service；
- API 封装；
- 工具和配置；
- 已存在的 Rule / Capability。

发现重复时先判断它是不是稳定的共同知识：

```text
稳定重复规则 → 值得抽象
偶然相似代码 → 可以保持独立
```

不要因为“未来可能扩展”提前设计复杂框架。

## 4. 清晰边界

以下职责原则上保持可分辨：

```text
展示/UI
状态
业务规则
数据访问
基础设施
配置
```

具体分层名称由项目架构决定，不强制固定目录。

## 5. 外部边界优先验证

从外部进入系统的数据至少经过适合场景的检查：

- 类型和格式；
- 必填字段；
- 长度和范围；
- 枚举值；
- 权限；
- 状态是否允许当前操作；
- 重复提交 / 幂等性；
- 资源是否存在。

不能因为“前端已经校验过”就跳过服务端边界校验。

## 6. 不把不确定性写成确定性

AI 执行过程中遇到缺失信息：

- 已确认 → 按事实执行；
- 有合理候选但未确认 → 标记 TBD / Open Item；
- 需要源码、环境、接口或真实运行证据 → 标记待验证；
- 不可根据常识自行把猜测写进正式 Spec / Rule。

## 7. 变更纪律

涉及业务、接口、数据、架构或 UI Contract 的变化，应先判断影响范围，再按 v3.2 的 Workflow Change / Rebase 机制处理。

代码不是唯一需要变更的对象：

```text
需求变化 → Spec
接口变化 → Contract
架构变化 → ADR / Architecture
测试变化 → Test
完成证据 → Evidence / Progress
```

## 8. 可回滚与可解释

高影响改动应具有：

- 清晰的版本边界；
- 可识别的提交或 Tag；
- 明确的回滚动作；
- 足够的变更上下文。

目的不是“每次都打 Tag”，而是确保重要改动发生后，团队能回答“改了什么、为什么改、如何回退”。

## 9. 工具使用边界

工具、脚本、MCP、AI 生成器都属于执行手段，不是事实源。

工具输出必须经过与任务相关的验证；不能因为某工具生成成功，就直接认定业务正确、接口兼容或生产可用。
