# User Rules（Generic Source）
> Rule ID：RULE-CORE-USER-GENERIC
> 生效：DEFAULT
> 适用：跨项目稳定工程习惯
> 定位：从历史 userrules 中抽取的通用部分；不绑定个人项目技术栈

## 1. 开发环境

- 运行时版本以项目声明为准，例如 `package.json`、`.nvmrc`、`tool-versions`、`pom.xml` 或等价配置。
- 包管理器优先依据仓库锁文件判断；同一个项目不要无故混用多个包管理器。
- Formatter / Linter 优先遵循仓库已有配置，不在单次任务中擅自引入另一套格式化标准。
- Git 操作以可审查、可回滚为目标。

## 2. 导入与模块组织

- import 顺序遵循项目格式化工具或既有约定。
- 内部模块优先使用项目既有别名策略。
- 共享类型放在项目约定的位置，不为“类型统一”强行建立第二套目录。
- 注意循环依赖；新增 barrel/index 导出前确认不会扩大依赖图或造成隐式耦合。

## 3. 注释与命名

- 只有在 WHY 不明确时写注释；不要复述代码。
- 名称表达意图，避免无语义缩写。
- 业务概念统一命名；跨层映射时明确转换关系。

## 4. 文档与知识沉淀

- README、环境变量、启动说明、API Contract 等应与实际状态保持同步。
- 复杂业务规则应在对应的 Spec / Capability / ADR 中记录，而不是只存在聊天上下文。
- 破坏性变更或用户可见变化需要进入项目定义的变更/发布记录。
- 示例代码若作为正式文档示例，应尽量与真实可运行代码保持一致。

## 5. 测试与工程化

- 自动化测试是否启用由项目 Workflow / Capability 决定，不在本文件强制工具。
- 已配置的 lint / typecheck / test / build 脚本，按项目门禁执行。
- 覆盖率目标、CI 阈值等数字必须来自项目决策，不应由通用规则自行创造。

## 6. 安全基线

- 不提交密钥、密码、Token、私钥及其他敏感凭据。
- 前端代码中的公开配置与真正 Secret 要区分；“隐藏在前端代码里”不等于安全。
- 输入验证、认证、授权和敏感信息保护应在系统适当边界落实。
- 用户可见错误不得泄露不必要的内部实现细节。

## 7. 协作

Code Review 至少关注：

```text
正确性 / Scope / 可维护性 / 安全 / 关键性能风险 / 测试 / 文档同步 / 可回滚性
```

遇到技术变化时，先小范围验证，再推广为项目正式规则。
