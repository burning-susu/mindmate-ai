# CODE-STANDARDS
> Rule ID：RULE-CORE-CODE-STANDARDS
> 生效：DEFAULT
> 适用：所有代码变更
> 定位：通用编码质量规则；具体语言/框架格式由对应 Rule 补充

## 0. 使用方式

本规则负责“代码应达到什么质量标准”，不负责规定某个框架的具体 API 写法。

- 本规则是默认基础规则。
- 语言、框架、构建工具的具体规则由对应技术栈 Rule 叠加。
- 若项目已有更高优先级的正式约定（架构、Spec、ADR、官方兼容要求等），先遵守项目事实，再将本规则作为通用质量基线。
- 本规则中的阈值类数字默认作为“风险信号”，不是跨项目机械门槛；除非项目明确把某项写成硬性门禁。

## 1. 注释规范

### 1.1 默认不写“复述型”注释

好的命名、结构和类型已经能解释“代码做了什么”时，不要再用注释重复描述执行动作。

### 1.2 应写注释的情况

当没有注释容易导致后续维护者做出错误修改时，应补充简洁说明，优先解释 WHY：

- 隐藏的约束、前置条件或时序要求；
- 非显而易见的 workaround，以及规避的已知问题；
- 反直觉业务规则；
- 性能或安全方面的取舍；
- 与外部系统兼容而不能直接按常规实现的特殊处理。

判断问题：**如果删掉这条注释，未来修改代码的人有较高概率做出错误修改吗？**

### 1.3 不应写的注释

- “遍历数组”“调用接口”“设置变量”等显而易见说明；
- 大段注释掉的旧代码；
- 把任务编号、Issue、PR 讨论内容永久写进业务代码；
- 为内部简单函数批量生成没有信息增量的模板化文档。

公共 API、SDK、复杂公共模块可以使用 JSDoc 或等价契约文档，但内容应服务于调用方理解。

## 2. 命名

- 名称应表达业务意图，而不是只表达实现形式。
- 变量、函数、类、组件、文件的具体命名风格遵循语言/框架 Rule。
- 同一业务概念在同一项目内尽量保持同一术语，不要在不同模块中随意换同义词。
- 避免只有作者本人理解的缩写。
- 布尔值命名应让真假语义清晰，例如 `isLoading`、`hasPermission`、`canSubmit` 等；具体前缀按项目习惯统一。
- 不使用“最终版”“临时版”“新版本2”之类没有业务语义的命名作为长期正式标识。

## 3. 可维护性

- 模块、函数、组件尽量保持单一职责。
- 当一个函数同时处理校验、业务决策、持久化、UI 提示等多个明显职责时，应评估拆分边界。
- 重复逻辑应先判断是否为稳定的共同规则，再决定抽象；不要为了消灭几行重复就过度封装。
- 修改前先搜索已有实现、工具函数、组件和服务，优先复用已有能力。
- 不要为了“未来可能会用”提前引入复杂抽象。
- 大范围重构必须与当前需求范围明确区分，并说明影响面。

## 4. 代码卫生

禁止提交：

- 无意义调试输出；
- 已确认废弃的死代码；
- 大段注释掉的历史实现；
- 临时密钥、账号、Token、私钥等敏感信息；
- 与当前任务无关的格式化噪声或批量重写。

## 5. 依赖与第三方库

新增依赖前至少确认：

1. 现有项目是否已有可复用能力；
2. 引入依赖解决的真实问题；
3. 依赖对构建、运行时体积、许可证、安全和维护成本的影响；
4. 是否超出当前 Spec / Workflow 允许的技术范围。

不能仅因为“AI 推荐”就增加依赖。

## 6. 边界与错误处理

- 外部输入、网络响应、文件内容、用户配置等不应被无条件视为可信。
- 在跨模块、跨网络、跨进程边界进行必要的校验和类型收窄。
- 不要用静默失败掩盖错误；错误应进入项目定义的错误处理链路。
- 用户可见提示与内部诊断信息分离，避免将堆栈、密钥、内部路径等敏感信息直接暴露给用户。

## 7. 可测试性

- 让关键业务规则尽量存在于可独立验证的边界中。
- 时间、随机数、网络、外部服务等造成不确定性的依赖，在需要自动化验证时应可替换、可 Mock 或可注入。
- 不为了测试方便牺牲真实业务边界；应优先调整依赖边界而非把实现全部改成测试专用代码。

## 8. 最小变更原则

默认优先选择：

```text
局部、可理解、可验证、可回滚
```

而不是：

```text
一次性重写、顺便重构全部相关代码
```

当确需扩大修改范围时，必须把扩大原因写入任务记录或变更记录，并让相关 Scope / Trace 可追踪。

## 9. Review 最小检查集

提交前至少检查：

- [ ] 改动是否仍在当前 Scope 内；
- [ ] 是否产生新的重复实现；
- [ ] 是否存在明显的死代码/调试残留；
- [ ] 关键边界是否有错误处理；
- [ ] 是否引入未经决策的新依赖；
- [ ] 是否有需要解释 WHY 的复杂逻辑却没有说明；
- [ ] 是否需要更新 Spec / Contract / Test / Evidence。
