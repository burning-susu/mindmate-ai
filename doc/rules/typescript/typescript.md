# TypeScript Rules
> Rule ID：RULE-TYPESCRIPT
> 生效：CONDITIONAL
> 激活条件：项目使用 TypeScript
> 定位：TypeScript 语言级规则，不绑定 Vue、React、Pinia 或特定构建工具

## 1. 类型先于断言

优先让类型系统表达真实约束，而不是依赖大量 `as`、非空断言或 `any` 绕过检查。

```text
真实数据约束
    ↓
类型表达
    ↓
运行时边界校验（需要时）
    ↓
业务逻辑
```

## 2. `any` / `unknown`

- 不要为了快速消除报错而引入 `any`。
- 外部输入、不可信数据或暂时未知结构优先使用 `unknown`，随后显式收窄。
- 如果确实必须使用 `any`，应让范围尽可能小，并说明原因（若原因不明显）。

## 3. interface / type

不做机械二选一：

- 对象结构可用 `interface`；
- 联合、交叉、条件、映射等类型可用 `type`；
- 项目若已有明确风格，保持一致比争论关键字更重要。

## 4. 函数类型

公共函数、跨模块 API、复杂回调应保持参数和返回值清晰。

不是所有简单局部函数都需要重复书写可以可靠推断出来的返回类型。

## 5. 数据状态与枚举

- 对有限状态优先使用字面量联合、enum 或项目统一方式表达。
- 不要用多个散落的字符串常量表示同一个状态集合。
- 状态扩展时同步搜索消费者，确认新增值是否存在默认分支遗漏。

## 6. Nullable

- 区分 `undefined` 与 `null` 的业务含义。
- 不要为了消除编译错误无条件使用 `!`。
- 可选字段进入业务逻辑前应完成适当收窄。

## 7. 泛型

泛型用于表达“调用者和实现之间稳定的类型关系”，不要为了看起来高级而泛型化。

```text
有稳定类型关系 → 泛型
只是想减少几行代码 → 不一定需要泛型
```

## 8. DTO 与外部数据

TypeScript 类型只保证编译时假设，不会自动验证运行时 JSON。

来自：

- HTTP API
- localStorage / IndexedDB
- URL 参数
- 文件
- 第三方 SDK
- 用户输入

的数据，在高风险边界应有运行时校验或等价保护。

## 9. 类型推断

- 能可靠推断时不重复写相同类型。
- 公共边界、复杂映射、重要返回值保持可读。
- 不要通过过长的类型表达式换取毫无收益的“绝对类型精确”。

## 10. 模块与类型组织

- 类型与其最相关的业务模块保持邻近；
- 真正跨模块共享的类型进入公共位置；
- 避免建立“所有类型都放一个 types/index.ts”的巨型入口；
- barrel 导出要关注循环依赖和 tree-shaking 影响。

## 11. 编译严格性

以项目 `tsconfig` 为事实源。不要在单个文件里通过关闭规则、宽松 cast 或 `// @ts-ignore` 绕过项目整体约束。

`@ts-ignore` / `@ts-expect-error` 只用于经过确认的边界问题；应尽可能写出原因，尤其是长期保留时。

## 12. Review

- [ ] 是否引入不必要的 `any`；
- [ ] 外部数据是否被当成可信类型；
- [ ] nullable 状态是否处理；
- [ ] 公共边界类型是否清晰；
- [ ] 是否存在无意义的类型复杂化；
- [ ] 是否与项目 `tsconfig` / formatter / lint 规则一致。
