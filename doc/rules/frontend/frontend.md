# Frontend Engineering Rules
> Rule ID：RULE-FRONTEND-GENERIC
> 生效：CONDITIONAL
> 激活条件：项目包含 Web、SPA、SSR、Hybrid、组件化客户端或其他前端运行层
> 定位：前端通用规则；Vue/React 等仅在对应项目技术栈激活时生效

## 1. 前端职责边界

前端代码通常同时处理：

```text
视图展示 / 用户交互 / 本地状态 / API 调用 / 客户端路由 / 平台能力
```

不要把所有逻辑堆在单一页面或组件中。

推荐根据复杂度保持可理解的边界：

- 页面/容器：编排页面流程；
- 组件：展示与局部交互；
- hooks/composables/services：可复用状态或流程；
- API 层：网络契约映射；
- domain/util：纯业务规则或纯工具。

名称和目录以项目 Architecture 为准。

## 2. 组件设计

- 一个组件应有清晰职责和稳定输入/输出边界。
- Props / 参数应有明确类型或运行时约束（按技术栈能力决定）。
- 事件命名围绕业务行为，不围绕内部实现细节。
- 组件过度依赖父组件隐式状态时，应评估是否存在边界泄漏。
- 需要跨页面复用的状态逻辑不要复制粘贴；优先提取为项目既定复用单元。

## 3. 异步状态

涉及异步请求或外部资源时，按实际场景显式考虑：

```text
idle / loading / success / empty / error
```

不适用的状态可以省略，但不能为了简单而让“请求未完成”和“请求失败”共用一个无法解释的布尔值。

## 4. API 与 View Model

复杂前端项目中，建议明确区分：

```text
API DTO
   ↓ mapping
UI View Model
```

这样后端字段变化不会直接污染整个 UI 层。若数据结构非常简单且项目已有统一约定，也可以保持直接映射，但必须有明确依据。

## 5. 网络请求

- 请求封装按业务域或项目现有模块组织。
- 认证、错误、超时、取消请求等横切逻辑尽量集中处理。
- 对“过期请求”“重复请求”“快速连续点击”等竞态风险，在高风险场景考虑 Abort / dedupe / idempotency。
- 不要在每个页面各写一份 API 错误映射。

## 6. 路由

适用时：

- 路由名、path、meta 等保持唯一且可理解；
- 需要鉴权时使用项目约定的 route guard；
- 大型页面按路由懒加载；
- 处理 404、无权限和导航失败等兜底场景；
- 路由级逻辑不要和领域业务深度耦合。

不要强制项目使用 History 或 Hash；按平台部署边界决定。

## 7. 状态管理

- 只有真正需要跨组件/跨页面共享的状态才进入全局状态管理。
- 派生状态保持可计算、可解释，避免在多个地方重复维护同一事实。
- 异步 Action 应有明确成功/失败语义。
- 持久化、日志、同步等副作用应与核心状态定义保持边界。

具体工具（Pinia、Redux、Zustand 等）由项目 Workflow 决定。

## 8. 样式

- 全局 token、组件样式和页面特有样式保持职责分离。
- 不把同一视觉系统拆成互相冲突的多套“真相”。
- `!important` 应是例外，而不是默认覆盖工具。
- 响应式布局必须考虑真实内容、断点和交互状态，而不是只满足一个截图尺寸。

具体 CSS 方案由 UI Capability / 项目决策确定。

## 9. 事件与资源生命周期

组件/页面创建的监听器、Timer、订阅、观察器、AbortController、图表实例等，在生命周期结束时应按技术栈能力清理。

特别注意：

```text
DOM listener
Timer
WebSocket / SSE
第三方 SDK subscription
Canvas/WebGL instance
```

## 10. Vue（仅 Vue 项目）

- Composition API / `<script setup>` 等按项目版本和既有约定执行。
- Props / Emits 保持清晰契约。
- composables 保持单一职责，并负责自身副作用的清理。
- `provide/inject`、`Teleport`、`Suspense` 等能力按场景使用，不因“有能力”就强制使用。
- Pinia 仅在项目选择 Pinia 时适用。

## 11. React（仅 React 项目）

- Hooks 保持规则一致，副作用依赖项明确。
- UI 状态、服务调用和业务规则保持可理解边界。
- Context 适合稳定的跨层依赖，不要用 Context 代替所有状态管理。
- Server Components / SSR / Client Components 的边界以项目框架版本和架构决策为准。

## 12. Review

前端任务至少检查：

- [ ] 是否存在页面组件职责过重；
- [ ] 是否复制已有组件/逻辑；
- [ ] 是否明确处理关键异步状态；
- [ ] 是否存在请求竞态或重复提交风险；
- [ ] 是否有生命周期泄漏；
- [ ] 是否影响现有路由/权限行为；
- [ ] UI / API / 状态边界是否仍然清楚。
