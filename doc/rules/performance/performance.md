# Performance Rules
> Rule ID：RULE-PERFORMANCE
> 生效：CONDITIONAL
> 激活条件：项目或 REQ 声明性能关注点/性能测试 Capability
> 定位：性能实现层运行规则；指标和阈值由项目基线决定

## 1. 证据驱动

性能优化先测量，再优化，再回归：

```text
问题/风险假设
    ↓
基线
    ↓
定位瓶颈
    ↓
改动
    ↓
复测
    ↓
比较
```

不要仅凭“理论上更快”进行大范围重构。

## 2. 前端渲染

- 避免无意义重复渲染；
- 大列表根据真实数据规模评估虚拟化；
- 派生状态使用适合框架的缓存/计算机制；
- 高频事件、watcher、pointer/scroll 等按场景做 debounce / throttle / batching；
- 大型组件或路由按需分割；
- 非关键资源按需加载。

这些是风险检查点，不意味着所有页面都必须使用每一种技术。

## 3. 生命周期

性能问题常来自资源未释放：

- event listener；
- timer；
- WebSocket/SSE；
- subscription；
- observer；
- chart / canvas / WebGL 实例。

组件销毁或任务结束时按其生命周期清理。

## 4. 网络与数据

- 避免在用户一次操作中无意触发大量重复请求；
- 合并或缓存必须建立在真实访问模式之上；
- 对可取消的过期请求考虑 Abort；
- 分页 / cursor / lazy loading 由数据规模和交互决定；
- 不要把“大 JSON 全量塞进首屏”当成默认做法。

## 5. 资源

- 图片、字体、脚本、模型等大型资源按需加载；
- 生产构建使用项目已有的压缩、tree-shaking、代码分割能力；
- 不为了微小体积收益增加难以维护的构建复杂度。

## 6. 非 DOM 渲染层

Canvas、WebGL、地图、图表、三维引擎等应分别考虑：

```text
实例数量
渲染频率
GPU/CPU 使用
资源释放
批量更新
事件频率
```

不要把所有性能问题归因于 Vue/React 重渲染。

## 7. 性能基线

若项目建立基线，应记录：

- 指标名称；
- 测试环境；
- 数据规模；
- 测试方法；
- 结果；
- 基线日期 / 版本。

后续相关改动需要比较基线；如果出现退化，应记录幅度和原因，由项目规则判断是否接受。

## 8. 反模式

避免：

- 为不存在的性能问题提前引入复杂缓存；
- 在高频路径同步写大量持久化数据；
- 一条消息导致整页无差别重渲染；
- 为了“看起来优化”而牺牲代码可读性，却没有测量证据。

## 9. Review

- [ ] 有性能声明的 REQ 是否有对应测量或基线；
- [ ] 是否存在明显重复请求/重复渲染；
- [ ] 高频路径是否有不必要工作；
- [ ] 外部资源是否合理加载；
- [ ] 手动创建资源是否释放；
- [ ] 性能优化是否有回归证据。
