# 15 技术架构与开发约束

## 1. 文档目的

本文档在产品、数据和 API 稳定后冻结 MindMate AI V1 的具体技术方案。Codex 开发时直接执行本方案，不再比较框架、数据库、向量引擎、Provider、Embedding、任务队列或打包方式。

## 2. 最终技术栈

| 层级 | 最终选择 | 说明 |
| --- | --- | --- |
| 前端 | React 19＋TypeScript＋Vite | 桌面 Web 工作区、生态稳定 |
| 路由 | React Router | 与 14 文档路由一致 |
| 服务端状态 | TanStack Query | API 缓存、失效与重试 |
| 轻量 UI 状态 | Zustand | 只保存侧栏、临时 UI 偏好 |
| 表单 | React Hook Form＋Zod | 交互校验与类型约束 |
| 样式 | Tailwind CSS＋CSS Variables | 语义 Token 与响应式 |
| 无障碍组件 | Radix UI primitives | 弹窗、抽屉、菜单等基础行为 |
| Markdown | react-markdown＋严格 sanitize | 统一安全渲染 |
| 本地后端 | Python 3.12＋FastAPI | AI/RAG 与文档处理生态、OpenAPI |
| DTO/配置 | Pydantic 2＋pydantic-settings | 类型与配置校验 |
| ORM | SQLAlchemy 2 | 明确事务和仓储实现 |
| 迁移 | Alembic | 只前进的版本化迁移 |
| 数据库 | SQLite＋WAL＋FTS5 | 单用户、本地、无服务 |
| 向量存储 | sqlite-vec，经 VectorStoreAdapter | 轻量、嵌入 SQLite、无独立服务 |
| HTTP 客户端 | httpx | DeepSeek OpenAI 兼容接口与流式请求 |
| Chat Provider | DeepSeek API `deepseek-flash` | 不使用厂商 SDK，走 Adapter |
| Embedding | `BAAI/bge-small-zh-v1.5` ONNX，512 维 | 本地 CPU，固定 revision 和哈希 |
| Embedding Runtime | ONNX Runtime CPU＋tokenizers | 避免随包携带完整 PyTorch |
| 关键词检索 | SQLite FTS5 BM25 | 本地 |
| 重排 | 本地混合分数＋多样性规则 | V1 不加载神经 Reranker |
| PDF | pypdf | 文本型 PDF；V1 不做 OCR |
| Word | python-docx | DOCX |
| PowerPoint | python-pptx | PPTX |
| TXT/Markdown | Python 标准库 | 编码探测与纯文本解析 |
| 后台任务 | SQLite 持久任务表＋进程内 Worker | 不引入 Redis/Celery |
| 凭据 | Windows Credential Manager Adapter | API Key 不进入数据库 |
| 发布形态 | 本地 Web 应用＋PyInstaller one-folder | 启动本机 API 并打开浏览器 |
| Windows 安装 | Inno Setup | 当前用户级安装、升级和卸载 |
| Python 包管理 | uv＋`uv.lock` | 快速、可重复 |
| 前端包管理 | npm＋`package-lock.json` | 降低个人开发环境门槛 |
| 测试 | pytest＋Vitest＋Testing Library＋Playwright | 单元、集成、组件、E2E |
| 质量 | Ruff＋Pyright＋ESLint＋Prettier | 自动化检查 |

精确 patch 版本在首次脚手架创建时选取相互兼容的稳定版本并立即写入 lockfile；后续不得在同一功能提交中无关升级依赖。

## 3. 选择结论与取舍

### 3.1 为什么使用 React

现有产品是消息、列表、抽屉、流式状态和复杂表单组成的桌面 Web 工作区。React 与 TanStack Query 对流式与服务端状态边界清晰，设计稿转组件成本低。V1 不同时维护 Vue 实现。

### 3.2 为什么使用 Python/FastAPI

本地 Embedding、文档解析、RAG 和 Provider 编排是核心。Python 可直接使用成熟库；FastAPI 自动生成 OpenAPI，适合 11 文档的契约。后端仍保持分层，禁止把业务全部写在路由里。

### 3.3 为什么不使用 Electron/Tauri

V1 采用本机 Web 服务＋系统浏览器，最终包不携带 Node/Chromium，构建链更短，便于个人 Windows 项目先完成闭环。代价是窗口不是完全原生应用；原生壳可在 V1.1 评估。

### 3.4 “没有服务器”的准确实现

应用启动一个只监听回环地址的本地 FastAPI 进程。它不是公网服务器，不需要购买云主机，也不接受局域网访问。浏览器只是 UI，数据库、文件和 AI 调用均由本机后端处理。

### 3.5 为什么选择 sqlite-vec

V1 已使用 SQLite，sqlite-vec 可通过同一数据库和适配器完成向量查询，避免 Chroma 服务进程和较重依赖。若 Windows 打包验证失败，开发必须停止并提交证据；不得私自换库。替换需更新 09、15 和 18。

### 3.6 为什么使用 ONNX Embedding

ONNX Runtime CPU 比完整 PyTorch 发布体积更可控。模型在首次使用时下载到本地模型目录，校验后加载；安装包不默认内置模型，从而保持初始包较小。

## 4. 总体架构

~~~mermaid
flowchart TD
    UI["React 前端"] --> API["FastAPI /api/v1"]
    API --> APP["应用服务与领域层"]
    APP --> DATA["SQLite、托管文件、任务"]
    APP --> AI["RAG 与 AI Adapter"]
    AI --> LOCAL["FTS5、sqlite-vec、ONNX"]
    AI --> DS["DeepSeek API"]
~~~

依赖方向：Web/API/Infrastructure 依赖 Application/Domain；Domain 不依赖 FastAPI、SQLAlchemy、sqlite-vec 或 DeepSeek。

## 7. 前端功能目录

每个 `features` 模块包含 routes、components、queries、mutations、schemas、types 和 tests。建议模块：home、files、knowledge-bases、chat、learning、history、tasks、trash、settings。

共享组件不得引用具体 feature；feature 可以引用共享组件。页面不直接使用 `fetch`，只调用生成/封装 API 客户端。

## 8. 本地进程与启动流程

1. Launcher 获得单实例锁；
2. 解析应用目录和用户数据目录；
3. 初始化结构化日志；
4. 校验目录权限和磁盘空间；
5. 打开 SQLite，设置 PRAGMA；
6. 检查 schema，必要时备份并迁移；
7. 执行异常退出恢复；
8. 选择随机可用回环端口；
9. 生成内存态本地会话令牌；
10. 启动 FastAPI 和 Worker；
11. 打开默认浏览器到一次性启动 URL；
12. 前端交换短期令牌并进入应用；
13. 正常退出时停止接单、保存检查点、关闭数据库。

不得把固定端口、固定会话令牌或 Key 写入前端构建产物。

## 10. SQLite 配置

连接建立后至少设置：

~~~text
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
~~~

- 写事务保持短小；
- 一个应用级写协调器避免长事务竞争；
- 解析和 Embedding 不在数据库事务内运行；
- 成果先写临时存储，最终用短事务发布；
- 定期 checkpoint，但不在用户交互热路径强制执行；
- 启动异常恢复运行 quick_check，备份/发布前按需 integrity_check。

## 11. sqlite-vec 约束

- 扩展路径由应用包确定，不接受请求参数；
- 启动时验证扩展版本和 512 维查询；
- 向量表按 `embedding_config_id` 和 `index_version_id` 隔离；
- 元数据映射仍由普通 SQLite 表管理；
- 查询必须先应用资料范围过滤；
- 删除采用版本失效＋后台清理；
- 任何扩展加载错误不得降级为伪向量结果；
- FTS-only 搜索可继续，但知识库 AI 明确标为索引不可用。

## 12. 文档解析方案

| 格式 | 库 | 定位单位 | V1 限制 |
| --- | --- | --- | --- |
| PDF | pypdf | 页码 | 不做 OCR；扫描 PDF 标记无可提取文本 |
| DOCX | python-docx | 标题路径、段落 | 不执行宏/嵌入对象 |
| PPTX | python-pptx | 幻灯片号、形状顺序 | 不播放媒体 |
| TXT | 标准库＋编码探测 | 行区间 | 限制输出字符数 |
| MD | 纯文本解析 | 标题路径、行区间 | 不加载远程资源 |

解析器运行在受限子进程；主进程通过输入文件 ID 和临时结果清单交换，不传任意输出路径。

## 13. Chunk 与检索实现

### 13.1 默认切片

- 优先按标题、段落、页或幻灯片边界；
- 目标约 500 中文字符或等效 Token；
- 重叠约 80 字符；
- 过短相邻段可合并；
- 表格和代码块尽量保持整体；
- 每个 Chunk 保存 source revision、位置和内容哈希。

实际阈值作为配置写入 `chunking_config`，更改即生成新配置与索引版本。

### 13.2 混合检索

1. 校验资料范围和激活索引；
2. FTS5 取候选 Top 30；
3. sqlite-vec 取候选 Top 30；
4. 使用 Reciprocal Rank Fusion 合并；
5. 添加标题/短语精确命中奖励；
6. 按文件与相邻 Chunk 去重和多样化；
7. 选择 Top 8 进入上下文；
8. 低于证据阈值时拒答；
9. 服务端绑定引用 ID。

融合常量和阈值必须配置化并由评测集确定，不能隐藏在组件中。

## 14. Embedding 生命周期

- 首次需要索引时展示模型下载说明、体积、来源和进度；
- 下载到 `.partial`，校验后原子重命名；
- 固定模型 revision 和 tokenizer；
- 批处理大小按内存动态上限设置，默认 16；
- 归一化向量后写入；
- 输入超过模型上限时由切片层保证，不静默截断关键位置；
- 模型配置变化创建重建任务；
- 启动不强制加载模型，仅在任务需要时懒加载；
- 闲置后 MAY 释放模型内存。

## 15. DeepSeek Adapter

### 15.1 实现方式

使用 `httpx.AsyncClient` 调用 OpenAI-compatible Chat Completions。业务层只依赖 `ChatProviderPort`，不导入 DeepSeek SDK。

### 15.2 固定配置

| 项目 | 值 |
| --- | --- |
| Base URL | `https://api.deepseek.com` |
| Model alias | `deepseek-flash` |
| Streaming | 默认 true |
| API Key | Windows Credential Manager |
| 自动模型切换 | 禁止 |
| 自动 Provider 切换 | 禁止 |
| 请求外发 | 最小必要上下文 |

模型动态能力在应用启动或设置页连接测试时探测；价格和上下文限制不硬编码为永久事实。

## 17. 后台任务实现

### 17.1 Worker

进程内异步 Worker 轮询/领取 SQLite 任务。领取通过原子状态更新和 lease 实现，单实例仍需防重复。任务阶段显式检查取消标志。

### 17.2 并发

- 重任务总并发 2；
- Embedding/向量写并发 1；
- 文档解析并发默认 2，但受总重任务限制；
- AI Operation 与持久 BackgroundTask 分离；
- 应用退出不后台常驻，任务保存检查点后停止。

### 17.3 不采用的组件

V1 不使用 Redis、Celery、RabbitMQ、Kafka、Docker 常驻服务或系统级数据库服务。

## 18. SSE 与断线恢复

- SSE 仅承载事件，不作为最终数据源；
- 每个事件包含 `event_id`、`operation_id`、`sequence`、`type`；
- 客户端保存最后 sequence 并在断线后查询 Operation 快照；
- 完成结果先持久化，再发 `completed`；
- 前端未收到完成事件时通过 GET 查询最终状态；
- 心跳不写业务日志；
- 用户停止时发送取消请求，不能仅关闭浏览器流。

## 19. API 与前端契约

- FastAPI 输出 OpenAPI 3.1；
- CI 将规范导出为固定文件并检查差异；
- 前端从规范生成 TypeScript 类型和客户端；
- 手写包装层负责 request_id、幂等键、本地会话和错误映射；
- 禁止前后端维护两套重复 DTO；
- OpenAPI 变化必须同步契约测试和 11 文档（若语义变化）。

## 20. 安全实现约束

- 后端绑定回环并验证 Host/Origin；
- 本地会话令牌 HttpOnly、SameSite=Strict，或使用等效安全头；
- CSP 禁止任意脚本和远程资源；
- Markdown 统一 sanitize；
- 文件服务只接受对象 ID，不接受任意绝对路径；
- API Key 通过 `CredentialStorePort` 获取；
- 日志采用字段 allowlist 和集中脱敏；
- Provider、解析器和模型下载设置超时、大小与资源限制；
- 不实现模型工具调用、函数执行、shell 或任意 URL 抓取。

## 21. 配置分层

优先级从低到高：代码安全默认值、应用配置文件、允许的环境变量、启动参数。生产中安全边界配置（监听地址、凭据后端、CORS）不得由前端或普通 API 修改。

允许的主要配置：数据目录（仅启动时）、日志级别、Provider Base URL/模型、Token 上限、预算提醒、模型目录、任务并发安全范围。敏感值不进配置文件。

## 22. 开发环境

最低开发工具：Git、Python 3.12、uv、Node.js 当前 LTS、npm。开发模式分别启动 FastAPI 和 Vite；Vite 只代理 `/api`，不得保存 Key。

推荐命令语义：

~~~bash
make bootstrap
make dev
make lint
make typecheck
make test
make test-e2e
make build
make package-windows
~~~

Windows 未安装 `make` 时，必须提供等价 PowerShell 脚本；CI 和文档以脚本为权威，不依赖开发者记忆长命令。

## 23. 测试策略

### 23.1 后端

- pytest 单元测试领域规则；
- SQLite 临时数据库做仓储和迁移集成测试；
- 虚拟文件系统/临时目录测试文件事务；
- Mock Provider 测超时、断流、429 和 Schema 错误；
- 固定小向量集测范围过滤和排序。

### 23.2 前端

- Vitest 测纯逻辑和状态；
- Testing Library 测组件用户行为；
- MSW 或生成客户端 mock API；
- Playwright 覆盖 13 文档核心 E2E；
- 可访问性自动检查＋核心页人工键盘检查。

### 23.3 禁止

- 自动化测试不得使用个人真实 Key；
- 不把真实 Provider 可用性作为 PR 必过项；
- 不通过修改生产数据完成测试；
- 不以快照测试代替关键业务断言。

## 24. 构建与发布

### 24.1 构建

1. 前端 lint、typecheck、test；
2. 构建静态资源；
3. 将静态资源复制到 Python 包资源目录；
4. 后端 lint、typecheck、test；
5. 生成 OpenAPI、SBOM、许可证清单；
6. PyInstaller one-folder 构建；
7. 在干净 Windows VM 冒烟；
8. Inno Setup 生成当前用户安装包；
9. 生成 SHA-256 和版本说明。

### 24.2 为什么 one-folder

本地模型、原生扩展和解析依赖较多，one-folder 启动更快、调试和升级更可靠。V1 不追求单个 exe；安装后用户仍只需一个快捷方式。

### 24.3 模型分发

Embedding 模型不放进初始安装包。首次建索引时下载固定版本；未来可增加离线模型包，但不进入 V1。

## 25. CI 门禁

每次主分支合并至少执行：

- 前后端格式与 lint；
- TypeScript 与 Python 类型检查；
- 单元/集成/组件测试；
- OpenAPI 差异检查；
- 数据库从空库迁移到最新；
- 依赖漏洞和秘密扫描；
- 前端生产构建；
- 关键 Playwright 冒烟。

Windows 安装包、完整 E2E、性能和真实 Provider 冒烟在发布候选流程运行。

## 26. Git 与变更纪律

- 主分支始终可运行；
- 每个开发阶段形成可回退提交；
- 不提交 `.env`、API Key、用户数据、模型缓存、日志、备份和构建产物；
- schema 变化必须带 Alembic 迁移和测试；
- API 变化必须更新 OpenAPI 客户端；
- Prompt 变化必须更新版本和评测；
- 依赖升级单独提交；
- 不在修功能时大规模格式化无关文件。

## 27. 禁止的架构偏移

未经变更流程不得：

- 将前端改为 Vue 或 Next.js；
- 将后端改为 Node/Spring Boot；
- 引入云服务器、Docker 必需运行环境或账号系统；
- 将 SQLite 改为 MySQL/PostgreSQL；
- 将 sqlite-vec 改为 Chroma/LanceDB；
- 将 Embedding 改为外部 API；
- 添加自动 Provider/模型切换；
- 让前端直连 DeepSeek；
- 引入 Redis/Celery；
- 添加工具调用、任意文件写入或网页浏览；
- 把整个知识库发送给 Provider。

## 28. 架构验证 Spike

正式全面开发前，第一阶段必须用最小垂直切片验证：

1. Windows 安装/加载 sqlite-vec；
2. 512 维向量写入、过滤、查询和删除；
3. ONNX 加载 bge-small-zh-v1.5 并生成稳定向量；
4. PyInstaller 包含 sqlite-vec 与 ONNX Runtime；
5. 回环随机端口启动并打开前端；
6. Windows Credential Manager 写入/读取/删除测试 Key；
7. DeepSeek Mock 流式 SSE 贯通。

Spike 失败属于实现阻塞，应输出证据和最小替代建议后询问，不得在整套业务完成后才发现打包不可行。

## 29. 架构验收标准

- ARCH-ACC-001：仓库分层和依赖方向通过静态检查/评审；
- ARCH-ACC-002：前端不含 Provider Key 和文件真实路径；
- ARCH-ACC-003：领域层可在无 FastAPI/SQLite/DeepSeek 情况下单测；
- ARCH-ACC-004：OpenAPI 可生成客户端且契约测试通过；
- ARCH-ACC-005：sqlite-vec 在 Windows 打包产物中可查询 512 维向量；
- ARCH-ACC-006：ONNX 模型固定版本、哈希校验且无需 PyTorch；
- ARCH-ACC-007：安装包不要求 Redis、Docker、数据库服务或 Node 运行时；
- ARCH-ACC-008：本地服务仅回环监听并使用随机会话；
- ARCH-ACC-009：迁移、备份、异常退出恢复可测试；
- ARCH-ACC-010：Windows 安装包完成核心 E2E。

## 30. 本部分冻结结论

V1 最终采用 React＋TypeScript 前端、Python/FastAPI 本地后端、SQLite/FTS5/sqlite-vec、本地 ONNX `BAAI/bge-small-zh-v1.5`、DeepSeek `deepseek-flash`、SQLite 持久任务和 PyInstaller＋Inno Setup。运行时不需要云服务器、Docker、Redis、独立向量服务或 Node。开发先完成 Windows 技术 Spike，再按垂直切片推进。
